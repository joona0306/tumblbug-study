# 19주차 — 개선 한 바퀴 (PR → CI → CD → 재측정)

> 18주차에 고른 두 가지를 **실제 코드로** 고쳤다. 이 문서의 전후 측정은 **실제**다 (가상 사례의 데이터로 문제를 찾았지만, 화면 문제는 실제 코드에 있었다).
> 개선 뒤 "사용자의 배송지 통과율"이 올랐는지는 실제 사용자가 있어야 잴 수 있다 → **학습자가 강의 뒤에 잰다** (아래 5번).

## 그림 먼저 — 개선 한 바퀴
```
① 테스트 먼저 (고친 뒤 이래야 한다) → ② 고치기 전 코드에서 실패 확인 = 개선 전 기록
→ ③ 고치기 → ④ 테스트 통과 = 개선 후 기록 → ⑤ PR → CI → (합치면) CD → ⑥ 운영에서 다시 재기
```
- 테스트를 먼저 쓰는 이유: "고쳤다"를 **말이 아니라 증거**로 남기려고. 고치기 전에 실패하지 않는 테스트는 아무것도 증명하지 못한다

## 개선 ① 배송지: 무엇이 틀렸는지 그 칸에서 (18주차 후보 A + C)

**테스트 먼저**: `e2e/shipping-errors.spec.ts`
- 틀린 칸이 `aria-invalid`(틀림 표시)이고, 이유가 그 칸의 설명으로 연결된다 (화면 낭독기도 읽는다)
- 첫 번째 틀린 칸으로 이동하고, 이유가 화면 안에 보인다
- 고치는 대로 표시가 사라진다 · "가짜 주소도 괜찮아요" 안내가 있다

**측정 방법**: 휴대폰(Pixel 7)·데스크톱(1280×720)에서 받는 분만 채우고 연락처 `1234`, 주소 빈칸 → "다음: 확인". 그 순간의 화면을 잰다 (Playwright)

| | 개선 전 (실제) | 개선 후 (실제) |
|---|---|---|
| 새 테스트 | **6개 모두 실패** | **6개 모두 통과** (+ 기존 후원 흐름 테스트 통과) |
| 보이는 문장 | "받는 분·연락처·주소를 **모두** 입력해 주세요" (어느 칸인지 모름) | 칸마다: "연락처는 010-1234-5678 모양으로 입력해 주세요", "주소를 입력해 주세요" |
| 틀림 표시된 칸 | 0개 | 2개 (빨간 테두리 + `aria-invalid`) |
| 커서 위치 | "다음" 버튼에 그대로 | **연락처 칸**으로 이동 |
| 데스크톱에서 이유가 보이나 | ❌ **하단 고정 바에 가려짐** (가상 설문 1번 "아무 일도 안 일어나는 줄"이 실제로 재현) | ✅ 보임 |
| 휴대폰에서 이유가 보이나 | 보이지만 맨 아래 한 줄 | ✅ 칸 바로 아래 |

**바꾼 코드**
- `lib/funding/rules.ts` — `shippingFieldErrors()` 칸마다 이유. 서버 검사(`quote.ts`)와 단계 이동 검사는 첫 번째 이유 하나(`shippingStepError`)를 그대로 쓴다 → **규칙은 한 곳**
- `components/fund/ShippingStep.tsx` — 칸마다 `error`, 첫 틀린 칸 `focus()`, "다음"을 한 번 누른 뒤부터 고치는 대로 갱신
- `FundFlow.module.css` — 칸으로 이동할 때 하단 고정 바에 가리지 않게 `scroll-margin-bottom`
- 단위 테스트 `lib/funding/rules.test.ts` 3개 추가

## 개선 ② 운영 점검: 배송지 통과율을 바로 (18주차 후보 B)

**테스트 먼저**: `tests/db/funnel.test.ts` — 배송지에 온 4명 중 2명 통과 + 배송 없이 결제 요청 2명
- 단계 개수로는 `결제 요청 ÷ 배송지 = 100%` (틀림) · 사람을 따라가면 **50%** ← `getShippingPass()` 가 이 값을 내야 한다

| | 개선 전 (실제) | 개선 후 (실제) |
|---|---|---|
| `npm run ops:check -- --project=번호` (가상 사례) | "결제 요청 (앞 단계의 70%)" 만 → 배송지 문제가 가려짐 | `↳ 배송지 통과율 50% (배송지에 온 20명 중 10명이 결제 요청까지)` + 주의 문장 |

**바꾼 코드**: `lib/funnel.ts` 의 `getShippingPass()` (`sql/week18-funnel-paths.sql` ①과 같은 계산) · `scripts/ops-check.mts` · `scripts/simulate-ops.mts`

## ⑤ PR → CI → CD
- 브랜치 `week19/improve` → PR 본문에 18주차 근거와 위 전후 표 → CI(lint·타입·단위·흐름 테스트·빌드) 통과 → 합치기 → 운영 배포 → 연기 테스트
- 한 PR 에 개선 둘을 담았지만 **커밋은 나눴다** — 문제가 생기면 하나만 되돌릴 수 있게

## 5. 운영에서 다시 재기 (학습자가 강의 뒤에)

| 기간 | 배송지 도착 | 통과 | 통과율 | 비고 |
|---|---|---|---|---|

| 개선 후 2주 | | | % | 배포한 날짜: |
- 사람이 적으면(예: 10명 미만) 숫자가 크게 흔들린다 → 설문의 "막힌 곳"에 배송지 이야기가 줄었는지도 함께 본다
