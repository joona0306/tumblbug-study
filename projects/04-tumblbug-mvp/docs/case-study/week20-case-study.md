# 모아 — 크라우드펀딩 MVP (예시)

> 작은 창작자의 프로젝트를 후원하는 크라우드펀딩 서비스. https://tumblbug-study.vercel.app · 결제는 토스페이먼츠 **테스트 모드**

## 1. 문제와 사용자
- 1~4주차 인터뷰(교재 예시 `02-interview-synthesis-example.md`, 가상 사례)에서: 창작자는 "얼마나 모였는지·누가 후원했는지"를 한눈에, 후원자는 "내 돈이 제대로 갔는지"를 확신하고 싶어 했다
- 가장 중요한 인사이트: **한정 수량 리워드가 초과 판매되면 신뢰가 무너진다** → 기술적으로 가장 먼저 지킬 것

## 2. 무엇을 만들었나
- 흐름: 프로젝트·리워드 등록 → 목록·상세 → 리워드 → 배송지 → 테스트 결제 → 진행률·남은 수량 반영 → 마감 뒤 성공/실패 확정
- 범위에서 뺀 것: 마감 후 결제(실제 텀블벅 방식) — 결제 예약·재시도가 필요해 범위가 두 배가 된다 → 즉시 결제로 단순화 (`PLAN.md` 알려진 한계)

## 3. 디자인
- Figma 디자인 시스템: 색 토큰 22개(Light/Dark), 컴포넌트 19종, 화면 17개 + 프로토타입 — **코드의 CSS 변수·컴포넌트 이름과 1:1**
- 사용성 개선 전/후: 배송지 오류 표시 (19주차, 아래 5번)

## 4. 기술과 설계 결정
- 구조: 브라우저 → Next.js 16(Vercel, 싱가포르) → Neon PostgreSQL(싱가포르) · Vercel Blob(사진) · 토스페이먼츠(테스트) · Sentry(에러) · GitHub Actions(CI/CD·매일 운영 점검)
- 결정 (ADR 요약)
  | 결정 | 고른 것 | 포기한 것 |
  |---|---|---|
  | 모금 상태 | 읽을 때 순수 함수로 계산 + 매일 예약 작업이 확정 | 상태를 매번 DB 에 저장 (시각이 지나면 틀어진다) |
  | 초과 판매 방지 | 결제 승인 직전 **조건부 차감** + DB CHECK 제약 + 트랜잭션, 토스 호출은 트랜잭션 밖 | 락을 오래 잡기 (다른 후원이 모두 기다린다) |
  | DB 드라이버 | 표준 `pg` Pool (트랜잭션·Docker 호환) | Neon HTTP 드라이버 |
  | 상태 관리 | 서버 데이터 = 서버 컴포넌트 + TanStack Query(찜·무한 스크롤·대시보드) / 후원 단계 = Zustand(sessionStorage) / 필터 = URL | 전역 스토어 하나에 다 넣기 |
- DB **[실제]**: 목록 쿼리 인덱스 전후 12.146ms → 0.103ms (약 118배), 상세 합계 40.930ms → 0.159ms (약 257배) — `docs/explain.md`
- 배포 **[실제]**: PR → CI → 미리보기(PR 마다 DB 브랜치) → 합치기 → 운영 배포 → 연기 테스트. 같은 이미지를 Docker 로 AWS EC2 에 올리고 **롤백 연습**(553d87c ↔ d8ace9b), 고장 난 이미지는 17초 만에 자동 롤백 — `docs/aws.md`
- 품질 **[실제]**: 단위·DB 테스트 170여 개 · 흐름 테스트 110여 개(CI 에서 1분 안쪽) · Sentry 알림 · 가동 감시 · 매일 운영 점검
- 부하 **[실제]**: "남은 1개를 50명이 동시에" → 판매 1/1, 성공 1, 품절 49 — **초과 판매 0건** (로컬·EC2) — `docs/load-test.md`

## 5. 운영과 개선
- 운영 **[가상]**: 창작자 1명 · 방문자 42명 · 후원 14건 시도 → 결제 완료 11건 · 285,000원 (목표의 57%) · 핵심 지표(상세 → 결제 완료) 26.2%
- 개선 사이클
  1. **지표 [가상]**: 단계 개수로는 "결제 요청 70%" — 그런데 사람 한 명씩 따라가니 **배송지 통과율 50%** (배송 없는 리워드가 섞여 가려졌다)
  2. **관찰 [가상]**: 설문 8건 중 3건 "배송지에서 뭐가 틀렸는지 모르겠다"
  3. **확인 [실제]**: 코드와 화면에서 — 오류가 맨 아래 한 줄뿐, **데스크톱에서는 하단 고정 바에 가려져 보이지 않았다**
  4. **변경 [실제]**: 칸마다 이유 + 첫 틀린 칸으로 이동 + 가짜 주소 안내 · 운영 점검에 배송지 통과율 — 새 테스트 6개가 전 **실패** → 후 **통과**
  5. **지표 후**: 실제 사용자로 재는 것은 학습자 몫 (성공 기준 70% 이상을 고치기 **전에** 적어 둠)
- 운영 중 문제 **[실제]**: Sentry 가 잡은 Fatal — 쉬던 DB 연결이 끊기면 서버가 죽음 → `pool.on("error")` + 재현 테스트 (15주차)
- 접근성 **[실제]**: Lighthouse 가 찾은 2건(목록 제목 순서, 찜 버튼 이름에 숫자 누락) 수정 → 측정한 모든 화면 100점

## 6. 알려진 한계와 다음 단계
- 결제는 테스트 모드, 즉시 결제 · 환불·정산 없음 · 비밀번호 찾기·탈퇴 버튼 없음 (삭제는 운영자에게 요청)
- EC2(서울)에서 DB(싱가포르)까지 왕복 180ms → 서버·DB 는 같은 지역에
- 다음에 한다면: 상세에서 리워드를 더 위로(18주차 후보 D) — 먼저 관찰로 근거를 모은 뒤

## 7. 배운 것
1. **숫자는 세는 방법에 따라 거짓말을 한다** — 단계 개수 vs 사람 단위
2. **맞게 동작하는가(정확성)와 빠른가(성능)는 따로** — 초과 판매 0건이어도 EC2 에서는 느렸다
3. **배포는 되돌릴 수 있어야 끝난다** — 롤백을 연습해 보기 전까지는 배포가 무서웠다

## 운영 종료 — 약속 지키기 (실제로 확인한 방법)

`/privacy` 에 "스터디가 끝나면 모든 계정과 후원 기록을 지운다"고 적었다. 20주차 케이스 스터디를 마친 뒤:

1. (안전하게) Neon 운영 프로젝트에서 **지금 시점의 브랜치**를 하나 만든다 (`operations.md` 5번) — 실수 대비. 약속한 기간 뒤 이 브랜치도 지운다
2. **세기만** — 무엇이 몇 개 지워지는지 먼저 본다:
   ```
   DATABASE_URL="운영 DB 주소" npm run ops:end
   ```
3. 숫자가 맞으면 **DB 이름을 한 번 더 적어서** 지운다:
   ```
   DATABASE_URL="운영 DB 주소" npm run ops:end -- --confirm=DB이름
   ```
   - 관리자 계정만 남고 후원·결제 기록·퍼널·찜·프로젝트·다른 계정·요청 수 기록·로그인 기록이 **한 트랜잭션으로** 지워진다 (`lib/ops/purge.ts`)
   - DB 이름이 틀리면 지우지 않는다 · 관리자가 없으면 멈춘다
4. 사진: `BLOB_READ_WRITE_TOKEN` 이 있으면 함께 지워지고, 없으면 Vercel → Storage → Blob 에서 직접
5. Google 설문지 응답 정리, Vercel·UptimeRobot 등 알림은 필요 없으면 끈다

**[실제] 확인**: 로컬 Docker DB(연습용)에 예시 데이터 + 가상 사례를 넣고 실행 → 틀린 DB 이름: 아무것도 안 지움 / 맞는 이름: 계정 135개 → 관리자 1개, 프로젝트·후원·퍼널 0, 관리자 로그인 정보는 남음
