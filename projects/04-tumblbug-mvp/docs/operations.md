# 운영 준비 (15주차)

> 목표: **문제가 생기면 내가 먼저 안다.** 사용자가 알려 주기 전에 알림이 오고, 무엇을 보면 되는지 정해져 있다.
> 이 문서는 17주차부터 실제 사용자와 운영할 때 매일·매주 보는 안내서다.

| 무엇이 잘못될 수 있나 | 누가 알려 주나 | 이 문서 |
|---|---|---|
| 코드 에러 (화면이 깨짐, 500) | **Sentry 알림** 메일 | 1 |
| 사이트가 아예 안 열림 (서버·DB 장애) | **가동 감시** 메일 | 2 |
| 데이터가 어긋남 (재고, 결제 상태, 예약 작업) | **매일 아침 운영 점검** (GitHub Actions 실패 메일) | 3 |
| 사람들이 어디서 후원을 포기하나 | **퍼널** (`npm run ops:check`) | 4 |
| 실수로 데이터를 지움 | **백업·복구** (Neon) | 5 |

**비밀값 규칙**은 배포 때와 같다: 토큰·DB 주소는 채팅·코드·스크린샷에 붙여 넣지 않는다.

## 0. 토스 웹훅 주소 등록 (14주차에 "배포 뒤에"로 미룬 것)

결제창에서 돌아오지 못한 결제(브라우저를 닫음 등)는 **웹훅**이 마무리한다 (11주차). 운영 주소가 생겼으니 등록해 둔다.

1. 토스페이먼츠 개발자센터 → **웹훅** → **테스트** 탭 → **웹훅 등록**
2. 이름 `모아 운영` · URL `https://운영주소/api/webhooks/toss` · 이벤트 **PAYMENT_STATUS_CHANGED**
3. 주소가 살아 있는지 확인 — 가짜 알림을 보내 본다. 우리 웹훅은 알림 내용을 믿지 않고 토스에 결제를 다시 조회하므로, 없는 결제면 `200 {"result":"ignored"}` (정상), 모양이 틀리면 `400`

```bash
curl -X POST https://운영주소/api/webhooks/toss -H "Content-Type: application/json"   -d '{"eventType":"PAYMENT_STATUS_CHANGED","createdAt":"2026-01-01T00:00:00.000000","data":{"paymentKey":"fake","orderId":"fake","status":"DONE"}}'
```

> ⚠️ **알려진 한계: 테스트 결제를 해도 "전송 기록"은 비어 있다 (14주차에 실제로 확인)**
> - 이 교재는 결제위젯 **문서 예제용 공용 키**(`test_gck_docs_…`, `test_gsk_docs_…`)를 쓴다. 개발자센터 API 키 화면에도
>   "문서 예제와 같은 테스트 연동 키예요. 내 키는 전자결제 신청하고 확인할 수 있어요" 라고 나온다
> - 공용 키는 **모든 개발자가 함께 쓰는 키**라서 내 상점과 연결되어 있지 않다 → 결제·승인·조회는 되지만,
>   내 상점의 **테스트 결제내역에도 안 나오고, 내 상점에 등록한 웹훅도 불리지 않는다**
> - 내 결제위젯 키는 **전자결제 신청**(사업자등록 등 필요) 후에 나온다 → 교재 범위 밖
> - 그래서 웹훅은 이렇게 검증한다: DB 테스트 8개(`tests/db/webhook.test.ts` — 같은 알림 두 번·가짜 알림·재고 되돌리기)
>   + 운영 주소에 가짜 알림(위 3번). 실제 전송은 전자결제 신청 뒤 내 키로 바꾸면 그대로 동작한다
> - (참고) 내 상점의 **API 개별 연동 키**(`test_ck_…`)는 상점에 묶여 있어 웹훅이 실제로 오지만, 결제위젯이 아닌
>   **결제창 방식**으로 코드를 바꿔야 한다 — 이 교재는 결제위젯을 유지하기로 했다 (케이스 스터디에 이 판단을 적는다)

## 1. Sentry 알림 — 새 에러가 생기면 메일

5주차에 연결한 Sentry 는 에러를 **모아 두기만** 한다. 알림을 켜야 내가 안다.

1. Sentry → **Alerts → Create Alert** → **Issues** 선택
2. 조건: **"A new issue is created"** (처음 보는 에러가 생겼을 때) + 환경(Environment) = `production`
   - 미리보기(`preview`) 에러까지 받으면 메일이 너무 많아진다 → 운영만
3. 동작: **Send a notification to** → 나(이메일)
4. 이름: `모아 운영 — 새 에러` → 저장

**확인**: 운영 주소의 `/debug/sentry?throw=render` 를 열어 에러 화면이 나오게 한다 → 몇 분 안에 메일이 오는지 본다.
(이 주소는 5·13주차에 만든 확인용 화면이다. 확인 뒤 Sentry 에서 그 이슈를 **Resolve** 한다)

## 2. 가동 감시 — 사이트가 안 열리면 메일

Sentry 는 "앱이 돌면서 낸 에러"만 안다. 서버가 아예 멈추거나 DB 가 끊기면 에러를 보낼 수도 없다.
→ **바깥에서 몇 분마다 사이트를 두드려 보는** 서비스가 필요하다 (가동 감시, uptime monitoring).

1. 무료 가동 감시 서비스(예: UptimeRobot, Better Stack)에 가입한다 — 무료 조건(감시 간격·개수)은 자주 바뀌므로 가입할 때 확인
2. 새 감시(Monitor) 만들기
   - 종류: **HTTP(s)** · 주소: `https://운영주소/api/health`
   - 간격: 5분 (무료로 가능한 가장 짧은 간격)
   - 조건: 응답 코드가 **200** 이 아니면 실패 — `/api/health` 는 DB 가 끊기면 **503** 을 준다 (14주차)
   - (가능하면) 응답 본문에 `"ok":true` 가 있는지도 확인
   - 알림: 내 이메일
3. **확인**: 감시 화면에서 "Up"(정상)이 뜨는지. (일부러 장애를 내 보려면 16주차 EC2 실습 때 서버를 잠깐 꺼 본다)

> 알림이 오면 → 사이트를 직접 열어 본다 → Vercel **Deployments·Logs**, Neon **Monitoring**, Sentry 순서로 본다 → 끝나면 **장애 회고**를 쓴다 (`docs/04-tumblbug-mvp/templates/08-incident-review.md`)

## 3. 매일 아침 운영 점검 — 데이터가 어긋나면 메일

에러도 없고 사이트도 열리는데 **데이터가 조용히 틀어지는** 경우가 가장 찾기 어렵다. 그래서 매일 확인한다.

- `.github/workflows/ops-check.yml` 이 **매일 아침 7시(한국 시간)** 운영 DB 에 `npm run ops:check` 를 돌린다
- 문제가 하나라도 있으면 작업이 **실패** → GitHub 가 저장소 주인에게 실패 메일을 보낸다
- 설정할 것 없음: 운영 DB 주소는 이미 GitHub `production` 환경에 있다 (14주차). 바로 돌려 보려면 GitHub **Actions → Ops check → Run workflow**

| 점검 | 무엇이 잘못됐다는 뜻 | 어떻게 |
|---|---|---|
| ① 재고 어긋남 | 판매 수 ≠ 결제 완료·승인 중 수량. 실패했는데 재고를 안 되돌림 → **품절이 아닌데 품절로 보임**, 또는 두 번 되돌림 → **초과 판매 위험** | 해당 리워드의 후원 목록을 보고 원인(어떤 실패 경로였나)을 찾아 코드부터 고친다. 숫자는 그다음 SQL 로 맞춘다 |
| ② 결제 상태 어긋남 | 토스는 결제 완료인데 우리 DB 는 아님 → **돈은 나갔는데 후원 내역에 없는 사람** | 가장 급하다. 토스 개발자센터에서 결제를 확인하고, 웹훅 로그(Vercel Logs 의 `[웹훅]`)를 본다 |
| ③ 예약 작업 미실행 | 마감 하루가 지났는데 모금중 → 매일 자정 예약 작업이 안 돌았다 | Vercel **Settings → Cron Jobs** 와 Logs 의 `[예약 작업]` 줄. `CRON_SECRET` 이 있는지 |
| ④ 오래된 결제 대기 | 하루 넘게 결제 대기 → 예약 작업의 정리가 안 돌았다 | ③과 같이 본다 |

직접 보고 싶을 때:
- 개발 DB: `npm run ops:check`
- Neon 콘솔(운영, `moa-prod`) → **SQL Editor** 에 `sql/week15-ops.sql` 을 붙여 넣고 하나씩 실행 (읽기만 한다)
- 운영 DB 주소를 내 컴퓨터에 두는 것은 권하지 않는다 — 자동 점검(GitHub Actions)과 Neon 콘솔로 충분하다

## 4. 퍼널 — 어디서 가장 많이 포기하나 (PLAN 성공 지표)

```
상세 보기 → 후원 시작(리워드) → 배송지 → 결제 요청 → 결제 완료
```

- 기록: 상세·리워드·배송지는 **브라우저**가 알리고(`/api/funnel`), 결제 요청·결제 완료는 **서버**가 직접 기록한다 — 브라우저가 "결제 완료"를 꾸며 보낼 수 없게
- 같은 방문자·같은 프로젝트·같은 단계는 한 번만 센다 (새로고침해도 한 번)
- 방문자는 브라우저 쿠키(`moa-vid`)의 **무작위 값**으로만 구분한다 — 로그인 계정·IP 와 연결하지 않는다 (개인정보 없음)
- 창작자가 자기 프로젝트를 보는 것은 세지 않는다
- 읽는 법 (`npm run ops:check` 의 "퍼널")
  - **핵심 지표** = 결제 완료의 "상세의 N%" (상세를 본 사람 중 후원을 끝낸 비율)
  - **가장 많이 빠지는 곳** = "앞 단계의 N%" 가 가장 낮은 단계 → 18주차에 그 화면부터 관찰·개선
  - 100%가 넘는 단계: 공유 링크로 후원 화면에 바로 온 사람이 있으면 앞 단계보다 많을 수 있다

## 5. 백업·복구 연습 — "지웠다"를 되돌릴 수 있나

사고는 대부분 사람이 낸다 (잘못된 SQL, 잘못된 마이그레이션). **복구해 본 적 없는 백업은 백업이 아니다** — 한 번 연습해 둔다.

Neon 은 DB 의 과거 상태를 일정 기간 기억한다 (**보관 기간은 요금제마다 다르다** → 프로젝트 **Settings** 에서 확인하고 적어 두기: ____시간/일).
그 기간 안의 **아무 시점으로 새 브랜치를 만들 수 있다** — 운영 DB 는 건드리지 않고 과거 모습을 따로 꺼내 보는 것이다.

연습 (운영 `moa-prod` 에서, 운영 데이터는 바뀌지 않는다):
1. 지금 시각을 적어 둔다 → SQL Editor 에서 `select count(*) from project;` 결과를 적어 둔다
2. 운영 사이트에서 테스트 프로젝트를 하나 만든다 (복구로 "사라지게" 할 대상)
3. Neon → **Branches → Create branch** → 부모 `main`, **시점 = 1에서 적은 시각** (Point in time) → 이름 `restore-drill`
4. `restore-drill` 브랜치의 SQL Editor 에서 `select count(*) from project;` → **1의 숫자와 같으면 복구 성공** (2에서 만든 프로젝트가 없다)
5. 끝나면 `restore-drill` 브랜치를 **삭제**한다 (남겨 두면 무료 사용량을 차지한다)

실제 사고 때는: 사고 직전 시점으로 브랜치를 만들어 **필요한 줄만 꺼내 운영에 되살린다**. 운영 전체를 과거로 되돌리는 것(Restore)은 그 뒤에 생긴 정상 후원까지 사라지므로 마지막 수단이다.
연습에서 걸린 시간과 막힌 곳을 장애 회고 양식에 "연습"으로 적어 둔다.

## 6. (선택) 커스텀 도메인

`moa.example.com` 같은 내 도메인을 쓰려면 도메인을 사야 한다 (비용 발생 — 선택).
1. 도메인 구입 → Vercel 프로젝트 **Settings → Domains → Add** → 안내대로 DNS 레코드 추가
2. 주소가 바뀌므로 함께 바꾼다: Vercel 운영 `BETTER_AUTH_URL`, GitHub `production` 환경의 `PRODUCTION_URL`, 가동 감시 주소, 토스 웹훅 주소(0번)
3. 다음 배포의 연기 테스트가 새 주소로 통과하는지 본다
