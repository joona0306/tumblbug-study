# 부하 테스트 — 남은 1개를 50명이 동시에 (16주차 4단계)

> 질문: 한정 수량이 **1개 남은 리워드**를 **50명이 동시에** 결제하면, 정말 1명만 성공하나? (초과 판매 0건)
>
> 마지막 확인: 2026-09-27 · k6 2.3.0 (Docker 이미지 `grafana/k6:2.3.0`)

## 무엇을 어떻게 시험하나

- **k6** = 가상 사용자(VU) 여러 명이 동시에 요청을 보내게 하는 부하 테스트 도구. 설치 없이 Docker 로 실행한다
- 결제창(토스)은 사람이 눌러야 해서 흉내 낼 수 없다 → **결제창 다음 단계(서버의 결제 승인)** 를 동시에 두드린다
  - 진짜 서버 · 진짜 DB · 진짜 승인 함수(`confirmFunding`)를 그대로 쓰고, **토스만 가짜**로 바꾼다 (0.2초 뒤 "승인")
  - 승인 함수가 토스 도구를 바꿔 끼울 수 있게 만들어져 있어서 가능하다 (11주차, 단위 테스트의 가짜 토스와 같은 원리)
- 부하 테스트 전용 주소 (`lib/load-test.ts`, `app/api/load-test/…`)
  | 주소 | 하는 일 |
  |---|---|
  | `POST /api/load-test/setup` | 한정 1개 리워드 + 서로 다른 후원자 50명의 결제 대기 후원 (이전 시험 데이터는 먼저 지운다) |
  | `POST /api/load-test/confirm` | 결제 승인 1건 |
  | `GET /api/load-test/result?projectId=` | 판매 수 · 성공 · 품절 실패 |
  | `DELETE /api/load-test/result` | 시험 데이터 지우기 |
- **안전장치**: 평소에는 **404**(없는 주소)
  1. 서버 환경 변수 `LOAD_TEST_SECRET`(16자 이상)이 있고, 요청 머리글 `x-load-test-secret` 이 같을 때만 열린다
  2. **Vercel(운영·미리보기)에서는 값이 있어도 열리지 않는다** (`VERCEL` 환경 변수가 있으면 무조건 닫힘)
  3. 시험 데이터는 `@loadtest.moa.test` 계정으로만 만들고 그것만 지운다
- k6 스크립트 `load/oversell.js`: 준비 1번 → **50명이 동시에 1번씩 승인** → 결과 확인. 기준을 하나라도 어기면 실패(종료 코드 99)
  | 기준 | 뜻 |
  |---|---|
  | 확인(check) 100% 통과 | 판매 수 ≤ 한정 수량, 성공 딱 1건, 나머지 49건은 품절 |
  | `http_req_failed` 0% | 서버 에러·연결 실패 0건 |
  | 승인 요청 p95 < 3초 | 100명 중 95명은 3초 안에 답을 받는다 (p95 = 느린 순으로 줄 세웠을 때 95% 지점) |

## 실행

**① 내 컴퓨터 (Docker compose)** — `compose.yaml` 에 연습용 `LOAD_TEST_SECRET` 이 들어 있다
```
docker compose up -d --build
docker run --rm -i -e BASE_URL=http://host.docker.internal:3000 -e LOAD_TEST_SECRET=local-load-test-secret-000 grafana/k6:2.3.0 run - < load/oversell.js
```
- `host.docker.internal` = k6 컨테이너 안에서 "내 컴퓨터"를 가리키는 이름 (컨테이너 안의 localhost 는 컨테이너 자신)
- Git Bash 에서 경로가 이상하게 바뀌면 앞에 `MSYS_NO_PATHCONV=1` 을 붙인다

**② EC2** — 시험하는 동안만 서버 `.env` 에 `LOAD_TEST_SECRET` 을 넣고, 끝나면 **지운다**
1. 이 브랜치의 이미지를 서버로 (SSH 가 "내 IP" 여도 된다):
   `docker save moa-app:local | gzip | ssh -i ~/.ssh/moa-ec2-key.pem ubuntu@IP 'gunzip | docker load'`
2. 서버 `~/moa/.env` 에 `LOAD_TEST_SECRET=무작위값` 한 줄 → `bash ~/moa/deploy.sh moa-app:local`
3. `BASE_URL=https://IP를-로-이은.sslip.io` 로 k6 실행
4. 정리: `DELETE /api/load-test/result` → `.env` 에서 그 줄 삭제 → 원래 이미지로 `deploy.sh` → `/api/load-test/setup` 이 **404** 인지 확인

## 결과 (2026-09-27)

| | 내 컴퓨터 (앱·DB 같은 컴퓨터) | EC2 서울 (DB 는 Neon 싱가포르) |
|---|---|---|
| **판매 / 한정** | **1 / 1** | **1 / 1** |
| **성공 / 품절 실패 / 그 밖** | **1 / 49 / 0** | **1 / 49 / 0** |
| 서버 에러 | 0건 | 0건 |
| 승인 응답 시간 (중간값 / p95) | 0.80초 / 1.0초 ✅ | 2.94초 / **4.37초 ❌** (기준 3초) |
| 서버 메모리 | — | 앱 92MB · Caddy 19MB (1GB 중) |

**✅ 초과 판매 0건 — 두 곳 모두.** 50개 요청이 동시에 와도 재고 차감이 1번만 성공했다.
- 지켜 준 것 (두 겹): ① 결제 승인 직전의 **조건부 차감** — `sold_qty + 1 <= limit_qty` 일 때만 줄인다 (6·11주차) ② DB 의 **CHECK 제약** `sold_qty <= limit_qty` — 코드가 실수해도 DB 가 거절한다

**❌ EC2 에서는 느렸다 — 원인은 서버가 아니라 "DB 까지의 거리"**
- EC2(서울)에서 Neon(싱가포르)까지 **쿼리 1번 왕복 ≈ 180ms** (서버 안에서 측정)
- 승인 1건에 쿼리가 여러 번 오간다 (조회 → 트랜잭션 시작 → 선점 → 차감 → 끝 → 결과 반영 …)
- 게다가 앱은 DB 연결을 **5개만** 쓴다 (`db/index.ts`, `max: 5`) → 50개 요청이 5개 연결 앞에 줄을 선다
- → 대략 "쿼리 수 × 180ms ÷ 5" 만큼 뒤쪽 요청이 기다린다. 서버 CPU·메모리는 여유가 있었다
- 운영(Vercel)은 이 문제를 이미 피하고 있다: Vercel 함수 지역을 **싱가포르(sin1)** 로 둬서 DB 와 같은 곳에서 돈다 (14주차 `vercel.json`)

**고친다면 (이번 범위 밖 — 기록만)**
| 방법 | 효과 | 비용·부담 |
|---|---|---|
| 서버와 DB 를 같은 지역에 (EC2 를 싱가포르에, 또는 DB 를 서울에) | 왕복이 몇 ms 로 → 가장 큰 효과 | 지역을 옮겨 다시 만들기 |
| 연결 수 늘리기 (`max`) | 줄이 짧아진다 | DB 연결 한도, 서버리스(Vercel)에서는 오히려 위험 |
| 승인 한 번의 쿼리 수 줄이기 | 조금 빨라진다 | 코드가 복잡해진다 |

> 배운 것: **부하 테스트는 "맞게 동작하나"(정확성)와 "빠른가"(성능)를 따로 본다.** 정확성은 어디서나 같아야 하고, 성능은 어디에 두느냐(배치)에 따라 달라진다.
