배포하고, 측정하고, 운영하고, 개선하기

지금까지는 내 컴퓨터(localhost)에서만 돌아갔습니다. 이번 주에는 실제 인터넷 주소로 서비스를 열고, 실제 사람이 쓰게 하고, 문제가 생기면 어디를 봐야 하는지 배웁니다.

📖 용어 풀이
  • 배포(Deploy): 내 코드를 24시간 켜져 있는 남의 컴퓨터(서버)에 올려서, 누구나 인터넷 주소로 접속할 수 있게 만드는 것.
  • 운영(Operation): 배포한 서비스가 잘 돌아가는지 지켜보고, 문제를 고치고, 사용자 의견을 반영하는 일. 서비스는 배포가 끝이 아니라 시작입니다.

먼저 그림으로: 개발 환경과 운영 환경

💡 왜 DB를 둘로 나누나요?개발하다 보면 테스트 계정을 만들고, 링크를 지우고, 표 구조를 바꿔보는 일이 계속 생깁니다. 이걸 실제 사용자 데이터가 있는 DB에서 하면, 실수 한 번에 사용자의 링크가 사라집니다. 그래서 연습은 dev에서, 실제 서비스는 production에서 합니다.

📖 코드 읽는 법VERCEL_ENV는 Vercel이 자동으로 넣어주는 환경 변수로, 운영 배포면 "production"입니다. 내 컴퓨터에는 이 값이 없으니 건너뜁니다. 파일 확장자 .mjs는 "최신 방식(import) 자바스크립트 파일"이라는 표시입니다.

package.json의 "build" 한 줄을 바꿔서, 빌드 직전에 이 스크립트가 돌게 합니다.

프로젝트 최상위에 vercel.json을 만들어 서버 위치를 싱가포르로 정합니다.

💡 서버 위치가 왜 중요한가요?Vercel의 기본 서버는 미국에 있습니다. 우리 DB는 싱가포르에 있으니, 페이지 하나를 열 때마다 미국↔싱가포르를 여러 번 오가느라 느려집니다. 서버를 DB 옆(싱가포르, sin1)에 두면 빨라집니다.

마지막으로 drizzle.config.js에서 한 줄을 바꿉니다. loadEnvConfig(process.cwd()) → loadEnvConfig(process.cwd(), true)

💡 true 하나가 왜 필요해요?이 값이 없으면 drizzle-kit이 "운영 모드"로 환경 변수를 읽습니다. 나중에 운영용 설정 파일(.env.production.local)을 만들면, 내 컴퓨터에서 친 npm run db:migrate가 운영 DB에 실행될 수 있어요. true(개발 모드)로 고정해 항상 개발 DB를 쓰게 합니다.
✅ 여기까지 됐는지 확인하는 법

내 컴퓨터에서 운영용 빌드를 해봅니다. 개발 서버는 꺼 두세요.

맨 처음에 [migrate] 운영 배포가 아니므로 DB 마이그레이션을 건너뜁니다., 마지막에 ✓ Compiled successfully와 주소 목록(/dashboard, /[username] 등)이 나오면 성공입니다.

  • .env.local 파일이 목록에 없다 (있으면 즉시 저장소를 Private으로 바꾸고, Neon에서 DB 비밀번호를 재설정하세요)
  • 커밋 기록(Commits)에 2~4주차 동안 남긴 단계별 커밋이 보인다
3개발용 DB와 운영용 DB 나누기

Neon은 DB를 통째로 복사한 브랜치를 만들 수 있습니다. 지금까지 쓰던 기본 브랜치는 운영용으로 남기고, 개발용 브랜치를 새로 만들어 내 컴퓨터는 그쪽을 보게 바꿉니다.

📖 용어 풀이DB 브랜치: 특정 시점의 DB를 복사한 별도 DB입니다. 복사본에서 무엇을 하든 원본에는 영향이 없습니다. Git 브랜치와 비슷한 개념이에요.

① dev 브랜치 만들고 내 컴퓨터 연결 바꾸기

  1. Neon 대시보드 → 왼쪽 Branches → New branch
  2. Name: dev, Parent branch: 기본 브랜치(production 또는 main) → 만들기
  3. 만든 dev 브랜치 화면에서 Connect → 주소 복사
  4. .env.local의 DATABASE_URL= 값을 dev 브랜치 주소로 교체하고 개발 서버를 껐다 켭니다

dev 브랜치는 기본 브랜치를 복사한 것이라 테스트 계정과 링크가 그대로 들어 있습니다. localhost:3000/dashboard에 로그인이 그대로 되는지 확인하세요.

② 운영 DB의 테스트 데이터 지우기

운영 DB는 실제 사용자만 쓰도록 깨끗하게 비웁니다. Neon → SQL Editor에서 위쪽 브랜치 선택이 기본 브랜치(production/main)인지 꼭 확인한 뒤 실행합니다.

💡 user만 지웠는데 링크도 지워지나요?네. 2주차 설계에서 session, account, link의 user_id에 onDelete: "cascade"를 걸었습니다. "주인이 사라지면 딸린 줄도 함께 삭제"라는 뜻이라, 사용자를 지우면 그 사람의 세션·비밀번호·링크가 한꺼번에 지워집니다.
✅ 여기까지 됐는지 확인하는 법
  • Neon Tables에서 브랜치를 기본 브랜치로 두면 user, link 표가 비어 있다 (표 자체는 5개 그대로 있음)
  • 브랜치를 dev로 바꾸면 테스트 데이터가 그대로 있다
  • 내 컴퓨터의 localhost:3000/api/health가 여전히 ok: true
4Vercel로 배포하기

① 운영용 비밀키 새로 만들기

운영 서비스는 개발용과 다른 비밀키를 씁니다. 개발용 키가 새더라도 운영 서비스는 안전하게 하려는 것입니다.

② 프로젝트 가져오기와 환경 변수

  1. vercel.com/new → Import Git Repository에서 my-links 옆 Import (목록에 없으면 GitHub 접근 권한 설정에서 저장소를 허용)
  2. Framework Preset이 Next.js로 자동 선택된 것 확인
  3. Environment Variables를 펼쳐 3개를 넣습니다
    KeyValue
    DATABASE_URLNeon 기본 브랜치(production/main)의 Connect 주소 — dev 주소가 아님!
    BETTER_AUTH_SECRET①에서 새로 만든 문자열
    BETTER_AUTH_URLhttps://my-links.vercel.app (일단 이렇게 넣고 ③에서 확인)
  4. Deploy 클릭 → 1~3분 기다리기

③ 실제 주소 확인하고 맞추기

배포가 끝나면 프로젝트 화면의 Domains에 실제 주소가 보입니다. 이름이 이미 쓰이고 있으면 my-links-abc123.vercel.app처럼 뒤에 글자가 붙을 수 있어요.

  • 주소가 BETTER_AUTH_URL에 넣은 값과 다르면: Settings → Environment Variables에서 BETTER_AUTH_URL을 실제 주소(https://로 시작, 끝에 / 없이)로 고치고 → Deployments 탭 → 맨 위 배포의 ⋯ → Redeploy
📖 빌드 로그 읽기Deployments → 배포 하나 클릭 → Building 로그에서 [migrate] 운영 DB 마이그레이션 완료를 찾아보세요. 1단계에서 만든 스크립트가 운영 DB 구조를 확인하고 맞춘 흔적입니다.
✅ 여기까지 됐는지 확인하는 법
  1. https://내주소.vercel.app/api/health → {"ok":true,...}
  2. 휴대폰(와이파이 끄고 데이터로)에서 내 주소 → 회원가입 → 링크 3개 추가 → 공개 페이지 확인
  3. Neon에서 기본 브랜치의 user 표에 방금 가입한 1줄이 생겼고, dev 브랜치에는 없다
🆘 막혔을 때
빌드가 DATABASE_URL 환경 변수가 없습니다로 실패해요

Settings → Environment Variables에 DATABASE_URL이 있는지, 적용 환경에 Production이 체크되어 있는지 확인하고 Redeploy 하세요.

가입/로그인 버튼을 누르면 에러가 나거나 로그인이 유지되지 않아요

거의 항상 BETTER_AUTH_URL이 실제 주소와 다른 경우입니다. 주소창의 주소와 글자 하나까지 같은지(https, 끝의 / 없음) 확인하고 Redeploy 하세요. 환경 변수는 다시 배포해야 반영됩니다.

/api/health가 ok: false

DATABASE_URL 값을 복사할 때 앞뒤 공백이나 줄바꿈이 들어갔는지 확인하세요.

5사용량 측정: 방문 수와 성공 지표

1주차에 정한 성공 지표를 실제로 잴 준비를 합니다. 두 가지 도구를 씁니다.

무엇을어떻게알 수 있는 것
방문 수Vercel Analytics (무료)몇 명이 어느 페이지를 봤나, 어느 나라·기기에서 왔나
성공 지표운영 DB에 SQL 한 번 실행가입자 중 링크를 1개 이상 등록한 비율

① 방문 수 측정 붙이기

app/layout.js에 두 줄(맨 위 import, <Analytics />)을 추가합니다.

commit + push로 배포한 뒤, Vercel 프로젝트 화면의 Analytics 탭에서 Enable(Web Analytics 켜기)을 누릅니다.

💡 개인정보는 괜찮나요?Vercel Web Analytics는 쿠키를 쓰지 않고, 방문자를 개인 단위로 추적하지 않는 방식으로 페이지뷰를 셉니다. 그래서 별도 동의 팝업 없이 쓸 수 있는 편입니다. 서비스를 키우면 개인정보처리방침에 "방문 통계를 수집한다"는 문장은 꼭 넣으세요.

② 성공 지표를 SQL로 계산하기

이 SQL은 프로젝트에 파일로 저장해 두고(sql/success-metric.sql), 필요할 때 Neon SQL Editor에 붙여넣어 실행합니다. 이때 브랜치가 운영(production/main)인지 꼭 확인하세요.

📖 SQL 읽는 법count(*) = 전체 줄 수(가입자 수). FILTER (WHERE EXISTS (…)) = "그중 link 표에 내 id로 된 줄이 하나라도 있는 사람만" 세기. nullif(count(*), 0)는 가입자가 0명일 때 0으로 나누는 오류를 막아줍니다.
✅ 확인하는 법
  • 휴대폰으로 운영 주소를 몇 번 열고 몇 분 뒤 Vercel Analytics 탭에 방문 수가 잡힌다 (내 컴퓨터의 localhost 방문은 세지 않습니다)
  • SQL을 실행하면 가입자_수 | 링크_등록자_수 | 등록_비율_퍼센트 한 줄이 나온다. (작성자 검증: 가입자 3명 중 2명이 링크 등록 → 66.7)

6운영 루프: 로그 보기, 두 DB 확인

① 로그 보기

서비스에서 문제가 생기면 가장 먼저 보는 곳이 로그입니다. 서버에서 일어난 일이 시간순으로 기록되어 있어요.

  1. Vercel 프로젝트 → Logs 탭
  2. 휴대폰으로 /없는이름 같은 주소에 접속 → 로그에 그 요청이 404와 함께 찍히는 것을 찾아보세요
  3. 코드에서 console.error(...)로 남긴 메시지(예: "DB 연결 실패")는 여기에 빨간 줄로 나타납니다
💡 서비스 상태를 확인하는 순서
  1. /api/health → DB가 살아 있나?
  2. Vercel Logs → 빨간 에러 줄이 있나? 언제부터?
  3. Deployments → 문제가 시작된 시각에 새 배포가 있었나? (있다면 그 배포의 변경이 원인일 가능성이 큼)

② 두 DB가 정말 분리되었는지 확인

내 컴퓨터(localhost)에서 링크를 하나 추가해 보세요. 운영 주소의 공개 페이지에는 나타나지 않아야 합니다. 반대로 운영에서 가입한 계정으로는 localhost에 로그인할 수 없습니다.

📖 나중에 표 구조를 바꾸고 싶다면
  1. db/schema.js 수정
  2. npx drizzle-kit generate --name 변경내용 → npm run db:migrate (dev DB에 먼저 적용해 확인)
  3. commit + push → Vercel 빌드에서 migrate.mjs가 운영 DB에 같은 변경을 적용

이렇게 하면 운영 DB를 손으로 건드릴 일이 없습니다. (2단계 이후 교재에서 실제로 해봅니다)

접근성은 눈이 불편하거나, 마우스를 쓰기 어렵거나, 작은 화면을 쓰는 사람도 서비스를 쓸 수 있게 하는 것입니다. 세 가지만 확인합니다.

  1. 키보드만으로: 마우스를 치우고 Tab(다음), Shift+Tab(이전), Enter(누르기)만으로 가입 → 링크 추가 → 수정 → 삭제를 해보세요. 지금 어디에 있는지 파란 테두리(포커스 표시)가 항상 보여야 합니다.
  2. 자동 점검(Lighthouse): 크롬에서 F12 → Lighthouse 탭 → Categories에서 Accessibility만 체크 → Analyze. 90점 이상이 목표이고, 빨간 항목이 있으면 설명을 따라 고칩니다. (작성자 검증: 교재 코드 그대로면 로그인·회원가입·대시보드·공개 페이지 모두 100점)
  3. 크게 보기: Ctrl++로 200%까지 확대해도 글자가 잘리거나 겹치지 않는지 확인. 1주차에 색을 바꿨다면 대비(4.5:1)도 다시 확인하세요.
8지표 기반으로 개선 1개 하기

이제 1단계의 마지막 조각입니다. 감으로 고치지 않고, 숫자로 문제를 찾고 → 관찰로 원인을 짐작하고 → 고친 뒤 → 다시 숫자로 확인합니다.

예시로 한 바퀴

  1. 지표: 가입자 5명 중 2명만 링크 등록 → 40% (목표 70%)
  2. 관찰: 사용성 테스트에서 2명이 가입 직후 "이제 뭘 하면 되지?"라며 화면을 위아래로 스크롤함
  3. 가설: "링크가 0개일 때 추가 폼이 아래쪽에 있어 눈에 안 띈다. 빈 상태 안내 문구를 '첫 링크를 추가해보세요 ↓'처럼 바꾸고 폼을 위로 올리면 등록 비율이 오를 것"
  4. 수정·배포: 그 한 가지만 고쳐서 commit + push
  5. 다시 측정: 새로 가입한 사람들로 며칠 뒤 SQL을 다시 실행해 비교

내 서비스의 실제 숫자와 관찰 기록으로 한 바퀴를 돌아보세요. 사람이 적어 숫자가 크게 의미 없더라도, 이 순서로 생각하는 연습이 목표입니다. 고칠 것은 1주차 범위(포함 칸) 안에서 고르고, 범위 밖 요청(예: 테마 꾸미기)은 기획 문서의 "다음에 할 것"에 적어 두세요.

push하면 Vercel Deployments 탭에 새 배포가 생기고, 1~2분 뒤 운영 주소에 반영됩니다.
