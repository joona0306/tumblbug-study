# 4단계: 텀블벅 MVP — 포트폴리오 프로젝트 교재 기획서

**교재 제작 상태**: 기획 확정 / 정답 코드 작성 전
**학습 기간**: 16주 (약 4개월, 4~8개월차)
**학습 목표**: 실무와 같은 과정으로 **기획 → UX/UI → 구현 → 배포 → 운영 → 개선**을 완주하고,
그 과정의 결정과 결과를 **케이스 스터디**로 정리해 포트폴리오로 제시할 수 있게 하기

## 1~3단계와 무엇이 다른가
| 영역 | 1~3단계 (기초) | 4단계 (포트폴리오 수준) |
|---|---|---|
| 기획 | 경쟁 서비스, 포함/제외 표 | 사용자 인터뷰 3~5명, PRD(요구사항 문서), 결정 기록(ADR), 상태 전이도 |
| UI/UX | 종이 와이어프레임, 색 토큰 | Figma 흐름도 → 와이어프레임 → 시안, 디자인 시스템(상태별 컴포넌트·아이콘), 클릭 프로토타입으로 사용성 테스트, 로딩·빈 화면·에러 상태 설계 |
| 상태 관리 | useState, useActionState, URL 필터를 기능별로 사용 | "이 값은 어디에 두나" 기준(서버·URL·폼·화면·전역), 전역 상태 라이브러리(Zustand), 낙관적 업데이트, React Context |
| 구현 | 한 줄기로 바로 커밋 | 기능별 브랜치 → PR → CI 통과 → 병합, zod 입력 검사, 단위 테스트(Vitest), 흐름 테스트(Playwright) |
| 배포 | Vercel 1회 배포 | PR마다 미리보기 배포 + 미리보기 전용 DB 브랜치, (선택) 커스텀 도메인 |
| 운영 | 로그, SQL 지표 | 에러 모니터링(Sentry), 퍼널 지표, 예약 작업 감시, 백업·복구 연습, 관리자 화면 |
| 개선 | 지인 1명 피드백 | 실제 창작자 1명의 프로젝트 운영, 개선 전후 지표, 케이스 스터디 |

- 모든 독자가 **같은 텀블벅 클론**을 만든다. 대신 포트폴리오의 차별점은
  **각자의 인터뷰·결정 기록·실제 운영 지표·케이스 스터디**에서 나온다.

## 선수 지식
- 1~3단계 완료 (특히 2단계 결제, 3단계 사진 업로드·TypeScript)
- 계정: Figma(무료), Sentry(무료), GitHub, Vercel, Neon, 토스페이먼츠 개발자센터

## 문제 정의
> 창작자가 프로젝트(목표 금액·마감일·리워드 포함)를 올리면 후원자가 리워드를 골라 후원(결제)하고,
> 마감일에 목표 달성 여부에 따라 프로젝트가 성공/실패로 끝난다.

## 사용자와 권한
| 역할 | 할 수 있는 것 |
|---|---|
| 방문자 | 프로젝트 목록·상세 보기 |
| 후원자 (로그인) | 찜하기, 리워드 선택 후원(결제), 내 후원·찜 목록 보기 |
| 창작자 (로그인) | 내 프로젝트·리워드 등록·수정, 내 프로젝트의 모금 현황·후원자·배송지 보기 |
| 관리자 | 프로젝트 숨기기, 결제 실패 목록 보기 |
- 한 사람이 후원자이자 창작자일 수 있다. 단, **내 프로젝트에는 후원할 수 없다**
- 배송지는 **결제 완료된 후원**에 한해 **그 프로젝트의 창작자만** 볼 수 있다 (개인정보)

## 기능 범위 (반드시 이 표를 지킬 것 — 스코프 크립 방지)

| 포함 | 제외 |
|---|---|
| 프로젝트 등록/수정 (대표 사진 1장, 제목, 한 줄 요약, 소개, 카테고리, 목표 금액, 마감일) | 사진 여러 장, 동영상 |
| 리워드 등록/수정 (이름, 설명, 금액, 수량 한정(선택), 예상 전달 시기, 배송 필요 여부) | 리워드 옵션(색상·사이즈), 리워드 여러 개 한 번에 담기 |
| 공개 목록 (카테고리·모금중/성공/실패 필터, 마감 임박순·인기순) | 추천 알고리즘, 검색 |
| 상세 (진행률 %, 모인 금액, 후원자 수, 남은 일수, 리워드 목록·남은 수량) | 업데이트 글, 댓글 |
| **여러 단계 후원**: ① 리워드 선택(+ 추가 후원금) ② 배송지 ③ 확인·결제 — 리워드 없이 후원도 가능 | 실제 결제(라이브), 정기 후원 |
| 수량 한정 리워드의 품절 처리 (동시에 결제해도 초과 판매 없음) | 예약 대기, 재입고 알림 |
| 찜하기 (카드·상세·헤더 개수에 즉시 반영) + 내 찜 목록 | 찜한 프로젝트 마감 알림 |
| 모금 상태 자동 계산 (모금중 → 성공/실패) | 목표 미달 시 자동 환불, 정산 자동화 |
| 창작자 대시보드 (내 프로젝트 현황, 후원자·리워드·배송지 목록) | 배송 추적, 이메일·카카오톡 알림 |
| 내 후원 내역 (리워드·배송지·프로젝트 결과) | 후원 취소·변경 |
| 관리자 화면 (프로젝트 숨기기, 결제 실패 목록) | 신고 기능, 관리자 여러 등급, 소셜 로그인 |

- **알려진 한계(케이스 스터디에 적을 것)**: 실제 텀블벅은 마감 후 성공한 프로젝트만 결제되지만,
  이 MVP는 후원 즉시 (테스트) 결제된다. 실패 시 환불은 범위 밖

## 화면 목록
1. 홈 `/` (대표 프로젝트, 카테고리, 마감 임박·인기 프로젝트)
2. 프로젝트 목록 `/projects` (카테고리·상태 필터, 정렬 — 모두 주소(URL)에 저장)
3. 프로젝트 상세 `/projects/[id]` (진행률, 리워드 목록, 찜, 하단 고정 후원 바)
4. 후원하기 `/projects/[id]/fund` — ① 리워드 ② 배송지 ③ 확인·결제 → 결제 성공/실패
5. 프로젝트 만들기·수정 `/projects/new`, `/projects/[id]/edit` (기본 정보 + 리워드)
6. 창작자 대시보드 `/studio` (모금 현황, 후원자·배송지 목록)
7. 내 후원 내역 `/me/fundings`, 내 찜 `/me/likes`
8. 관리자 `/admin` (프로젝트 숨기기, 결제 실패 목록)
9. 회원가입 / 로그인

## 데이터 구조
```
user         : Better Auth 구조 + role(user | admin)
project      : id, creator_id, title, summary, description, category, goal_amount,
               deadline(마감일), image_url, status(funding | success | failed, 확정값), hidden,
               created_at, updated_at
reward       : id, project_id, title, description, price, limit_qty(null = 무제한), sold_qty,
               delivery_month, needs_shipping, sort_order, created_at
funding      : id, project_id, supporter_id, reward_id(null = 리워드 없이), quantity, extra_amount,
               amount(총액), message, recipient_name, recipient_phone, address,
               order_id, payment_key, status(pending | paid | failed), fail_reason, created_at, paid_at
project_like : user_id, project_id, created_at  (둘을 합쳐 기본 키 = 같은 프로젝트를 두 번 찜할 수 없음)
```
- 관계: user 1 : N project, project 1 : N reward, user 1 : N funding, project 1 : N funding, user N : M project(찜)

## 상태 전이 (2주차에 그림으로 그리고 ADR로 남길 것)
- **프로젝트**: 모금중 → 성공 | 실패 (마감 시각에 한 번만, 되돌아가지 않음)
- **후원(결제)**: 결제 대기(pending) → 완료(paid) | 실패(failed) (완료·실패는 끝 상태)
- **리워드 수량**: 남음 → 품절 (sold_qty = limit_qty). 결제 승인이 실패하면 차감을 되돌린다

## 상태 관리 지도 (5주차에 이 표를 이 앱 기준으로 채움)
| 상태 종류 | 어디에 두나 | 이 앱의 예 |
|---|---|---|
| 서버 상태 | DB → 서버 컴포넌트에서 읽기, 변경 후 `revalidatePath` | 프로젝트·리워드·후원 목록, 모인 금액 |
| URL 상태 | 주소의 `searchParams` (공유·뒤로가기 가능) | 목록의 카테고리·상태 필터, 정렬 |
| 폼 상태 | `useActionState`, `useFormStatus` | 입력 에러 메시지, 결제 버튼 "처리 중…" |
| 화면 임시 상태 | `useState` | 수량 +/− 버튼, 탭 선택 |
| 전역 클라이언트 상태 | **Zustand** | ① 후원 단계 간 선택 유지(`persist`로 새로고침해도 유지) ② 찜 목록(카드·상세·헤더가 공유, 낙관적 업데이트 + 실패 시 되돌리기) |
| 앱 전체 공유 값 | React Context | 토스트 알림 |
- **TanStack Query**는 비교 수업으로 다룬다: "브라우저가 서버 데이터를 직접 가져와 캐시하는 도구 — 이 앱은 서버 컴포넌트가 그 일을 해서 필수가 아니다". 찜 기능을 TanStack Query로 바꿔 보는 선택 과제 제공

## 결정 사항
- **모금 상태 계산**: 순수 함수 `getProjectStatus(목표, 모인 금액, 마감일, 지금)` 하나로 정의한다.
  - 화면은 항상 이 함수의 결과를 쓴다 (언제 봐도 정확)
  - Vercel Cron이 하루 1번 마감된 프로젝트의 `status`를 DB에 확정 저장한다 (목록 필터·기록용)
  - 이 함수가 단위 테스트의 첫 대상 (마감 당일 23:59, 목표 딱 도달 등 경계값)
- **마감 시각**: 마감일의 23:59:59 한국 시간
- **결제**: 2단계 흐름(서버가 금액 기록 → 서버 승인) 재사용 + 서버 검사 추가:
  마감 지난 프로젝트·숨김 프로젝트·내 프로젝트에는 후원 불가, 금액 범위,
  **총액은 서버가 리워드 가격 × 수량 + 추가 후원금으로 다시 계산** (브라우저가 보낸 총액을 믿지 않음)
- **수량 한정 (초과 판매 방지)**: 결제 승인 직전에 조건부 차감
  `UPDATE reward SET sold_qty = sold_qty + 수량 WHERE id = ? AND (limit_qty IS NULL OR sold_qty + 수량 <= limit_qty)`
  - 바뀐 줄이 0개면 품절 → 결제를 **승인하지 않고**(돈이 빠져나가지 않음) 실패 처리
  - 결제 승인이 실패하면 차감한 수량을 되돌린다
  - Playwright/단위 테스트로 "남은 1개를 두 명이 동시에" 경우를 검증
- **사진**: 3단계 Vercel Blob 흐름 재사용
- **디자인**: Figma(무료)에서 디자인 시스템(색·글꼴·간격 토큰 + 상태별 컴포넌트 + 아이콘)을 만들고,
  같은 이름의 CSS 변수·React 컴포넌트로 옮긴다. 모바일 우선 + 데스크톱
- **공학 도구 (모두 필수)**: zod(입력 검사), Vitest(단위 테스트), Playwright(흐름 테스트),
  GitHub Actions(CI: 코드 검사·타입 검사·테스트·빌드), Sentry(에러 모니터링), Zustand(전역 상태)
- **개발 방식**: 기능마다 브랜치 → PR(셀프 리뷰 체크리스트) → CI 통과 → 병합 → 자동 배포
- **결제는 테스트 모드 유지** (라이브 결제에는 사업자등록 등이 필요 — 2단계 부록 참고)
- **커스텀 도메인**: 선택 (도메인 구매 비용 발생)

## 성공 지표
- **핵심 지표**: 프로젝트 상세를 본 방문자 중 후원을 완료한 비율
- **퍼널**: 상세 → 후원 시작(리워드 선택) → 배송지 → 결제 요청 → 결제 완료 (어디서 가장 많이 빠지는지)
- **보조**: 프로젝트 성공률, 결제 실패 이유 분포, 찜 → 후원 전환율

## 주차별 체크리스트

### 기획 (1~2주)
- [ ] 1주차: 경쟁 서비스 분석(텀블벅·와디즈·킥스타터) / 창작자·후원자 인터뷰 3~5명 / 인사이트 정리
- [ ] 2주차: PRD(문제·사용자·범위·지표·위험) / 결정 기록(ADR) 시작 / 데이터 모델 / 상태 전이도

### UX/UI (3~4주)
- [ ] 3주차: 사용자 흐름도(창작자·후원자·관리자, 여러 단계 후원 포함) / Figma 와이어프레임
- [ ] 4주차: 디자인 시스템(토큰·아이콘·상태별 컴포넌트) / 모바일·데스크톱 시안 / 클릭 프로토타입으로 사용성 테스트 3명 → 수정

### 구현 (5~11주)
- [ ] 5주차: 프로젝트 준비 — TypeScript, zod, Vitest, Playwright, GitHub Actions CI, PR 흐름, Sentry / 디자인 시스템을 코드로 / 상태 관리 지도
- [ ] 6주차: 인증·역할 / 프로젝트 등록·수정 (사진, zod 검사)
- [ ] 7주차: 리워드 등록·수정 / 홈·목록(URL 필터)·상세·진행률 / 모금 상태 함수 + 단위 테스트
- [ ] 8주차: 여러 단계 후원 흐름 — Zustand 스토어 + `persist`, 단계 이동 규칙, 서버 총액 재계산
- [ ] 9주차: 결제 + 수량 한정(조건부 차감·품절·되돌리기) / 동시 결제 테스트 / 내 후원 내역 / 결제 흐름 테스트(Playwright)
- [ ] 10주차: 찜하기 — Zustand 공유 상태 + 낙관적 업데이트(실패 시 되돌리기) / 토스트(React Context) / TanStack Query 비교 수업
- [ ] 11주차: 창작자 대시보드(후원자·배송지) / 관리자 화면 / 상태 확정 예약 작업 / 로딩·빈 화면·에러 상태

### 배포·운영 준비 (12주)
- [ ] 12주차: 운영 배포 / 미리보기 배포 + DB 브랜치 / Sentry 알림 / 퍼널 지표 SQL / 백업·복구 연습 / (선택) 커스텀 도메인

## 운영 루프
- Sentry로 에러가 나면 알림 → 원인 확인 → 수정 PR
- 퍼널 지표로 가장 많이 빠지는 단계 찾기 → 사용성 관찰 → 가설 → 개선 → 재측정
- 예약 작업(상태 확정)이 매일 돌았는지 로그 확인
- 품절·결제 실패 이유 분포 확인 (수량 차감이 되돌려졌는지 점검 SQL)
- 백업·복구 연습: Neon의 특정 시점 복구로 "실수로 지운 데이터 되살리기"

## 완료 기준 (Definition of Done)
- [ ] 프로젝트·리워드 등록 → 목록 노출 → 리워드 선택 → 배송지 → 결제 → 진행률·남은 수량 반영까지 끊김 없이 동작
- [ ] 후원 단계 중 새로고침해도 선택이 유지되고, 결제 완료 후에는 초기화된다
- [ ] 남은 수량보다 많이 팔리지 않는다 (동시 결제 테스트 통과)
- [ ] 찜이 카드·상세·헤더에 즉시 반영되고, 서버 실패 시 되돌아간다
- [ ] 마감일이 지나면 목표 달성 여부에 따라 성공/실패로 바뀌고, 예약 작업이 DB에 확정한다
- [ ] 권한이 분리되어 있다 (남의 프로젝트 수정 불가, 내 프로젝트 후원 불가, 배송지는 해당 창작자만, 관리자만 숨김)
- [ ] 모든 PR에서 CI(코드 검사·타입 검사·단위 테스트·흐름 테스트·빌드)가 통과한다
- [ ] 운영 중 발생한 에러가 Sentry에 기록되고 알림이 온다
- [ ] Figma 디자인 시스템과 코드의 토큰·컴포넌트 이름이 일치한다
- [ ] 실제 창작자 1명의 프로젝트를 운영하고, 개선 1회 이상의 전후 지표가 있다
- [ ] 케이스 스터디가 완성되어 포트폴리오로 제시할 수 있다 (상태 관리 도구 선택 이유 포함)
- [ ] 키보드 조작 가능, Lighthouse 접근성 90점 이상
