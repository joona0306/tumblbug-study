# 4단계: 텀블벅 MVP — 포트폴리오 프로젝트 교재 기획서

**교재 제작 상태**: 기획 확정 / 정답 코드 작성 전
**학습 기간**: 14주 (약 3.5개월, 4~7개월차)
**학습 목표**: 실무와 같은 과정으로 **기획 → UX/UI → 구현 → 배포 → 운영 → 개선**을 완주하고,
그 과정의 결정과 결과를 **케이스 스터디**로 정리해 포트폴리오로 제시할 수 있게 하기

## 1~3단계와 무엇이 다른가
| 영역 | 1~3단계 (기초) | 4단계 (포트폴리오 수준) |
|---|---|---|
| 기획 | 경쟁 서비스, 포함/제외 표 | 사용자 인터뷰 3~5명, PRD(요구사항 문서), 결정 기록(ADR) |
| UI/UX | 종이 와이어프레임, 색 토큰 | Figma 흐름도 → 와이어프레임 → 시안, 디자인 시스템, 시안으로 사용성 테스트, 로딩·빈 화면·에러 상태 설계 |
| 구현 | 한 줄기로 바로 커밋 | 기능별 브랜치 → PR → CI 통과 → 병합, zod 입력 검사, 단위 테스트(Vitest), 흐름 테스트(Playwright) |
| 배포 | Vercel 1회 배포 | PR마다 미리보기 배포 + 미리보기 전용 DB 브랜치, (선택) 커스텀 도메인 |
| 운영 | 로그, SQL 지표 | 에러 모니터링(Sentry), 퍼널 지표, 예약 작업 감시, 백업·복구 연습, 관리자 화면 |
| 개선 | 지인 1명 피드백 | 실제 창작자 1명의 프로젝트 운영, 개선 전후 지표, 케이스 스터디 |

- 모든 독자가 **같은 텀블벅 클론**을 만든다. 대신 포트폴리오의 차별점은
  **각자의 인터뷰·결정 기록·실제 운영 지표·케이스 스터디**에서 나온다.

## 선수 지식
- 1~3단계 완료 (특히 2단계 결제, 3단계 사진 업로드·TypeScript)
- 계정: Figma(무료), Sentry(무료), GitHub, Vercel, Neon, 토스페이먼츠 개발자센터

## 문제 정의
> 창작자가 프로젝트(목표 금액·마감일 포함)를 올리면 후원자가 후원(결제)하고,
> 마감일에 목표 달성 여부에 따라 프로젝트가 성공/실패로 끝난다.

## 사용자와 권한
| 역할 | 할 수 있는 것 |
|---|---|
| 방문자 | 프로젝트 목록·상세 보기 |
| 후원자 (로그인) | 후원(결제), 내 후원 내역 보기 |
| 창작자 (로그인) | 내 프로젝트 등록·수정, 내 프로젝트의 모금 현황·후원 목록 보기 |
| 관리자 | 프로젝트 숨기기, 결제 실패 목록 보기 |
- 한 사람이 후원자이자 창작자일 수 있다. 단, **내 프로젝트에는 후원할 수 없다**

## 기능 범위 (반드시 이 표를 지킬 것 — 스코프 크립 방지)

| 포함 | 제외 |
|---|---|
| 프로젝트 등록/수정 (대표 사진 1장, 제목, 한 줄 요약, 소개, 카테고리, 목표 금액, 마감일) | 리워드 여러 옵션 + 재고 관리 |
| 공개 목록 (모금중/성공/실패 필터, 마감 임박순) | 추천 알고리즘, 검색 |
| 상세 (진행률 %, 모인 금액, 후원자 수, 남은 일수) | 업데이트 글, 댓글 |
| 후원(결제) — 금액 직접 입력(1,000원~1,000,000원) + 응원 메시지 | 실제 결제(라이브), 정기 후원 |
| 모금 상태 자동 계산 (모금중 → 성공/실패) | 목표 미달 시 자동 환불, 정산 자동화 |
| 창작자 대시보드 (내 프로젝트 현황, 후원 목록) | 이메일·카카오톡 알림 |
| 내 후원 내역 | 소셜 로그인 |
| 관리자 화면 (프로젝트 숨기기, 결제 실패 목록) | 신고 기능, 관리자 여러 등급 |

- **알려진 한계(케이스 스터디에 적을 것)**: 실제 텀블벅은 마감 후 성공한 프로젝트만 결제되지만,
  이 MVP는 후원 즉시 (테스트) 결제된다. 실패 시 환불은 범위 밖

## 화면 목록
1. 프로젝트 목록 `/` (상태 필터, 마감 임박순)
2. 프로젝트 상세 `/projects/[id]` (진행률, 후원 버튼)
3. 후원하기 `/projects/[id]/fund` → 결제 성공/실패
4. 프로젝트 만들기·수정 `/projects/new`, `/projects/[id]/edit` (창작자)
5. 창작자 대시보드 `/studio` (내 프로젝트들의 모금 현황)
6. 내 후원 내역 `/me/fundings`
7. 관리자 `/admin` (프로젝트 숨기기, 결제 실패 목록)
8. 회원가입 / 로그인

## 데이터 구조
```
user    : Better Auth 구조 + role(user | admin)
project : id, creator_id, title, summary, description, category, goal_amount,
          deadline(마감일), image_url, status(funding | success | failed, 확정값), hidden,
          created_at, updated_at
funding : id, project_id, supporter_id, amount, message, order_id, payment_key,
          status(pending | paid | failed), fail_reason, created_at, paid_at
```
- 관계: user 1 : N project (창작자), user 1 : N funding (후원자), project 1 : N funding

## 결정 사항
- **모금 상태 계산**: 순수 함수 `getProjectStatus(목표, 모인 금액, 마감일, 지금)` 하나로 정의한다.
  - 화면은 항상 이 함수의 결과를 쓴다 (언제 봐도 정확)
  - Vercel Cron이 하루 1번 마감된 프로젝트의 `status`를 DB에 확정 저장한다 (목록 필터·기록용)
  - 이 함수가 단위 테스트의 첫 대상 (마감 당일 23:59, 목표 딱 도달 등 경계값)
- **마감 시각**: 마감일의 23:59:59 한국 시간
- **결제**: 2단계 흐름(서버가 금액 기록 → 서버 승인) 재사용 + 서버 검사 추가:
  마감 지난 프로젝트·숨김 프로젝트·내 프로젝트에는 후원 불가, 금액 범위
- **사진**: 3단계 Vercel Blob 흐름 재사용
- **디자인**: Figma(무료)에서 디자인 시스템(색·글꼴·간격 토큰 + 버튼·카드·입력칸 컴포넌트)을 만들고,
  같은 이름의 CSS 변수·React 컴포넌트로 옮긴다. 모바일 우선
- **공학 도구 (모두 필수)**: zod(입력 검사), Vitest(단위 테스트), Playwright(흐름 테스트),
  GitHub Actions(CI: 코드 검사·타입 검사·테스트·빌드), Sentry(에러 모니터링)
- **개발 방식**: 기능마다 브랜치 → PR(셀프 리뷰 체크리스트) → CI 통과 → 병합 → 자동 배포
- **결제는 테스트 모드 유지** (라이브 결제에는 사업자등록 등이 필요 — 2단계 부록 참고)
- **커스텀 도메인**: 선택 (도메인 구매 비용 발생)

## 성공 지표
- **핵심 지표**: 프로젝트 상세를 본 방문자 중 후원을 완료한 비율
- **퍼널**: 목록 방문 → 상세 → 후원 시작 → 결제 완료 (어디서 가장 많이 빠지는지)
- **보조**: 프로젝트 성공률, 결제 실패 이유 분포

## 주차별 체크리스트

### 기획 (1~2주)
- [ ] 1주차: 경쟁 서비스 분석(텀블벅·와디즈·킥스타터) / 창작자·후원자 인터뷰 3~5명 / 인사이트 정리
- [ ] 2주차: PRD(문제·사용자·범위·지표·위험) / 결정 기록(ADR) 시작 / 데이터 모델·상태 설계

### UX/UI (3~4주)
- [ ] 3주차: 사용자 흐름도(창작자·후원자·관리자) / Figma 와이어프레임
- [ ] 4주차: 디자인 시스템(토큰·컴포넌트) / 모바일 우선 시안 / 클릭 가능한 시안으로 사용성 테스트 3명 → 수정

### 구현 (5~9주)
- [ ] 5주차: 프로젝트 준비 — TypeScript, zod, Vitest, Playwright, GitHub Actions CI, PR 흐름, Sentry / 디자인 시스템을 코드로
- [ ] 6주차: 인증·역할 / 프로젝트 등록·수정 (사진, zod 검사)
- [ ] 7주차: 목록·상세·진행률 / 모금 상태 함수 + 단위 테스트
- [ ] 8주차: 후원 결제 (서버 검사 추가) / 내 후원 내역 / 결제 흐름 테스트(Playwright)
- [ ] 9주차: 창작자 대시보드 / 관리자 화면 / 상태 확정 예약 작업 / 로딩·빈 화면·에러 상태

### 배포·운영 준비 (10주)
- [ ] 10주차: 운영 배포 / 미리보기 배포 + DB 브랜치 / Sentry 알림 / 퍼널 지표 SQL / 백업·복구 연습 / (선택) 커스텀 도메인

### 운영·개선 (11~14주)
- [ ] 11주차: 실제 창작자 1명의 프로젝트 운영 시작, 지인 후원(테스트 결제) 요청
- [ ] 12주차: 지표·Sentry 에러·피드백 수집 → 개선 우선순위
- [ ] 13주차: 개선 사이클 1~2회 (PR → CI → 배포 → 재측정)
- [ ] 14주차: 케이스 스터디 (README, 구조도, 결정 기록, 개선 전후 지표, 데모 영상) / 전체 회고

## 운영 루프
- Sentry로 에러가 나면 알림 → 원인 확인 → 수정 PR
- 퍼널 지표로 가장 많이 빠지는 단계 찾기 → 사용성 관찰 → 가설 → 개선 → 재측정
- 예약 작업(상태 확정)이 매일 돌았는지 로그 확인
- 백업·복구 연습: Neon의 특정 시점 복구로 "실수로 지운 데이터 되살리기"

## 완료 기준 (Definition of Done)
- [ ] 프로젝트 등록 → 목록 노출 → 후원(결제) → 진행률 반영까지 끊김 없이 동작
- [ ] 마감일이 지나면 목표 달성 여부에 따라 성공/실패로 바뀌고, 예약 작업이 DB에 확정한다
- [ ] 창작자·후원자·관리자 권한이 분리되어 있다 (남의 프로젝트 수정 불가, 내 프로젝트 후원 불가, 관리자만 숨김)
- [ ] 모든 PR에서 CI(코드 검사·타입 검사·단위 테스트·흐름 테스트·빌드)가 통과한다
- [ ] 운영 중 발생한 에러가 Sentry에 기록되고 알림이 온다
- [ ] Figma 디자인 시스템과 코드의 토큰·컴포넌트 이름이 일치한다
- [ ] 실제 창작자 1명의 프로젝트를 운영하고, 개선 1회 이상의 전후 지표가 있다
- [ ] 케이스 스터디가 완성되어 포트폴리오로 제시할 수 있다
- [ ] 키보드 조작 가능, Lighthouse 접근성 90점 이상
