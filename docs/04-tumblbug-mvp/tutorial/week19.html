개선 한 바퀴: 테스트 먼저, 증거로 남기기

18주차에 고른 두 가지를 실제 코드로 고칩니다. 이번 주의 전후 측정은 모두 [실제]입니다 — 가상 사례로 문제를 찾았지만, 화면 문제는 실제 코드에 있었어요.

🗺️ 이번 주 그림 — 개선 한 바퀴
① 테스트 먼저고친 뒤 이래야 한다
② 지금 코드에서 실패= 개선 전 기록
③ 고치기
④ 통과= 개선 후 기록
⑤ PR → CI → CD커밋은 개선마다 따로
⑥ 운영에서 재측정강의 뒤 여러분이

고치기 전에 실패하지 않는 테스트는 아무것도 증명하지 못한다.

1개선 ①: 테스트 먼저 쓰기

고치기 전 코드에서 돌리면:

✅ 개선 전 기록 [실제]
  • 새 테스트 6개(휴대폰·데스크톱 × 3) 모두 실패 — 틀린 칸 표시 없음, 가짜 주소 안내 없음
  • 보이는 문장: "받는 분·연락처·주소를 모두 입력해 주세요" (연락처가 틀렸는데 그 말은 없음)
  • 데스크톱(1280×720)에서 그 문장이 하단 고정 바에 완전히 가려짐 — 가상 설문 1번 "다음을 눌러도 아무 일도 안 일어나는 줄"이 실제로 재현
  • 커서는 "다음" 버튼에 그대로
🔁 방금 무슨 일이 일어났나"고친 뒤에는 이래야 한다"를 테스트로 먼저 쓰고, 고치기 전 코드에서 실패하는 것을 확인했습니다. 이 실패가 개선 전 기록이자, 나중에 "정말 고쳤다"를 증명할 기준입니다.
2개선 ①: 고치기 — 칸마다 이유, 첫 틀린 칸으로
💡 규칙을 한 곳에 두는 이유화면은 칸마다 이유(shippingFieldErrors)를, 서버 검사(quote.ts)와 단계 이동 검사는 첫 번째 이유 하나(shippingStepError)를 씁니다. 같은 파일의 같은 규칙이라, 화면에서는 통과했는데 서버에서 막히는 어긋남이 생기지 않습니다.
✅ 개선 후 기록 [실제]
전후
새 테스트6개 실패6개 통과 (+ 기존 후원 흐름 테스트 통과)
틀림 표시된 칸02 (빨간 테두리 + aria-invalid + 설명 연결 → 화면 낭독기도 읽음)
커서버튼연락처 칸
데스크톱에서 이유가려짐보임 (scroll-margin-bottom)
🔁 방금 무슨 일이 일어났나"어디가 틀렸는지 모르겠다"는 말을, 틀린 칸에서 바로 이유를 보여 주고 그 칸으로 데려가는 화면으로 바꿨습니다. 그리고 그것을 테스트로 증명했습니다.
3개선 ②: 운영 점검에 배송지 통과율

DB 테스트를 먼저 썼습니다: 배송지에 온 4명 중 2명 통과 + 배송 없이 결제 요청 2명 → 단계 개수로는 100% (틀림), 사람을 따라가면 50%.

✅ 전후 [실제] — npm run ops:check -- --project=번호 (가상 사례 데이터)

전: "결제 요청 (앞 단계의 70%)" 만 → 배송지 문제가 가려짐
후: ↳ 배송지 통과율 50% (배송지에 온 20명 중 10명이 결제 요청까지) + "결제 요청의 앞 단계 % 에는 배송지를 건너뛴 사람도 섞여 있어요" 주의 문장

🔁 방금 무슨 일이 일어났나측정 도구(운영 점검)가 틀린 비율(70%) 대신 맞는 비율(배송지 통과율 50%)을 보여 주게 고쳤습니다. 측정이 맞아야 개선 뒤에 다시 잴 수 있습니다.
4PR → CI → CD, 그리고 재측정
  1. 브랜치 → 커밋을 개선마다 따로 (문제가 생기면 하나만 되돌릴 수 있게) → PR 본문에 18주차 근거와 위 전후 표
  2. CI(lint·타입·단위·흐름 테스트·빌드) 통과 → 합치기 → 운영 배포 → 연기 테스트
  3. (강의 뒤) 운영에서 2주 재측정 — 18주차에 적은 기준: 배송지 통과율 50% → 70% 이상

🆘 기준에 못 미치면

실패가 아니라 다음 가설입니다. 무엇이 여전히 막는지 다시 관찰합니다 (18주차로). 사람이 적으면(10명 미만) 숫자가 크게 흔들리니, 설문에서 배송지 이야기가 줄었는지도 함께 봅니다.

🔁 방금 무슨 일이 일어났나관찰 → 가설 → 테스트 → 고치기 → 배포 → 재측정의 한 바퀴를 돌았습니다. 가짜 "후" 숫자를 지어내지 않고, 실제 사용자로 잴 칸을 비워 둔 것도 중요합니다.
🤔 스스로 확인
개선 전 코드에서 새 테스트가 실패하는 것을 먼저 확인한 이유는?

처음부터 통과하는 테스트는 "고쳐서 좋아졌다"를 증명하지 못합니다. 실패 → 통과가 개선의 증거입니다.

서버의 배송지 검사는 왜 따로 규칙을 만들지 않나?

규칙이 두 곳에 있으면 한쪽만 고쳐져 어긋납니다. rules.ts 하나를 화면과 서버가 같이 씁니다.
