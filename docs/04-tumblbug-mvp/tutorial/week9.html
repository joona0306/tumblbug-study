API 설계와 무한 스크롤

이번 주에는 화면이 아니라 데이터를 주는 주소(API)를 설계합니다. 누가 어떻게 불러도 같은 모양으로 답하고, 너무 많이 부르면 막고, 끝없는 목록을 빠짐없이 나눠 줍니다.

🗺️ 이번 주 그림 — 화면 말고 "데이터 주소"를 만든다
GET /api/projectsJSON · 커서 · 응답 규칙
요청 수 제한1분 60번 · 429
CDN 캐시30초
무한 스크롤TanStack Query
용어한 줄 뜻
API프로그램끼리 데이터를 주고받는 약속된 주소 (여기서는 JSON 을 돌려주는 Route Handler)
응답 코드200 성공 · 400 잘못된 입력 · 401 로그인 필요 · 403 권한 없음 · 404 없음 · 429 너무 많음
커서 페이지네이션"마지막으로 본 항목 다음부터" 가져오는 방식
TanStack Query브라우저에서 서버 데이터를 가져오고 기억(캐시)하는 도구
1GET /api/projects — 응답 규칙 · 커서 페이지네이션 · 캐시
🗺️ 그림 먼저 — offset 과 cursor
offset (몇 번째부터)중간에 새 프로젝트가 생기면 같은 항목이 두 번 나오거나 빠짐 · 뒤로 갈수록 느림
cursor (이 항목 다음부터)정렬 기준값 + id 로 "다음"을 정확히 · 인덱스를 타서 늘 빠름

Route Handler = 화면이 아니라 데이터(JSON)를 돌려주는 주소 (app/api/…/route.ts). 먼저 모든 API 가 같은 모양으로 답하게 규칙을 정합니다:

💡 화면 주소는 이상한 값을 기본값으로 바꾸는데, API 는 왜 400 으로 거절하나요?화면은 사람이 보니 친절하게, API 는 프로그램(우리 무한 스크롤 등)이 쓰니 실수를 바로 알 수 있게 거절합니다. 응답 코드는 약속입니다: 400 입력이 잘못됨 · 401 로그인 필요 · 403 권한 없음 · 404 없음 · 409 충돌 · 429 요청이 너무 많음.
💡 Cache-Control 은 무엇을 하나요?누구에게나 같은 공개 데이터라서 Vercel(CDN)이 30초 동안 저장해 두고 대신 답합니다. 그 뒤 60초는 저장본을 먼저 주고 뒤에서 새로 받아옵니다(stale-while-revalidate). DB 에 가는 요청이 크게 줄어요.
✅ 확인하는 법
  • http://localhost:3000/api/projects?limit=2 → {"items":[…2개],"nextCursor":"…"}
  • 그 nextCursor 를 &cursor= 로 붙이면 다음 2개
  • ?limit=abc → 400 과 칸마다 이유
🔁 방금 무슨 일이 일어났나목록을 "조각조각" 가져갈 수 있는 공개 API 를 만들었습니다. 커서가 "마지막으로 본 항목"을 가리켜서, 중간에 새 프로젝트가 생겨도 빠짐·중복이 없습니다.
🤔 스스로 확인
limit+1 개를 가져오는 이유는?

하나를 더 가져와 보면 "다음 페이지가 있는지"를 쿼리 한 번으로 알 수 있습니다. 있으면 마지막 항목으로 커서를 만들고, 더 가져온 하나는 버립니다.

2요청 수 제한 (429 Too Many Requests)
🗺️ 그림 먼저 — 1분짜리 칸에 요청 수를 센다
요청IP + API 이름
rate_limit 표(키, 1분 칸) → 횟수 +1
429Retry-After: 몇 초 뒤 다시

서버리스는 서버가 여러 대로 나뉘어 돌아서 메모리로는 셀 수 없다 → 모두가 보는 DB 에 센다.

💡 "없으면 1, 있으면 +1"을 한 문장(upsert)으로 하는 이유는?먼저 읽고 나중에 쓰면, 동시에 온 요청 둘이 같은 숫자를 읽고 둘 다 +1 해서 하나를 놓칩니다 (6주차 조건부 차감과 같은 문제). INSERT … ON CONFLICT DO UPDATE 한 문장이면 DB 가 정확히 셉니다.
✅ 확인하는 법응답 헤더에 X-RateLimit-Limit: 60, X-RateLimit-Remaining. 같은 IP 로 1분에 61번째 요청부터는 429 (흐름 테스트는 헤더의 60 을 확인)
🔁 방금 무슨 일이 일어났나공개 API 를 누군가 자동으로 긁어 가거나 실수로 무한 반복해도 DB 가 버티게 했습니다. 지난 칸 기록은 13주차 예약 작업이 하루 한 번 지웁니다.
3TanStack Query 로 무한 스크롤
🗺️ 그림 먼저 — 첫 페이지는 서버가, 나머지는 브라우저가
서버 컴포넌트첫 12개를 그려서 보냄 (initialPage)
useInfiniteQuery/api/projects?cursor= 로 다음 12개
캐시(기억)조건별로 따로 · 30초 신선

상태 관리 지도: "서버 데이터를 브라우저에서 이어서 가져온다" → TanStack Query. 서버 데이터를 useState 에 복사해 두지 않는다.

💡 스크롤로 자동으로 불러오는데 "더 보기" 버튼은 왜 두나요?키보드나 화면 낭독기로는 "스크롤해서 끝에 닿기"가 어렵습니다. 같은 동작을 버튼으로도 할 수 있게 둡니다. 실패하면 이유와 "다시 시도" 버튼을 보여 주고요.
✅ 확인하는 법목록을 끝까지 내리면 다음 12개가 이어서 나온다 · 칩을 바꾸면 처음부터 · 다 보면 "모든 프로젝트를 봤어요"
🆘 막혔을 때
서버와 브라우저 결과가 다르다는 hydration 경고

"지금 시각"을 브라우저에서 새로 만들면 서버가 그린 "N일 남음"과 어긋날 수 있습니다. 서버가 쓴 시각(nowIso)을 넘겨받아 같은 시각으로 그립니다.

🔁 방금 무슨 일이 일어났나목록이 끝없이 이어집니다. 첫 화면은 서버가 바로 그려서 빠르고, 이어지는 부분만 API 로 가져오며, 이미 받은 것은 기억해 둡니다.
🤔 스스로 확인
queryKey 에 필터 조건(params)을 넣는 이유는?

조건이 다르면 다른 목록이므로 다른 "기억 칸"을 써야 합니다. 안 넣으면 리빙 목록 뒤에 공예 목록이 섞여 이어 붙습니다.

4API·무한 스크롤 흐름 테스트 + 테스트 간섭 없애기
🆘 같은 DB 를 쓰는 테스트끼리 서로 흔든다흐름 테스트는 여러 파일이 동시에 같은 DB 를 씁니다. 다른 테스트가 프로젝트를 만들고 지우는 사이에 "전체 개수가 N개"를 확인하면 가끔 틀려요. 그래서 ① 내 테스트만의 표식(TAG)을 붙인 데이터만 세고 ② 기기와 무관한 테스트는 desktop 에서만 ③ 전체 개수 대신 "성공·실패 배지 0개"처럼 흔들리지 않는 것을 확인합니다.
✅ 확인하는 법npm run test:e2e → 커서로 끝까지: 빠짐·중복 없이 30개, 5페이지 · 잘못된 값 400 · 무한 스크롤 30개 + 끝 안내
🔁 방금 무슨 일이 일어났나API 의 약속(빠짐·중복 없음, 400, 요청 제한 헤더)과 무한 스크롤을 테스트로 고정하고, 테스트끼리 서로 흔들지 않게 했습니다.
