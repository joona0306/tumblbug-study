리워드와 모금 상태, 그리고 첫 화면들

창작자는 리워드를 붙이고, 후원자는 홈·목록·상세에서 프로젝트를 둘러봅니다. 이번 주의 중심은 "언제 끝나고, 성공인가"를 정하는 함수 하나입니다.

상태를 DB 에 저장만 해 두면, 마감 시각이 지나도 누가 바꿔 주기 전까지 "모금중"으로 남는다 → 볼 때마다 계산한다.

💡 "지금 시각"까지 인자로 받는 이유는?함수 안에서 new Date() 를 부르면 테스트할 때마다 결과가 달라집니다. 시각을 인자로 받으면 "마감일 23:59:59", "다음 날 00:00:00" 같은 경계값을 정확히 넣어 볼 수 있어요. 이런 함수를 순수 함수(같은 입력 → 늘 같은 결과)라고 합니다.
⚠️ 시간대 함정마감은 "마감일 23:59:59 한국 시간"까지. UTC 로는 그날 15:00 에 끝납니다. 테스트의 마지막 경우(UTC 로는 아직 8일인데 한국은 9일 새벽)가 바로 이 함정을 지킵니다.
✅ 확인하는 법npm test → 경계값 테스트 통과 (23:59:59 모금중 · 00:00:00 끝 · 목표 딱 도달 성공 · 1원 모자라면 실패)
🔁 방금 무슨 일이 일어났나앱에서 가장 중요한 규칙(언제 끝나고, 성공인지 실패인지)을 함수 하나로 정하고, 헷갈리기 쉬운 경계를 테스트로 못 박았습니다.

2리워드 추가·수정·삭제
💡 왜 서버 액션마다 "내 프로젝트인지"를 먼저 확인하나요?폼의 projectId 는 브라우저가 보내는 값이라 누구나 고칠 수 있습니다. 남의 프로젝트 번호로 바꿔 보내도 리워드가 붙지 않도록, 서버에서 소유자를 확인합니다 (requireMyProject).

후원이 들어온 리워드는 가격 변경·삭제를 막습니다 — 이미 산 사람이 있는 물건의 가격을 바꾸면 안 되니까요.

✅ 확인하는 법수정 화면 아래에서 리워드 추가 → 목록에 나타남, 수정·삭제 가능 · 11개째는 "10개까지" 안내

목록에서 "모금중인 것만 12개"를 가져오려면 DB 안에서 상태를 알아야 한다. 그래서 같은 규칙을 SQL 로도 쓰고, 테스트가 둘을 비교한다.

💡 왜 규칙을 한 곳에 두지 못하나요?가능하면 한 곳이 좋지만, 목록은 DB 에서 걸러야 빠릅니다(모든 프로젝트를 가져와 코드로 거르면 느려짐). 대신 "두 곳이 같다"를 테스트로 계속 감시합니다.
✅ 확인하는 법npm test → listing 테스트 (어제·오늘·내일 마감 × 달성·미달·딱 도달)
🔁 방금 무슨 일이 일어났나목록은 SQL 로 빠르게, 규칙은 함수와 똑같이. 둘이 어긋나는 순간 테스트가 알려 줍니다.

💡 주소의 이상한 값(?category=food)을 에러로 보여 주지 않는 이유는?주소는 사람이 손으로 고치기도 하고, 옛 링크일 수도 있습니다. 화면에서는 친절하게 "기본값으로" 보여 줍니다. (9주차 API 는 반대로 400 으로 알려요 — 프로그램이 실수를 바로 알아야 하니까)
✅ 확인하는 법
  • 홈: 마감 임박·인기 프로젝트, 3일 이내면 D-3 배지
  • 목록: 칩을 누르면 주소가 바뀌고, 새로고침해도 유지
  • 상세: 모인 금액·후원자 수·남은 기간·리워드(남은 수량)
