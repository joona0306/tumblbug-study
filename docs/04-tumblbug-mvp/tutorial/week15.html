2운영 점검 — 데이터가 조용히 어긋나지 않았나
💡 가장 찾기 어려운 문제에러도 없고 사이트도 열리는데 데이터만 틀어진 경우입니다. 예: 결제는 실패했는데 재고를 안 되돌려서 "품절이 아닌데 품절"로 보임. 아무도 알려 주지 않으니 매일 스스로 확인합니다.
점검무엇이 잘못됐다는 뜻
① 재고 어긋남판매 수 ≠ 결제 완료·승인 중 수량 → 품절 오표시 또는 초과 판매 위험
② 결제 상태 어긋남토스는 결제 완료인데 우리 DB 는 아님 → 돈은 나갔는데 후원 내역에 없는 사람 (가장 급함)
③ 예약 작업 미실행마감 하루가 지났는데 모금중 → 매일 자정 예약 작업이 안 돌았다
④ 오래된 결제 대기하루 넘게 결제 대기 → 정리 작업이 안 돌았다

Neon SQL Editor 에서 직접 보고 싶으면 같은 점검을 적어 둔 sql/week15-ops.sql 을 붙여 넣어 하나씩 실행합니다.

🔁 방금 무슨 일이 일어났나에러도 없고 사이트도 열리는데 데이터가 조용히 틀어지는 경우(재고·결제 상태·예약 작업·오래된 결제 대기)를 SQL 로 찾는 점검을 만들었습니다. 읽기만 하고, 문제가 있으면 종료 코드 1 로 알려 줍니다.
3매일 아침 자동 점검 (운영 DB)

매일 한국 시간 아침 7시에 운영 DB 로 점검을 돌리고, 문제가 있으면 작업이 실패 → GitHub 가 저장소 주인에게 실패 메일을 보냅니다. 설정할 것 없음 — 운영 DB 주소는 14주차에 만든 production 환경에 이미 있습니다.

🆘 "내 터미널에서 npm run ops:check 를 하라는 건가요?"

아닙니다 (작성자가 실제로 헷갈린 부분). 내 터미널에서 하면 .env.local 의 개발 DB를 봅니다. 운영 DB 점검은 운영 DB 주소를 가진 GitHub Actions 가 합니다. 바로 돌려 보려면 Actions → Ops check → Run workflow. 운영 DB 주소는 내 컴퓨터에 두지 않습니다.

✅ 확인하는 법Run workflow → 초록불, 로그에 "점검 ✅ 4개"와 운영 퍼널 (작성자 기록: 운영 테스트 후원 1건이 퍼널에 1·1·0·1·1 로 잡힘 — 배송이 없는 리워드라 배송지 0 은 정상)
🔁 방금 무슨 일이 일어났나그 점검을 사람 대신 GitHub 이 매일 아침 운영 DB 에 돌리게 했습니다. 문제가 있으면 작업이 실패하고 실패 메일이 옵니다 — 내 컴퓨터에 운영 DB 주소를 둘 필요가 없습니다.
4Sentry 알림 — 새 에러가 생기면 메일

5주차에 연결한 Sentry 는 에러를 모아 두기만 합니다. 프로젝트를 만들 때 "Send a notification for high priority issues" 알림이 하나 있지만(중요해 보이는 것만), 처음 보는 에러는 전부 받는 알림을 하나 더 만듭니다.

  1. 왼쪽 Monitors → Alerts → 오른쪽 위 + Create Alert (예전 화면의 "Issues 고르기" 단계는 없어졌습니다)
  2. Source: Alert on all issues in selected projects → 내 프로젝트 · Filter Issues: Environment = production
  3. WHEN: A new issue is created + A resolved issue regresses (고친 에러가 다시 생김)
  4. IF: Any event 그대로 · Throttling: 기본 "Notify on every trigger" 그대로 (두 조건 모두 에러 하나당 한 번이라 메일이 쏟아지지 않는다)
  5. THEN: Notify → 이메일 → 나 · Send Test Notification → 이름 모아 운영 — 새 에러 → Create Alert

진짜로 울리는지 확인

  1. Issues 에서 Sentry 로 검색 → 5·13주차 확인 때 생긴 테스트 이슈를 모두 Resolve
  2. 운영 주소 /debug/sentry?throw=render
  3. 이슈가 Regressed(처음이면 New) → 알림의 History 에 1줄 → 메일 → 확인 뒤 다시 Resolve
🆘 작성자가 실제로 막힌 곳
테스트 에러를 냈는데 알림이 안 와요

테스트 이슈가 이미 있고 Resolve 되지 않은 상태라, 새 에러가 "이미 있는 이슈에 1건 더"로 붙기만 했습니다. 새 이슈도 재발도 아니라서 알림이 울리지 않아요 → 먼저 Resolve.

알림 메일의 시간이 한국 시간이 아니에요

Sentry 는 기본이 UTC(한국 −9시간)입니다. 내 프로필 → User Settings → Preferences → Timezone → (UTC+09:00) Asia/Seoul.

✅ 실제 사례 [실제] — 알림을 켜자마자 온 Fatal

Error: Connection terminated unexpectedly — Neon 이 한동안 쉬던 DB 연결을 끊었는데, 앱에 "연결이 끊겼을 때"를 받는 코드가 없어서 서버 프로세스가 통째로 멈췄습니다. 고친 코드:

테스트가 DB 에 직접 연결(-pooler 를 뺀 주소)하는 이유: pooling 주소는 중간 관리자(PgBouncer)가 실제 연결을 돌려 써서, "그 연결을 끊어"가 엉뚱하게 명령한 쪽 연결을 끊었습니다. 처리 코드를 빼면 테스트가 "처리되지 않은 에러"로 실패하는 것까지 확인 → 재발 방지 장치.

🔁 방금 무슨 일이 일어났나처음 보는 에러와 고친 에러의 재발이 생기면 메일이 오게 했습니다. 그리고 알림이 실제로 진짜 장애를 잡아냈고, 재현 테스트와 함께 고쳤습니다.
🤔 스스로 확인
"A resolved issue regresses" 를 추가하는 이유는?

고쳤다고 Resolve 한 에러가 다시 생기면 알려 줍니다. 고친 게 제대로 안 됐거나, 다른 변경이 다시 망가뜨렸다는 신호예요.

5가동 감시 — 사이트가 안 열리면 메일
💡 Sentry 로는 부족한 이유Sentry 는 "앱이 돌면서 낸 에러"만 압니다. 서버가 아예 멈추거나 DB 가 끊기면 에러를 보낼 수조차 없어요. 그래서 바깥에서 몇 분마다 두드려 보는 서비스가 필요합니다.
  1. UptimeRobot 가입 (화면이 단순함. Better Stack 도 되지만 팀용 기능이 많아 처음엔 복잡) — 가입 화면 Website to monitor 에 https://운영주소/api/health
  2. 가입 뒤: 설문은 아무거나, 소식 메일 스위치는 꺼도 됨(장애 알림은 따로 온다), "Upgrade by …" 유료 홍보 알림은 닫기
  3. 감시 설정: HTTP(s) · 5분 · Alert contacts = 내 이메일 (가입 확인 메일의 인증 링크를 눌러야 알림이 온다). 무료로 되면 Keyword "ok":true 가 없으면 실패로

첫 화면이 아니라 /api/health 를 감시하는 이유: DB 까지 확인하고, 끊기면 503 을 줍니다 (14주차).

📌 알림이 오면사이트를 직접 열어 본다 → 업체 쪽 장애인지 먼저: Vercel 상태 https://www.vercel-status.com · Neon 상태 https://neonstatus.com → Vercel Deployments·Logs, Neon Monitoring, Sentry 순서로 → 끝나면 장애 회고(templates/08-incident-review.md)
✅ 확인하는 법감시 화면 Up(초록), 5분 간격
🔁 방금 무슨 일이 일어났나Sentry 는 "앱이 돌면서 낸 에러"만 압니다. 그래서 바깥에서 5분마다 /api/health 를 두드리는 감시를 달았습니다. 서버가 멈추거나 DB 가 끊기면(503) 메일이 옵니다.
6백업·복구 연습 — "지웠다"를 되돌릴 수 있나
🗺️ 그림 먼저 — 운영 DB 는 건드리지 않고 과거를 꺼내 본다
① 지금 개수 세기시각은 SQL Editor History 에
② 테스트 프로젝트 만들기"사라지게" 할 대상
③ 과거 시점 브랜치①의 시각으로
④ 개수 비교①과 같으면 복구 성공
💡 복구해 본 적 없는 백업은 백업이 아니다사고는 대부분 사람이 냅니다 (잘못된 SQL, 잘못된 마이그레이션). 사고 난 날 처음 해 보면 당황해서 더 큰 사고가 납니다.
  1. Neon 운영 프로젝트 → SQL Editor → select count(*) from project; → 결과와 왼쪽 History 의 실행 시각을 적는다
  2. 운영 사이트에서 테스트 프로젝트를 하나 만든다
  3. Branches → New Branch → 이름 restore-drill · 부모 = 기본 브랜치 · 데이터 범위 Branch data and schema from a past point in time → ①의 시각 (Beta 선택지는 고르지 않는다)
  4. restore-drill 의 SQL Editor 에서 같은 쿼리 → ①의 숫자와 같으면 성공
  5. restore-drill 브랜치 삭제 (이름을 꼭 확인 — 기본 브랜치는 지우지 않는다)
🆘 막혔을 때
숫자가 다르게 나와요

시각 입력칸의 시간대(한국 시간 / UTC)를 확인하세요. History 가 한국 시간인데 입력칸이 UTC 면 9시간을 빼야 합니다.

"Branch data and schema" 를 골랐어요

그건 "지금" 복사라 ②의 프로젝트까지 들어가서 연습이 안 됩니다. 과거 시점(past point in time)을 골라야 해요.

✅ 작성자 기록 [실제]15:03 시점 복사본 1개 · 운영 2개(= 원래 1 + 테스트 1) → 복구 성공
🔁 방금 무슨 일이 일어났나운영 DB 를 전혀 바꾸지 않고, 과거 모습을 따로 꺼내 봤습니다. 실제 사고 때는 사고 직전 시점 브랜치에서 필요한 줄만 꺼내 운영에 되살립니다 (전체를 과거로 되돌리면 그 뒤의 정상 후원까지 사라지므로 마지막 수단).
7토스 웹훅 등록 (알려진 한계 포함)

결제창에서 돌아오지 못한 결제(브라우저를 닫음 등)는 웹훅이 마무리합니다 (11주차). 운영 주소가 생겼으니 등록합니다: 토스 개발자센터 → 웹훅 → 등록 → URL https://운영주소/api/webhooks/toss · 이벤트 PAYMENT_STATUS_CHANGED.

🆘 테스트 결제를 했는데 전송 기록이 비어 있어요 (작성자 실제 경험 — 알려진 한계)

전자결제 신청 전에 쓰는 문서 예제용 공용 테스트 키(test_gck_docs_…)는 내 상점과 연결돼 있지 않아서, 결제는 되지만 내 상점에 등록한 웹훅은 불리지 않습니다. 주소가 살아 있는지는 가짜 알림으로 확인할 수 있어요 — 우리 웹훅은 토스에 결제를 다시 조회하므로, 없는 결제면 {"result":"ignored"} 로 200 을 줍니다 (정상). 내 상점 키를 받으면 전송 기록이 생깁니다.

🔁 방금 무슨 일이 일어났나결제창에서 돌아오지 못한 결제를 마무리할 웹훅 주소를 토스에 등록했습니다. 다만 문서 예제용 공용 테스트 키로는 내 상점 웹훅이 불리지 않는다는 한계를 확인하고 기록했습니다 — 코드는 테스트로 검증되어 있습니다.
