PRD, 결정 기록, 개념 ERD

1주차 인사이트를 근거로 무엇을, 누구를 위해, 어디까지 만들지 한 문서(PRD)에 적습니다. 중요한 결정은 왜 그렇게 정했는지까지 남기고(ADR), 저장할 데이터의 큰 그림(개념 ERD)과 상태가 바뀌는 규칙(상태 전이도)을 그립니다.

PRD제품 요구사항 문서. 개발 중 "이거 해야 해?"라는 질문에 답하는 기준

ADR결정 기록. 결정 1개 = 파일 1개, 번호는 바꾸지 않는다

1PRD 쓰기
💡 왜 문서부터?혼자 만들어도 20주는 깁니다. 중간에 "검색도 넣을까? 댓글도?" 하는 순간이 반드시 옵니다. PRD 의 비목표(이번에는 안 한다) 칸이 그때 나를 지켜 줍니다 — 스코프 크립(범위가 슬금슬금 커지는 것) 방지.

예시 답안: templates/03-prd.md. 여러분은 근거 칸을 내 인터뷰 인용으로 바꿔 씁니다.

PRD 칸예시 답안의 요점
1. 문제창작자는 제작비를 미리 모으기 어렵고, 후원자는 믿을 만한 프로젝트인지 판단할 정보가 부족하다
2. 대상 사용자창작자 · 후원자 · 관리자(나)
3. 목표10분 안에 프로젝트 등록 / 리워드 → 배송지 → 결제 3단계 후원 / 초과 판매 없음 / 마감일에 성공·실패 자동 결정
3. 비목표리워드 옵션, 정산, 환불, 알림, 댓글, 검색·추천, 실제 결제 — 20주 안에 핵심 흐름을 운영 수준으로 완성하는 게 우선
4. 사용자 스토리후원자 B-1~B-5, 창작자 C-1~C-5, 관리자 A-1~A-2 + 인수 조건
5. 성공 지표핵심: 상세를 본 방문자 중 후원 완료 비율 / 퍼널: 상세 → 리워드 → 배송지 → 결제 요청 → 결제 완료
6. 위험과 대응마감 시각 버그, 금액 위조, 동시 결제 초과 판매, 결제창 이탈, 배송지 노출 …
✅ 확인하는 법목표마다 근거(인터뷰 인용)가 있고, 비목표가 3개 이상이며, 사용자 스토리마다 인수 조건이 있다.
🆘 막혔을 때
하고 싶은 기능이 너무 많아요

"핵심 흐름(등록 → 후원 → 결과)에 꼭 필요한가?"로 걸러 보세요. 아니면 비목표에 적고 "다음에 할 것"으로 남깁니다. 버린 흔적이 판단력을 보여 줍니다.

🔁 방금 무슨 일이 일어났나"무엇을 만들고 무엇을 안 만들지"를 근거와 함께 정했습니다. 앞으로 16주 동안 범위를 판단할 기준이 생겼어요.
2결정 기록(ADR) 시작하기
💡 왜 남기나?석 달 뒤의 나는 "왜 이렇게 만들었지?"를 기억하지 못합니다. ADR 은 그 질문에 답하고, 포트폴리오에서 내 판단력을 보여 주는 가장 좋은 자료예요.

예시 네 개: templates/04-adr.md

ADR고른 것포기한 것
001 모금 상태순수 함수로 계산 + 하루 1번 예약 작업이 확정한쪽만 쓰기 (화면이 틀리거나 필터가 어려움)
002 결제 시점후원 즉시 (테스트) 결제마감 뒤 결제 (범위가 크게 늘어남) → 알려진 한계로
003 초과 판매결제 승인 직전 조건부 차감수량 예약(만료 처리 필요)
004 브라우저 상태 (5주차)Zustand · TanStack Query · Context 를 종류별로한 도구로 통일
✅ 확인하는 법ADR 을 최소 1개(모금 상태 또는 결제 시점) 내 말로 썼다. 선택지가 2개 이상이고 "결과(포기한 것)"가 비어 있지 않다.
🔁 방금 무슨 일이 일어났나"정답"이 아니라 "이 상황에서의 선택과 그 대가"를 기록했습니다. 결정을 뒤집을 땐 옛 ADR 을 고치지 않고 새 ADR 을 씁니다.
🤔 스스로 확인
ADR-003 에서 "결제 승인 직전"에 차감해도 돈이 잘못 나가지 않는 이유는?

토스페이먼츠는 서버가 승인 API 를 부르기 전까지 돈을 가져가지 않습니다. 차감에 실패하면 승인하지 않고 "품절"만 알리면 됩니다.

3개념 ERD: 명사에서 개체 찾기
🗺️ 그림 먼저 — 모아의 개념 ERD (예시 답안)
사용자이메일, 이름, 역할
프로젝트제목, 목표 금액, 마감일, 대표 사진, 상태…

후원수량, 총액, 배송지, 결제 상태…
프로젝트(리워드는 0~1개)
사용자
찜연결 개체 + 찜한 날짜
프로젝트
  1. PRD 사용자 스토리에서 명사를 뽑는다: 사용자, 창작자, 후원자, 프로젝트, 리워드, 후원, 결제, 찜, 배송지, 사진, 카테고리…
  2. 저장해야 하고 여러 개가 생기는 것만 개체로 남긴다
    • 창작자·후원자·관리자 → 모두 "사용자" 하나 (역할만 다름)
    • 배송지 → 후원마다 하나씩 적으니 후원의 속성 · 대표 사진 1장 → 프로젝트의 속성
  3. 개체 둘씩 짝지어 두 방향으로 묻는다: "프로젝트 1개에 리워드는 몇 개? → 여러 개", "리워드 1개는 프로젝트 몇 개에? → 1개" ⇒ 1 : N
  4. 양쪽 다 "여러 개"면 N : M → 사이에 연결 개체 (찜)

자세한 예시와 범위 판단: templates/07-data-model.md ① · Figma 예시 파일의 Flow 페이지

💡 왜 기획 단계에 ERD 를?ERD 는 범위 판단 도구이기도 합니다. "리워드에 색상·사이즈 옵션" 을 넣으면 옵션 개체와 연결이 생기고 수량 계산이 옵션별로 바뀝니다 → 그림을 그려 보면 "이번 범위 제외"의 근거가 눈에 보여요.
✅ 확인하는 법개체 5개 안팎, 모든 선에 1 : N / N : M 표시, 개체마다 핵심 속성 이름(타입 없이)이 있다.
🆘 막혔을 때
"카테고리"는 개체인가요, 속성인가요?

고정된 몇 개 중 하나라면 프로젝트의 속성, 관리자가 늘리고 줄이는 목록이라면 개체입니다. 모아는 고정 6개라 속성으로 둡니다.

🔁 방금 무슨 일이 일어났나"무엇을 저장하고 어떻게 연결되나"를 개발자가 아니어도 읽을 수 있는 그림으로 만들었습니다. 6주차에 이 그림이 실제 표(물리 ERD)가 됩니다.
🤔 스스로 확인
찜을 "사용자" 개체의 속성(찜한 프로젝트 목록)으로 두면 안 되는 이유는?

한 사람이 여러 프로젝트를, 한 프로젝트를 여러 사람이 찜하는 N : M 관계라서 한쪽의 칸 하나로 담을 수 없습니다. 연결 개체가 있어야 "누가 언제 무엇을" 찜했는지 한 줄씩 남아요.
