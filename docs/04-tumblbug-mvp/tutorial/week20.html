🤔 스스로 확인
"세기만"을 기본으로 하고 --confirm 에 DB 이름을 적게 한 이유는?

되돌릴 수 없는 삭제를 실수로 하지 않게. 먼저 무엇이 지워질지 보고, 엉뚱한 DB(예: 개발 DB)를 가리키고 있으면 이름이 달라서 멈춥니다.

한 트랜잭션으로 지우는 이유는?

중간에 실패하면 아무것도 지워지지 않아서, 반쯤 지워진 어중간한 상태가 남지 않습니다.

🔁 방금 무슨 일이 일어났나"스터디가 끝나면 지운다"는 약속을 지킬 도구를 만들었습니다. 기본은 세기만 하고, DB 이름을 한 번 더 적어야만 한 트랜잭션으로 지웁니다 — 되돌릴 수 없는 일일수록 확인 단계를 둡니다.

4케이스 스터디 쓰기

양식: docs/04-tumblbug-mvp/templates/06-case-study.md · 예시 답안: projects/04-tumblbug-mvp/docs/case-study/week20-case-study.md. 포트폴리오를 보는 사람은 "무엇을 만들었나"보다 "어떤 문제를, 어떻게 판단해서, 어떤 결과를 냈나"를 봅니다.

칸예시 답안에서 쓴 것
문제와 사용자한정 수량이 초과 판매되면 신뢰가 무너진다 → 가장 먼저 지킬 것
결정 (고른 것 / 포기한 것)조건부 차감 + CHECK + 트랜잭션, 토스 호출은 트랜잭션 밖 / 락을 오래 잡기
숫자 [실제]인덱스 118배·257배, 초과 판매 0건, 자동 롤백 17초, 접근성 100
운영·개선[가상] 배송지 통과율 50% 발견 → [실제] 데스크톱에서 오류가 가려진 버그 → 테스트 6개 실패→통과 → 재측정은 여러분
한계테스트 결제·즉시 결제, 환불·정산 없음, EC2↔DB 거리
배운 것숫자는 세는 방법에 따라 거짓말을 한다 / 정확성과 성능은 따로 / 배포는 되돌릴 수 있어야 끝난다
💡 [가상]과 [실제]를 나눠 적는 이유정직함이 판단력을 보여 줍니다. 테스트 결제로 운영했다면 그렇게 쓰고, 지어낸 숫자는 쓰지 않습니다. 가상 사례로 연습한 것은 "방법을 안다"는 증거이고, 실제 숫자는 여러분이 운영해서 채웁니다.
🔁 20주를 한 문장으로기획하고, 디자인하고, 만들고, 자동으로 배포하고, 문제를 먼저 알아채고, 숫자와 사용자의 말로 고칠 곳을 찾아 고치고, 그 과정을 정직하게 기록했습니다.
