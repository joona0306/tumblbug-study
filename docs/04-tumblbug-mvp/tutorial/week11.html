11주차 · 5단계 · 구현의 핵심

결제와 초과 판매 방지

모아에서 가장 조심해야 하는 순간입니다. 돈이 오가고, 한정 수량이 걸려 있습니다. 이번 주에는 2단계(커피 후원)의 결제 흐름에 세 가지를 더합니다: 남은 수량보다 많이 팔지 않기, 결제 결과를 여러 곳에서 받아도 한 번만 반영하기(웹훅), 그리고 이것을 테스트로 증명하기.

🗺️ 이번 주 그림 — 결제 한 건이 지나가는 길
① 결제하기서버가 총액 계산 → 결제 대기(pending) 후원 저장
② 토스 결제창테스트 모드 — 실제 청구 없음
③ 승인 전 트랜잭션금액 비교 → 주문 선점 + 재고 조건부 차감
④ 토스 승인트랜잭션 밖에서 (느릴 수 있으니까)
⑤ 결과 반영완료: 결제 기록 / 실패: 재고 되돌리기

결제창에서 돌아오지 못하면(브라우저를 닫음 등) → 토스가 보내는 웹훅이, 그것도 없으면 13주차 예약 작업이 마무리한다.

용어한 줄 뜻
조건부 차감"남아 있을 때만 줄여라"를 UPDATE 한 문장에 넣는 것. 확인과 차감 사이에 다른 사람이 끼어들 틈이 없다
트랜잭션여러 DB 변경을 "모두 되거나, 모두 안 되거나"로 묶는 것
웹훅결제 상태가 바뀌면 토스가 우리 서버 주소로 알려 주는 것
멱등성같은 요청이 여러 번 와도 결과가 한 번 온 것과 같은 성질
1결제 시작: 결제 대기 후원 + 결제위젯
💡 왜 결제창을 열기 "전에" 후원을 저장하나요? 결제가 끝나고 돌아왔을 때 "원래 얼마였지?"를 비교할 기준이 필요합니다. 브라우저가 알려 주는 금액은 조작될 수 있으니, 서버가 계산한 금액을 결제 대기(pending) 후원으로 먼저 적어 두고, 돌아온 금액과 비교합니다 (2단계 커피 후원과 같은 원리).

.env.local 에 토스 테스트 키 두 개를 넣습니다 (개발자센터 → API 키 → 결제위젯 연동 키). 실수로 라이브 키(live_)를 넣으면 서버가 시작할 때 막습니다 (lib/env.ts).

확인 화면은 결제위젯을 그리고, "결제하기"를 누르면 서버에 고른 것만 보낸 뒤 서버가 준 금액으로 결제창을 엽니다.

✅ 확인하는 법
  • 확인 화면에 결제수단·약관 위젯이 그려지고 "○○원 결제하기" 버튼이 켜진다
  • 결제창을 열었다 닫으면 "결제를 시작하지 못했어요" 안내 + DB 의 그 후원이 failed
🆘 막혔을 때
버튼이 "결제 준비 안 됨"에서 바뀌지 않아요

NEXT_PUBLIC_TOSS_CLIENT_KEY 가 비어 있습니다. .env.local 을 고친 뒤 개발 서버를 다시 시작하세요 (NEXT_PUBLIC_ 값은 시작할 때 읽습니다). CI 처럼 키가 없는 곳에서는 일부러 결제를 끈 상태입니다.

전자결제 신청 전이라 "문서 예제용 공용 키"(test_gck_docs_…)만 보여요

결제 테스트는 됩니다. 다만 이 공용 키로 한 결제는 여러분 상점의 웹훅을 부르지 않습니다 (작성자가 실제로 확인한 한계 — 3단계 참고).

🔁 방금 무슨 일이 일어났나"결제하기"를 누르면 서버가 다시 검사하고, 서버가 계산한 금액으로 결제 대기 후원을 만든 뒤, 그 금액으로 토스 결제창을 엽니다. 결제창을 닫으면 그 후원은 "실패"로 남아 어디서 포기했는지 알 수 있습니다.
2결제 승인: 주문 선점 + 조건부 차감 → 토스 승인 → 결과 반영
🗺️ 그림 먼저 — 남은 1개를 두 사람이 동시에
A 의 UPDATEsold_qty + 1 ≤ limit_qty 일 때만
✅ 1줄 바뀜A 는 토스 승인으로
B 의 UPDATE같은 조건 — A 가 끝날 때까지 줄을 기다림
❌ 0줄 바뀜B 는 품절 → 토스를 부르지 않는다 (돈이 안 나감)

"확인(SELECT) 후 차감(UPDATE)" 두 문장으로 나누면, 둘 다 "1개 남았네"를 보고 사 버릴 수 있다.

💡 왜 토스 승인을 트랜잭션 "밖"에서? (ADR-003) 트랜잭션 안에서 바꾼 줄은 끝날 때까지 잠깁니다. 토스 승인은 바깥 서버라 몇 초 걸릴 수도 있어요. 그 사이 같은 리워드의 다른 후원이 모두 줄을 서서 기다리게 됩니다. 그래서 ② 선점·차감(짧게) → ③ 토스(밖) → ④ 결과 반영(짧게)으로 나눕니다. ③에서 응답을 못 받으면 "처리 중"으로 두고, 웹훅·예약 작업이 마무리합니다.

결제창이 성공하면 토스가 보내 주는 주소(성공 주소)에서 이 함수를 부릅니다:

✅ 확인하는 법
  • DB 테스트 통과 — 특히 "남은 1개를 10명이 동시에 결제해도 1명만 승인, 초과 판매 0건", "같은 주문이 동시에 두 번 와도 토스 승인은 한 번만", "품절·금액 조작이면 토스를 부르지 않는다"
  • 테스트는 진짜 토스 대신 가짜 토스(정해 둔 답을 돌려주는 도구)를 끼워 넣습니다 — confirmFunding(db, toss, …) 가 토스 도구를 인자로 받게 만든 이유
🆘 막혔을 때
동시성 테스트가 가끔만 실패해요

확인과 차감이 한 문장인지 보세요. select … soldQty 로 읽고 JavaScript 에서 비교한 뒤 update 하면, 가끔 두 요청이 겹쳐 둘 다 통과합니다. 조건은 반드시 UPDATE 의 WHERE 안에.

테스트에서 시각 비교가 이상해요 (now())

PostgreSQL 의 now() 는 트랜잭션이 시작한 시각입니다. 한 트랜잭션 안에서는 몇 번을 불러도 같은 값이에요. 시각 순서가 중요한 테스트는 값을 직접 넣으세요 (작성자가 겪은 함정).

🔁 방금 무슨 일이 일어났나결제 승인을 네 조각으로 나눴습니다. 가장 중요한 ②에서 "주문 선점"과 "재고 조건부 차감"을 한 트랜잭션으로 묶어, 동시에 몰려도 한정 수량을 넘지 않게 했습니다. 이 규칙은 16주차 k6 부하 테스트(50명 동시)로 다시 증명됩니다.
🤔 스스로 확인
"주문 선점"(payment_key 를 비어 있을 때만 채우기)은 무엇을 막나?

같은 주문으로 요청이 두 번 동시에 오는 경우(새로고침, 두 번 클릭)입니다. 한 요청만 다음으로 가서, 토스 승인이 두 번 일어나지 않습니다.

품절이면 왜 토스를 부르지 않나?

승인하지 않으면 돈이 빠져나가지 않습니다. "돈을 받고 나서 환불"보다 "처음부터 받지 않기"가 사용자에게도, 운영에도 훨씬 안전합니다.

3토스 웹훅: 돌아오지 못한 결제 마무리하기
🗺️ 그림 먼저 — 알림을 믿지 말고 확인하라
토스"결제 상태 바뀜" 알림 (여러 번 올 수 있음)
① 처리한 알림?이미 봤으면 건너뛰기
② 토스에 직접 조회알림 내용은 누구나 꾸밀 수 있다
③ 결제 대기만 바꾸기이미 끝난 후원은 그대로
④ 알림 기록처리가 끝난 "다음에"
💡 왜 기록을 "처리한 다음에" 남기나요?먼저 기록하고 처리하다 에러가 나면, 토스가 다시 보낸 같은 알림을 "이미 처리했음"으로 착각해 영영 반영하지 못합니다. 처리 → 기록 순서면, 에러가 났을 때 500 으로 답해 토스가 다시 보내고, 그때 제대로 처리됩니다.
✅ 확인하는 법DB 테스트: 같은 알림 여러 번 → 한 번만 · 가짜로 DONE 이라고 보내도 토스 조회가 없으면 무시 · 주문 번호가 다르면 무시 · 이미 끝난 후원은 그대로 · 토스 조회가 실패하면 에러 → 500 → 다시 받기
🆘 막혔을 때
웹훅을 등록하고 테스트 결제를 했는데 전송 기록이 비어 있어요

작성자가 실제로 겪은 일입니다. 웹훅 주소 등록은 배포 뒤(14주차)에 하고, 결제위젯의 문서 예제용 공용 키로 결제하면 토스는 여러분 상점의 웹훅을 부르지 않습니다. 웹훅 코드는 DB 테스트와 흐름 테스트(가짜 알림 → "ignored")로 검증하고, 실제 전송은 전자결제 신청 후 받은 내 키로 확인합니다 (docs/operations.md 0번, PLAN 의 알려진 한계).

🔁 방금 무슨 일이 일어났나결제창에서 돌아오지 못한 결제도 토스의 알림으로 마무리되게 했습니다. 알림은 몇 번이 와도(멱등), 가짜가 와도(토스에 직접 조회) 결과가 틀어지지 않습니다.
🤔 스스로 확인
웹훅 알림에 적힌 "DONE"을 그대로 믿으면 무슨 일이 생길까?

누구나 우리 웹훅 주소로 "DONE" 알림을 꾸며 보내 돈을 내지 않고 후원 완료를 만들 수 있습니다. 그래서 토스 결제 조회로 진짜 상태를 확인합니다.

4내 후원 내역 (/me/fundings)
💡 왜 필요한가요?후원자가 가장 불안한 순간은 결제 직후입니다. "내 돈이 제대로 갔나?"를 스스로 확인할 곳이 있어야 문의가 줄고 신뢰가 생깁니다 (1주차 인터뷰의 인사이트).
✅ 확인하는 법결제한 계정으로 /me/fundings → 방금 후원이 "결제 완료"로. 결제창을 닫은 후원은 보이지 않는다 (돈이 오간 적 없는 기록)
🔁 방금 무슨 일이 일어났나DB 의 세 상태(pending·paid·failed)를 사용자에게 보이는 말(확인 중·결제 완료·실패)로 바꿔 보여 줬습니다. "승인 단계에 들어간" 후원만 보여서, 포기한 기록이 목록을 어지럽히지 않습니다.
5결제 흐름 테스트
✅ 확인하는 법
  • 금액 조작 → 승인 안 함 · 남의 주문 번호로 결과 화면 불가 · 결제창 취소 → 실패 기록 · 내 후원 내역 · 웹훅 모양 검사(400)·모르는 결제 무시(200)
  • 진짜 토스 테스트 결제 테스트는 키가 있을 때만(내 컴퓨터) 돌고, CI 에서는 건너뜁니다
🆘 결제창의 인증(PIN·카드사 화면)은 누가 하나요?

외부 결제창의 인증 단계는 자동화 도구나 AI 에게 맡기지 않고 여러분이 직접 합니다 (작성자도 이 단계는 직접 확인했어요). 테스트 모드라 실제로 청구되지 않습니다.

🔁 방금 무슨 일이 일어났나결제에서 사고가 날 수 있는 길(금액 조작, 남의 주문, 취소, 가짜 웹훅)을 하나씩 테스트로 막았습니다.
