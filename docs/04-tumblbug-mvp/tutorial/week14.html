14주차 · 7단계 · 배포(CD)의 시작

CD 파이프라인: CI 를 통과한 코드만 배포된다

1~3단계에서는 Vercel 이 GitHub 에 올라온 코드를 바로 배포했습니다. 이번 주부터는 GitHub Actions 가 순서를 지휘합니다. 검사(CI)를 통과해야만 DB 를 바꾸고, 배포하고, 배포된 주소가 정말 살아 있는지까지 확인합니다. PR 마다 미리보기 주소와 미리보기 DB도 자동으로 생겼다가 사라집니다.

PR 을 닫으면 미리보기 DB 브랜치도 지운다. 어느 단계든 실패하면 그 뒤는 돌지 않는다 — 망가진 코드가 운영에 가지 않는다.

용어한 줄 뜻
CI (지속적 통합)변경할 때마다 자동으로 검사·테스트해서 "합쳐도 되는 코드인가"를 확인
CD (지속적 배포)검사를 통과한 코드를 자동으로 배포까지. 이 교재는 합치기(merge)가 사람의 관문이고, 그 뒤는 자동
연기 테스트배포 직후 "불이 붙었나(연기가 나나)"만 빠르게 보는 테스트

비밀값(Secret)토큰·DB 주소처럼 남에게 보이면 안 되는 값. GitHub·Vercel 설정 화면에만 넣는다
1배포 준비: Vercel 자동 배포 끄기 · 상태 확인 주소 · 연기 테스트
💡 왜 Vercel 의 자동 배포를 끄나요?Vercel 이 스스로 배포하면 CI 가 실패해도 배포가 됩니다. 순서를 지키려면 배포하는 곳을 하나(GitHub Actions)로 정해야 해요.

"git": { "deploymentEnabled": false } — Vercel 이 git push 를 보고 스스로 배포하지 않게 합니다. 배포 주소가 살아 있는지 확인할 곳도 만듭니다:

💡 연기 테스트가 DB 에 쓰지 않는 이유운영 주소에도 돌리기 때문입니다. 운영 데이터를 건드리지 않고, 프로젝트가 하나도 없는 빈 운영 DB 에서도 통과해야 해요. 그리고 commit 을 확인해서 "도메인이 방금 올린 커밋을 가리키나"까지 봅니다.
🔁 방금 무슨 일이 일어났나배포 권한을 Vercel 에서 GitHub Actions 로 옮기고, 배포가 끝나면 두드려 볼 문(/api/health)과 두드리는 방법(연기 테스트)을 준비했습니다.

💡 왜 마이그레이션이 배포보다 먼저?새 코드는 새 칸(열)을 찾습니다. 코드가 먼저 나가면 "그런 칸 없음" 에러가 납니다. 그래서 마이그레이션은 옛 코드도 계속 돌 수 있게 만듭니다 (칸 삭제·이름 바꾸기는 두 번의 배포로 나눈다).

빌드 때 비밀값이 없다 — 그래서 바꾼 코드

GitHub Actions 에서 vercel build 를 하면 Vercel 의 Secret 타입 환경 변수는 진짜 값으로 오지 않습니다. 그런데 next build 는 페이지 정보를 모으려고 서버 코드를 한 번 불러오고, 그때 환경 변수 검사가 "DB 주소 없음"으로 멈췄습니다 (작성자가 실제로 겪음).

검사는 서버가 켜질 때 instrumentation.ts 의 parseEnv 가 합니다 → 값이 틀리면 여전히 배포 직후에 바로 드러납니다. 마이그레이션 단계에는 DB 주소만 있으니 drizzle.config.ts 는 DB 주소만 검사하는 parseDatabaseUrl 을 씁니다.

🔁 방금 무슨 일이 일어났나"PR 이면 미리보기, 합치면 운영"을 한 파일에 적었습니다. 그리고 비밀값은 빌드가 아니라 실행할 때 필요하다는 사실에 맞춰 검사 시점을 옮겼습니다.
🤔 스스로 확인
미리보기 배포에 운영 DB 가 아니라 "개발 DB 복사본"을 쓰는 이유는?

PR 코드는 아직 검증 전이라 운영 데이터를 망가뜨릴 수 있고, 운영 DB 에는 개인정보(배송지)가 있습니다. 그래서 운영 DB 는 아예 다른 Neon 프로젝트(moa-prod)에 두어 복사되지 않게 합니다.

CD 인데 왜 사람이 매번 "Merge" 를 누르나?

합치기가 "이 코드를 운영에 내보내도 된다"는 사람의 결정(관문)입니다. 합친 뒤의 마이그레이션·배포·확인은 모두 자동이라 지속적 배포(continuous deployment)가 맞습니다.

3Neon · Vercel 설정

① Neon: 운영 DB 는 따로

  1. Neon → New Project moa-prod, Postgres 18, 지역 Singapore (Vercel 함수 sin1 과 같은 곳 — 멀면 쿼리마다 왕복 시간이 붙는다)
  2. Connect → pooling 켠 주소(앱용 → Vercel) · pooling 끈 주소(마이그레이션용 → GitHub). 둘 다 끝을 sslmode=verify-full 로
  3. 개발용 프로젝트의 Project ID → GitHub 변수 NEON_PROJECT_ID · 계정 → API keys → github-actions → 비밀값 NEON_API_KEY

② Vercel: 환경 변수 7개

📌 Secret 과 ConfigSecret = 저장 후 다시 볼 수 없음 (비밀번호·키·토큰). Config = 저장 후에도 보임. NEXT_PUBLIC_ 값은 어차피 브라우저로 보내지는 공개 값이고, 빌드할 때 값이 있어야 화면 코드에 새겨지므로 반드시 Config 로 넣습니다.

"Add Environment Variable" 창 하나에서는 Type 과 환경을 한 가지로만 고를 수 있어서, 같은 것끼리 묶어 창을 4번 엽니다 (Secret·Production / Secret·Production+Preview / Config·Production / Config·Production+Preview). 환경 여러 개는 Environments › 로 한 단계 더 들어가 체크합니다.

③ 나머지 Vercel 값

  • Storage → Blob 저장소를 Connect — 뜨는 창에서 Production·Preview 를 직접 체크해야 BLOB_READ_WRITE_TOKEN 이 들어갑니다
  • Deployment Protection → Protection Bypass for Automation → 비밀값 VERCEL_AUTOMATION_BYPASS_SECRET (잠긴 미리보기 주소에 연기 테스트가 들어가는 열쇠)
  • 프로젝트 Project ID → VERCEL_PROJECT_ID · 팀 Settings → Team ID(team_…) → VERCEL_ORG_ID
  • 계정 Tokens → Create → Scope: 팀 이름 → All Projects → VERCEL_TOKEN
🆘 작성자가 실제로 막힌 곳
Import .env 로 한꺼번에 불러왔더니 production,preview 로 섞이고 Caution 표시가 떠요

.env.local 을 통째로 불러오면 개발용 값(개발 DB 주소, localhost)이 운영에 들어가고, Type·환경도 한 가지로 묶여 버립니다. 불러온 것은 지우고 위 표대로 창 4번으로 나눠 넣으세요.

Blob 토큰이 "자동으로 들어간다"는데 체크를 해야 들어가요

Connect 창에서 넣을 환경을 직접 체크하는 방식입니다. 체크한 환경에만 토큰이 추가돼요. 값을 복사해 붙여 넣을 필요는 없습니다.

토큰 Scope 에 "프로젝트 하나"를 골랐더니 Could not retrieve Project Settings

Vercel CLI 는 프로젝트와 함께 팀 정보도 읽습니다. 프로젝트 하나로 제한한 토큰은 팀 정보를 못 봐서 멈춰요 (API 로 프로젝트만 조회하면 200 이라 원인을 찾기 어려웠습니다). 팀 → All Projects 로 새로 만듭니다.

VERCEL_ORG_ID 에 계정 설정의 "Your ID"를 넣었어요

요즘 Vercel 은 무료 계정도 "OO's projects" 팀 안에 프로젝트를 만듭니다. 개인 ID 가 아니라 팀 ID(team_…)를 넣어야 합니다.

🔁 방금 무슨 일이 일어났나배포에 필요한 값을 두 곳에 나눠 넣었습니다. Vercel에는 앱이 실행될 때 쓰는 값(운영 DB 주소, 로그인 비밀키 등)을, 곧 GitHub 에는 배포를 지휘할 때 쓰는 값을 넣습니다. Secret 종류는 빌드 때 값이 오지 않으니 앱이 실행될 때 검사합니다.

💡 production "환경"을 따로 만드는 이유운영 DB 주소는 이 환경에 연결된 작업(production job)에서만 꺼낼 수 있습니다. 다른 브랜치나 미리보기 작업이 운영 비밀값을 쓰지 못하게 막는 벽이에요. (승인자 지정은 비공개 저장소면 유료 요금제에서만 — 그래서 이 교재에서는 합치기가 관문입니다.)
🆘 막혔을 때
토큰을 새로 발급했는데 403

옛 토큰을 지운 직후, 이미 돌고 있던 실행이 옛 토큰을 쓰다가 막힌 경우였습니다. 새 토큰을 넣은 뒤 Re-run 하면 됩니다.

"Vercel 연결 확인" 단계가 404 / 403

404 = ID 가 틀림 (VERCEL_ORG_ID 팀 ID·VERCEL_PROJECT_ID), 403 = 토큰 권한(Scope) 부족. 이 단계는 비밀값을 출력하지 않고 "무엇이" 틀렸는지만 알려 줍니다.

🔁 방금 무슨 일이 일어났나GitHub 이 Vercel·Neon 을 대신 조작할 수 있게 열쇠(토큰)와 주소(ID)를 맡기고, DEPLOY_ENABLED 스위치로 "설정을 다 마친 뒤에만 배포"하게 했습니다. 운영 DB 주소는 production 환경에만 둬서 운영 배포 작업만 꺼낼 수 있습니다.
5첫 파이프라인 돌리기
  1. 작은 변경으로 브랜치 → PR → Actions 의 CI/CD 가 ci → preview 순서로 도는지, PR 에 미리보기 주소 댓글이 달리는지
  2. 미리보기 주소에서 예시 계정으로 로그인 (미리보기 DB = 개발 DB 복사본 → docs/accounts.md)
  3. PR 을 합친다 → production 이 끝나면 운영 주소 /api/health 의 commit 이 합친 커밋인지
  4. PR 이 닫히면 Neon Branches 에서 preview/pr-N 이 사라졌는지
  5. 운영 주소에서 가입 → Neon moa-prod SQL Editor 에서 내 계정만 관리자로: update "user" set role = 'admin' where email = '내이메일';
✅ 작성자 기록 [실제]첫 실행은 토큰 Scope·팀 ID·빌드 때 비밀값 문제로 여러 번 실패했고, 하나씩 고친 뒤 미리보기·운영 모두 초록불. 운영 주소의 /api/health → {"ok":true,"db":"ok","commit":"…"}
🔁 방금 무슨 일이 일어났나이제 main 에 합치기만 하면, 사람 손 없이 같은 순서(검사 → DB → 배포 → 확인)로 운영에 나갑니다. PR 을 열면 남에게 보여 줄 수 있는 미리보기 주소가 생깁니다.
🤔 스스로 확인
연기 테스트가 운영 주소의 commit 까지 확인하는 이유는?

배포가 "성공"했다고 해도 도메인이 아직 옛 배포를 가리킬 수 있습니다. commit 이 같아야 "방금 올린 코드가 실제로 돌고 있다"가 증명됩니다.
