대시보드·관리자·예약 작업, 그리고 상태 화면

서비스를 쓰는 사람뿐 아니라 돌보는 사람을 위한 화면을 만듭니다. 창작자는 숫자로 모금 현황을 보고, 관리자는 문제 있는 프로젝트를 숨기고, 서버는 매일 밤 스스로 뒷정리를 합니다. 마지막으로 "불러오는 중·비어 있음·에러" 화면을 챙겨 구현 파트를 마무리합니다.

1창작자 대시보드: 숫자는 저장하지 않고 SQL 로 계산
💡 왜 "모인 금액" 칸을 따로 저장하지 않나요?후원이 생기고, 실패하고, 웹훅으로 뒤늦게 완료되는 길이 여러 개입니다. 합계를 따로 저장하면 어느 한 길에서 더하기를 빠뜨리는 순간 숫자가 틀어집니다. 후원 기록(원본)에서 매번 계산하면 틀릴 수가 없습니다 — 6주차에 배운 SQL 집계를 화면으로 옮기는 것입니다.
✅ 확인하는 법
  • 창작자 예시 계정(ohneul_workshop@seed.moa.test)으로 /studio → 모인 금액·후원자 수·평균 후원액, 14일 막대, 리워드별 판매, 후원자·배송지 표
  • 프로젝트 칩을 바꾸면 주소가 ?project=번호 로 바뀌고, 새로고침해도 그 프로젝트
  • npx vitest run tests/db/dashboard.test.ts 통과
🆘 막혔을 때
새벽에 한 후원이 전날 막대에 들어가요

날짜를 UTC 로 자르면 한국 시간 0~9시가 전날이 됩니다. (paid_at at time zone 'Asia/Seoul')::date 처럼 한국 시간으로 자릅니다.

후원이 없는 날이 막대에서 빠져요

후원 기록만 GROUP BY 하면 없는 날은 줄 자체가 없습니다. generate_series 로 날짜 목록을 먼저 만들고 LEFT JOIN 하면 0 으로 나옵니다.

🔁 방금 무슨 일이 일어났나창작자가 궁금한 숫자 네 가지를 SQL 집계 네 개로 만들고, 서로 기다릴 필요 없는 조회는 Promise.all 로 동시에 보냈습니다. 배송지(개인정보)는 결제 완료 후원만, 그 프로젝트의 창작자에게만 보입니다.
🤔 스스로 확인
count(distinct supporter_id) 와 count(id) 는 어떻게 다른가?

앞은 후원자 수(한 사람이 두 번 후원해도 1명), 뒤는 후원 건수(2건)입니다.

2관리자 화면: 숨기기와 결제 실패 목록
💡 버튼을 관리자에게만 보여 주면 충분하지 않나요?아닙니다. 서버 액션은 버튼이 없어도 누구나 직접 부를 수 있습니다. 버튼 숨기기는 편의일 뿐, 진짜 막는 것은 서버 액션 안의 requireAdmin() 입니다. 관리자가 아닌 사람이 /admin 에 오면 "없는 페이지"(404)를 보여 줘서 그런 화면이 있다는 사실조차 알리지 않습니다.
✅ 확인하는 법
  • moa_admin@seed.moa.test 로 /admin → 숨기기를 누르면 목록·상세에서 사라지고, 다시 보이기로 돌아온다
  • 일반 계정으로 /admin → 404
  • 결제 실패 이유별 개수 (예: PAY_PROCESS_CANCELED = 결제창을 닫음) — 15주차 운영 점검에서 다시 봅니다
🔁 방금 무슨 일이 일어났나운영자가 문제에 대응할 최소한의 도구를 만들었습니다. 숨긴 프로젝트는 지우지 않으므로 후원 기록은 그대로 남습니다.
3예약 작업: 매일 밤 서버가 스스로 하는 뒷정리 (Vercel Cron)
🗺️ 그림 먼저 — 매일 0시에 세 가지
Vercel Cron매일 15:00 UTC (= 한국 0시), 비밀값을 붙여 부른다
① 상태 확정마감이 지난 모금중 → 성공/실패
② 결제 대기 정리돌아오지 않은 결제 → 실패, 결과 모르는 결제 → 토스에 물어서 맞춤
③ 기록 청소하루 지난 요청 수 기록

.env.local 에 무작위 비밀값을 넣습니다 (Vercel 환경 변수에도 같은 값 — 14주차 배포 때):

💡 왜 "두 번 돌려도 결과가 같게"(멱등)?예약 작업은 늦게 돌 수도, 실패 후 다시 돌 수도, 사람이 손으로 한 번 더 돌릴 수도 있습니다. 그래서 "아직 모금중인 것만 확정", "아직 결제 대기인 것만 정리"처럼 이미 처리한 줄은 건드리지 않는 조건을 모든 작업에 넣습니다.
✅ 확인하는 법
  • DB 테스트: 마감 지난 것만 확정·두 번 돌려도 같음 · 돌아오지 않은 결제 → ABANDONED · 토스가 DONE 이면 완료 · 모르는 결제면 실패 + 재고 되돌리기 · 토스 조회 실패면 다음 날로
  • 비밀값 없이 /api/cron/daily → 401 (설정 전이면 500) — 아무나 부를 수 없다
🆘 막혔을 때
내 컴퓨터에서 Cron 이 돌지 않아요

정상입니다. Vercel Cron 은 배포된 운영 환경에서만 돕니다. 내 컴퓨터에서는 테스트로 확인하고, 배포 뒤(14주차) Vercel → Settings → Cron Jobs 에서 확인·수동 실행합니다.

🔁 방금 무슨 일이 일어났나사람이 매일 챙겨야 할 일을 서버가 매일 밤 하게 했습니다. 11주차에 "웹훅도 안 오면 예약 작업이 마무리한다"고 했던 그 마지막 안전망입니다.
🤔 스스로 확인
화면은 모금 상태를 매번 계산하는데, 왜 예약 작업이 DB 에도 확정해 두나?

화면은 항상 정확한 계산값을 보여 주지만(ADR-001), "성공한 프로젝트만" 같은 목록 필터와 기록에는 DB 에 저장된 값이 편하고 빠릅니다. 둘이 어긋나지 않게 같은 마감 규칙을 씁니다.

4로딩·빈 화면·에러·404
💡 왜 상태 화면까지 챙기나요?실제 사용자는 느린 인터넷, 빈 목록, 가끔 나는 에러를 만납니다. 그때 하얀 화면이나 "Error"만 보이면 떠납니다. 무슨 일인지 + 다음에 할 일을 보여 주는 것까지가 기능입니다 (Figma 의 State 컴포넌트).
✅ 확인하는 법
  • 개발자 도구 → Network → "Slow 4G" 로 목록을 열면 카드 모양 뼈대가 먼저 보인다
  • 찜이 없는 계정의 /me/likes → 빈 화면 안내 + "프로젝트 둘러보기"
  • /debug/sentry?throw=render → "화면을 불러오지 못했어요" + 오류 번호 (에러 내용 자체는 보이지 않음)
🔁 방금 무슨 일이 일어났나Next.js 의 규칙 파일(loading·error·not-found)과 빈 화면 컴포넌트로 "정상이 아닌 순간"의 화면을 만들었습니다. 에러는 사용자에게 내부 정보를 보여 주지 않고 Sentry 로 보냅니다.
5흐름 테스트 + 스트리밍 404 함정 (라우트 그룹)
🗺️ 그림 먼저 — 없는 프로젝트인데 왜 200 이 나올까
app/projects/loading.tsxprojects 아래 모든 페이지를 스트리밍으로
뼈대를 먼저 보냄이때 상태 코드 200 도 먼저 나가 버림
그 뒤 notFound()화면은 404 지만 응답은 이미 200
해결: app/projects/(list)/loading.tsx괄호 폴더(라우트 그룹)는 주소에 안 나타남 → 목록(/projects)에만 뼈대, 상세·후원은 제대로 404
🆘 작성자가 실제로 겪은 문제

없는 프로젝트 주소가 화면에는 "페이지를 찾을 수 없어요"를 보여 주는데, 흐름 테스트의 expect(res.status()).toBe(404) 가 200 으로 실패했습니다. 검색 엔진과 가동 감시는 상태 코드를 보기 때문에, 화면만 404 인 것은 404 가 아닙니다. 위처럼 뼈대(loading.tsx)를 목록 폴더 안으로 옮겨 해결했습니다.

✅ 확인하는 법대시보드 숫자·표 · 남의 프로젝트 번호로 남의 대시보드 불가 · 관리자 숨기기 · 예약 작업 비밀값 · 없는 주소는 진짜 404
🔁 방금 무슨 일이 일어났나13주차 기능을 흐름 테스트로 굳히고, 스트리밍이 상태 코드를 먼저 보내 버리는 함정을 라우트 그룹으로 피했습니다. 이것으로 구현 파트(5~13주)가 끝났습니다 — 다음 주부터는 이 앱을 자동으로 배포하고 지키는 법입니다.
🤔 스스로 확인
라우트 그룹 (list) 폴더 이름이 주소에 나타나지 않는다는 게 왜 중요한가?

주소(/projects)는 그대로 두고 파일 구조만 나눌 수 있어서, loading.tsx 가 적용되는 범위를 "목록 페이지만"으로 좁힐 수 있습니다.
