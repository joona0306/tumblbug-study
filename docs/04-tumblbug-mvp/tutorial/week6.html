DB·SQL 심화: 데이터가 사는 집 짓기

1~3단계에서는 표를 "쓰기만" 했다면, 이번 주에는 표를 설계하고, 규칙을 새기고, 빠르게 하고, 동시에 몰려도 틀리지 않게 합니다. 4단계에서 가장 공학적인 주입니다.

🗺️ 이번 주 그림 — 데이터가 사는 집을 짓는다
개념 ERD (2주차)무엇을 기억할까
물리 ERD + 규칙칸·키·CHECK·인덱스
SQL 로 확인통계·실행 계획
트랜잭션초과 판매 없는 재고 차감

화면은 아직 없다. 하지만 이번 주에 만든 규칙이 11주차 결제와 16주차 부하 테스트까지 앱을 지킨다.

용어한 줄 뜻
외래 키다른 표의 줄을 가리키는 칸 (후원.project_id → 프로젝트.id)
CHECK 제약칸 값이 지켜야 할 규칙을 DB 가 직접 검사 (가격 1,000~1,000,000)
인덱스빨리 찾기 위한 찾아보기 (책 뒤의 색인)
실행 계획DB 가 쿼리를 "어떤 방법으로" 실행했는지 (EXPLAIN ANALYZE)
트랜잭션여러 작업을 "둘 다 되거나 둘 다 안 되게" 묶기
1DB 연결: 표준 드라이버 pg + CI 의 테스트용 PostgreSQL
🗺️ 그림 먼저 — 같은 코드로 세 곳의 DB 에 붙는다
db/index.tspg Pool (연결 보관함, 5개)
Neon 개발 DBtumblbug_dev (-pooler 주소)
CI 의 PostgreSQL매번 빈 DB 로 시작
16주차 Docker·EC2일반 PostgreSQL

1~3단계의 Neon 전용 HTTP 드라이버 대신 표준 드라이버를 쓰는 이유가 바로 이 그림 — ADR-005

ADR(결정 기록) = "무엇을 골랐고, 무엇을 버렸고, 왜"를 짧게 남긴 글. 나중의 나(또는 동료)가 "왜 이렇게 했지?"를 알 수 있게 합니다.

Neon 에서 tumblbug_dev DB 를 만들고, Connect 화면에서 Connection pooling 을 켠 주소를 복사해 .env.local 의 DATABASE_URL 에 넣습니다. 이때 주소 끝의 sslmode=require 를 sslmode=verify-full 로 바꿉니다.

💡 왜 CI 에 DB 를 따로 띄우나요?테스트가 개발 DB(Neon)를 쓰면 여러 사람·여러 PR 의 테스트가 서로의 데이터를 건드립니다. CI 는 매번 빈 PostgreSQL 컨테이너를 잠깐 띄워 테스트하고 버립니다. 여기 적힌 비밀번호는 컨테이너 안에서만 쓰이고 사라지는 값이라 적어도 괜찮아요.
✅ 확인하는 법
  • npx drizzle-kit generate --name auth_tables → npm run db:migrate 로 인증 표(user·session·account·verification)가 생긴다 (Neon → Tables)
  • PR 의 CI 에서 PostgreSQL 컨테이너가 뜨고 통과
🆘 막혔을 때
pg 가 sslmode 경고를 내요

pg 8.20 이상은 sslmode=require 에 보안 경고를 냅니다. 인증서까지 확인하는 verify-full 로 바꾸세요 (ADR-005 결과).

🔁 방금 무슨 일이 일어났나앱이 DB 에 붙는 통로(Pool)를 만들고, 그 결정을 ADR 로 남겼습니다. 같은 코드가 Neon·CI·Docker 어디서든 동작합니다.
🤔 스스로 확인
Pool 크기를 5로 작게 두는 이유는?

서버리스(Vercel)는 요청마다 함수가 여러 개 뜰 수 있어서, 함수 하나가 연결을 많이 잡으면 DB 연결 한도를 금방 넘습니다. Neon 풀러가 뒤에서 나눠 씁니다. (16주차 부하 테스트에서 이 5개가 병목이 되는 것도 봅니다)

2물리 ERD: 표·칸·키·규칙을 코드로
🗺️ 그림 먼저 — 개념 ERD 에서 무엇이 더해졌나
2주차 개념 ERD개체와 관계만 (창작자 1:N 프로젝트)
물리 ERD (db/schema.ts)칸의 타입 · 기본 키 · 외래 키 · CHECK · UNIQUE · 인덱스

찜(사용자 N : M 프로젝트)은 연결 표 project_like 가 된다 — 두 칸을 합친 것이 기본 키라 같은 프로젝트를 두 번 찜할 수 없다.

템플릿 07-data-model.md ③ 의 물리 ERD 를 Drizzle 표 설계도로 옮깁니다. 핵심인 리워드 표부터:

💡 왜 규칙을 DB 에도 새기나요? 코드에서 검사하면 되지 않나요?코드는 여러 곳에서 DB 를 바꿉니다(서버 액션·웹훅·예약 작업·사람이 SQL Editor 에서). 한 곳이라도 검사를 빠뜨리면 틀린 값이 들어가요. DB 의 CHECK 는 마지막 방어선 — 특히 reward_sold_check(판매 수 ≤ 한정 수량)는 초과 판매를 막는 최후의 벽입니다.
삭제 규칙뜻어디에
restrict딸린 줄이 있으면 지우지 못하게 막는다후원이 있는 프로젝트·사용자 (결제 기록은 지우면 안 됨)
cascade부모를 지우면 딸린 줄도 함께 지운다프로젝트를 지우면 리워드·찜도
✅ 확인하는 법Neon → Tables 에 project · reward · funding · project_like · payment_event
🔁 방금 무슨 일이 일어났나"이 앱이 기억해야 할 것"을 표로 확정하고, 틀리면 안 되는 규칙은 DB 가 직접 거절하게 했습니다.
🤔 스스로 확인
후원(funding)의 외래 키를 restrict 로 한 이유는?

후원은 결제 기록이라 지워지면 안 됩니다. 프로젝트나 사용자를 지우려 해도 후원이 딸려 있으면 DB 가 막습니다.

3DB 규칙이 정말 막는지 테스트 (끝나면 되돌리기)

DB 테스트는 진짜 DB로 합니다. 대신 각 테스트를 트랜잭션 안에서 돌리고 끝나면 무조건 ROLLBACK — 개발 DB 에 흔적이 남지 않습니다.

📌 테스트가 가정을 바로잡은 순간작성자는 "restrict 로 막히면 외래 키 에러(23503)"라고 생각했는데, 테스트를 돌려 보니 23001(restrict_violation)이었습니다. 문서가 아니라 실제로 돌려 본 결과가 답이에요.
✅ 확인하는 법npm test → constraints 테스트 11개 통과 (초과 판매·가격·카테고리·금액·결제 완료 조건·중복 주문·중복 찜·restrict/cascade)
🔁 방금 무슨 일이 일어났나"DB 가 막아 준다"를 말이 아니라 테스트로 확인했습니다. 누가 나중에 규칙을 지워도 테스트가 알려 줍니다.
4시드 데이터 (예시 데이터 넣기)
💡 왜 DB 이름을 검사하나요?시드는 예시 데이터를 지우고 다시 넣습니다. 실수로 운영 DB 주소가 들어 있으면 운영 데이터를 지울 수 있어요. 그래서 이름이 _dev·_test 로 끝나는 DB 에서만 돕니다.
✅ 확인하는 법홈에 예시 프로젝트 8개, 예시 계정(비밀번호 moa-dev-1234)으로 로그인 가능 (7주차부터)
🔁 방금 무슨 일이 일어났나화면을 만들기 전에 "보여 줄 데이터"를 준비했습니다. 여러 번 실행해도 같은 결과가 나옵니다.
5SQL 을 직접 써 보기 → Drizzle 함수로 (+ 시간대 함정)

Neon SQL Editor 에 한 덩어리씩 붙여 실행해 봅니다. 결과를 눈으로 확인한 뒤 코드(Drizzle)로 옮깁니다:

⚠️ 시간대 함정 (작성자가 실제로 겪음)DB 서버는 UTC, 사용자는 한국 시간(UTC+9). 시각 칸을 시간대 없는 timestamp 로 두면 "오늘 후원"이 9시간 어긋납니다. 그래서 모든 시각 칸을 timestamptz(시간대 포함)로 바꾸고(마이그레이션 0002), 날짜별 통계는 Asia/Seoul 기준으로 셉니다.
💡 왜 SQL 을 먼저 손으로 쓰나요?Drizzle 은 SQL 을 대신 만들어 줄 뿐입니다. SQL 을 모르면 느린 쿼리나 틀린 집계를 알아볼 수 없어요. LEFT JOIN(0건도 빠지지 않게), FILTER(결제 완료만), HAVING(집계 결과로 거르기)을 직접 써 봅니다.
✅ 확인하는 법npm test → stats 테스트 (결제 완료만, 같은 후원자는 한 명, 0건도 0)
🔁 방금 무슨 일이 일어났나SQL 로 먼저 답을 확인하고, 같은 계산을 코드로 옮겨 테스트로 고정했습니다.
🤔 스스로 확인
후원이 0건인 프로젝트가 목록에서 빠지지 않게 하려면 JOIN 을 어떻게?

LEFT JOIN 을 쓰고, 합계는 coalesce(sum(...), 0) 으로 0 을 채웁니다.

6인덱스와 실행 계획 (EXPLAIN ANALYZE)
🗺️ 그림 먼저 — 책에서 단어 찾기
Seq Scan첫 쪽부터 끝까지 넘기며 찾기 — 데이터가 늘면 비례해서 느려짐
Index Scan책 뒤 찾아보기로 쪽수 바로 찾기 — 데이터가 늘어도 거의 그대로

데이터가 적으면 차이가 안 보이므로, 프로젝트 2만 개·후원 30만 건을 잠깐 넣고(sql/week6-bulk.sql) 인덱스 전후를 비교합니다.

💡 그럼 모든 칸에 인덱스를 달면 되나요?아니요. 인덱스도 저장 공간을 쓰고, 후원이 들어올 때마다 인덱스도 함께 고쳐야 해서 쓰기가 느려집니다. "자주, 많이 읽는 조건"에만 답니다. 거르는 칸(status)을 앞에, 정렬하는 칸(deadline)을 뒤에 두면 정렬 단계까지 사라져요.
✅ 확인하는 법인덱스 전후로 같은 SQL 을 실행해 계획(Seq → Index)과 시간이 바뀌는 것을 본다. 끝나면 sql/week6-bulk-cleanup.sql 로 대량 데이터 정리
🔁 방금 무슨 일이 일어났나느린 이유를 "감"이 아니라 실행 계획으로 확인했고, 인덱스 하나로 100배 넘게 빨라지는 것을 숫자로 남겼습니다.
🤔 스스로 확인
인덱스 (status, deadline) 에서 칸의 순서가 중요한 이유는?

먼저 status 로 거른 뒤 그 안에서 deadline 순서로 정렬돼 있어서, 조건에 맞는 것을 마감 순서대로 20개만 읽고 끝낼 수 있습니다.

7트랜잭션: 조건부 차감 · 원자성 · 동시성
🗺️ 그림 먼저 — "확인하고 줄이기"를 두 번에 나누면 생기는 일
A: 남았나? → 1개
B: 남았나? → 1개(A 가 줄이기 전에 끼어듦)
둘 다 구매초과 판매!

해결: 확인과 차감을 UPDATE 한 문장에 넣는다 — DB 가 한 줄씩 잠그며 처리해서 한 명만 성공한다 (조건부 차감, ADR-003)

💡 트랜잭션이 뭔가요?"둘 다 되거나, 둘 다 안 되거나". 재고 차감과 후원 저장을 한 트랜잭션으로 묶으면, 후원 저장이 실패할 때 재고 차감도 함께 취소됩니다. 묶지 않으면 후원은 없는데 재고만 줄어 있어요 (테스트의 첫 번째 경우).
✅ 확인하는 법npm test → transaction 테스트: 트랜잭션 없으면 재고만 줄어듦(문제) / 있으면 함께 취소 / 10명이 동시에 사도 1명만 성공
🔁 방금 무슨 일이 일어났나11주차 결제에서 쓸 핵심 부품(조건부 차감)을 먼저 만들고, 동시에 몰려도 초과 판매가 없다는 것을 테스트로 확인했습니다. 16주차에는 50명으로 다시 확인합니다.
🤔 스스로 확인
DB CHECK(sold ≤ limit)가 있는데 조건부 차감이 또 필요한 이유는?

CHECK 만 있으면 초과 판매 시도가 "에러"로 끝나서 처리하기 어렵습니다. 조건부 차감은 "품절이면 0줄 바뀜"으로 조용히 알려 줘서, 결제를 승인하지 않고 품절 안내를 할 수 있습니다. CHECK 는 그래도 코드가 실수할 때의 마지막 벽입니다.
