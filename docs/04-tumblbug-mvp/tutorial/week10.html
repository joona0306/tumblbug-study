여러 단계 후원: 리워드 → 배송지 → 확인

후원은 한 화면에서 끝나지 않습니다. 리워드와 수량을 고르고, 배송지를 적고, 마지막에 확인합니다. 이번 주에는 여러 화면이 같은 선택을 함께 기억하는 법(Zustand)과, 브라우저가 보낸 금액을 믿지 않고 서버가 다시 계산하는 법을 배웁니다. 결제 자체는 11주차입니다.

🗺️ 이번 주 그림 — 선택은 브라우저에, 단계는 주소에, 최종 판단은 서버에
① 리워드?step=1 · 리워드·수량·추가 후원금
② 배송지?step=2 · 배송이 필요한 리워드일 때만
③ 확인?step=3 · 고른 내용·총액
서버 검사DB 기준으로 총액 다시 계산 · 재고·마감·내 프로젝트
Zustand 스토어고른 내용 — 세 화면이 함께 본다, 새로고침해도 유지(sessionStorage)
주소 ?step=지금 몇 단계인지 — 뒤로가기가 이전 단계로
rules.ts규칙(순수 함수) — 브라우저와 서버가 같은 규칙을 쓴다
용어한 줄 뜻
Zustand여러 컴포넌트가 함께 쓰는 값을 담는 작은 저장소(스토어). 서버에 없는 값(아직 결제 전의 선택)을 둘 때 쓴다
persist스토어 값을 브라우저 저장소에 적어 두어 새로고침해도 되살리는 기능
순수 함수같은 입력이면 항상 같은 결과, 바깥을 바꾸지 않는 함수. 테스트하기 쉽고 브라우저·서버가 함께 쓸 수 있다
1후원 스토어와 단계 규칙
💡 왜 스토어가 필요한가요? 1단계에서 고른 리워드를 3단계 확인 화면이 알아야 합니다. 화면마다 따로 기억하면 단계를 오갈 때 선택이 사라지고, 주소(?reward=3&qty=2…)에 다 넣으면 배송지 같은 개인정보가 주소창·기록에 남습니다. 그래서 "결제 전까지 서버에 없는 값"은 브라우저의 스토어 하나에 모읍니다 (docs/state-map.md의 상태 관리 지도).

먼저 규칙부터. 총액·수량·단계 이동을 계산하는 순수 함수입니다. 화면(브라우저)도, 결제 직전 검사(서버)도 이 파일을 씁니다.

그리고 스토어. 고른 내용과 그것을 바꾸는 함수들을 한곳에 둡니다.

💡 왜 localStorage 가 아니라 sessionStorage? 후원서에는 받는 분 이름·연락처·주소가 들어갑니다. localStorage 는 브라우저를 껐다 켜도 남아서 공용 컴퓨터에 개인정보가 오래 남습니다. sessionStorage 는 탭을 닫으면 지워집니다. 새로고침에는 살아남고, 떠나면 사라지는 딱 필요한 만큼입니다.
✅ 확인하는 법
  • 규칙 테스트가 모두 통과 (총액 = 가격 × 수량 + 추가 후원금, 수량은 남은 수량과 5개 중 작은 값까지, 앞 단계를 안 끝내면 그 단계로 되돌아감)
  • npm run typecheck 통과
🆘 막혔을 때
sessionStorage is not defined

서버에서 스토어를 읽으려 하면 생깁니다 (서버에는 브라우저 저장소가 없어요). 스토어 파일 맨 위의 "use client" 를 확인하고, 스토어를 서버 컴포넌트에서 import 하지 마세요. 2단계에서 "브라우저에서만 그리기"로 해결합니다.

🔁 방금 무슨 일이 일어났나후원 규칙을 화면과 떨어진 순수 함수로 만들고, 세 화면이 함께 볼 저장소(스토어)를 만들었습니다. 아직 화면은 없습니다 — 규칙부터 테스트로 굳혔어요.
🤔 스스로 확인
규칙을 컴포넌트 안이 아니라 rules.ts 에 따로 둔 이유는?

브라우저(화면 검사)와 서버(결제 직전 검사)가 같은 규칙을 써야 하기 때문입니다. 두 곳에 따로 쓰면 언젠가 어긋납니다. 순수 함수라 화면 없이 단위 테스트로 확인할 수 있는 것도 장점입니다.

다른 프로젝트의 후원 화면으로 가면 선택은 어떻게 되나?

start(projectId) 가 스토어의 projectId 와 다르면 비우고 새로 시작합니다. A 프로젝트의 리워드가 B 프로젝트 후원서에 섞이지 않게요.

2세 단계 화면과 건너뛰기 막기
🗺️ 그림 먼저 — 주소에 적힌 단계를 그대로 믿지 않는다
주소 ?step=3누군가 주소창에 직접 입력
allowedStep()리워드를 안 골랐네? 배송지가 비었네?
?step=1끝내지 않은 가장 앞 단계로

후원 페이지(서버 컴포넌트)는 로그인·프로젝트·마감·내 프로젝트를 먼저 확인하고, 단계 화면은 브라우저 컴포넌트에 맡깁니다.

💡 왜 "브라우저에서만 그리기"(useIsClient)? 서버는 sessionStorage 를 볼 수 없어서 "아무것도 안 고른" 화면을 그립니다. 브라우저는 저장된 선택을 읽어 "머그 2개"를 그립니다. 두 결과가 다르면 React 가 hydration 오류를 냅니다. 그래서 선택을 읽은 뒤(브라우저)에만 단계 화면을 그리고, 그 전에는 "불러오는 중…"을 보여 줍니다.

각 단계 화면은 스토어에서 값을 읽고, "다음"을 누르면 규칙 함수로 검사합니다. 리워드 단계의 앞부분:

✅ 확인하는 법
  • 예시 계정(supporter_kim@seed.moa.test)으로 로그인 → 프로젝트 상세 → 후원하기 → 리워드·수량 → 배송지 → 확인
  • 2단계에서 새로고침해도 고른 리워드·적은 배송지가 그대로
  • 리워드를 고르기 전에 주소를 ?step=3 으로 바꾸면 1단계로 돌아온다
  • 배송이 필요 없는 리워드(또는 리워드 없이)는 배송지 단계를 건너뛴다
🆘 막혔을 때
콘솔에 "Hydration failed…"

스토어 값을 서버가 그린 화면과 다르게 처음부터 그리고 있습니다. useIsClient() 로 브라우저에서만 단계 화면을 그리는지 확인하세요.

뒤로가기를 누르면 후원 화면 밖으로 나가 버려요

단계를 주소(?step=)가 아니라 컴포넌트 상태로만 바꾸면 브라우저 기록에 남지 않습니다. 단계 이동은 router.push(…?step=N) 로 하세요 (자동 보정은 기록을 쌓지 않게 replace).

🔁 방금 무슨 일이 일어났나세 단계 화면이 스토어 하나를 함께 보고, 지금 단계는 주소가 기억합니다. 주소를 조작해 앞 단계를 건너뛰면 규칙 함수가 되돌려 보냅니다 — 하지만 이건 편의일 뿐, 진짜 방어는 3단계의 서버 검사입니다.
🤔 스스로 확인
"현재 단계"는 스토어가 아니라 주소에 둔 이유는?

뒤로가기·새로고침·링크 공유가 자연스럽게 동작하기 때문입니다. 브라우저 기록은 주소 단위로 쌓입니다.

3결제 직전 서버 검사: 총액은 서버가 다시 계산
🗺️ 그림 먼저 — 브라우저가 보내는 것과 보내지 않는 것
브라우저고른 것만: 프로젝트·리워드 번호·수량·추가 후원금·배송지 (총액 ✗)
zod모양 검사 (숫자인가, 범위 안인가)
quoteFundingDB 에서 가격·재고·마감을 새로 읽고, 같은 규칙으로 검사, 총액 계산
💡 왜 브라우저의 총액을 믿지 않나요? 브라우저에서 계산한 값은 개발자 도구로 얼마든지 바꿀 수 있습니다. 36,000원짜리를 100원으로 바꿔 보낼 수도 있어요. 또 화면을 연 뒤 그 사이에 리워드가 품절됐거나 마감됐을 수도 있습니다. 그래서 결제 직전에 서버가 "지금 DB 기준으로" 다시 봅니다.
✅ 확인하는 법
  • DB 테스트 7개 통과: DB 가격으로 다시 계산 · 그 사이 가격이 바뀌면 바뀐 가격 · 다른 프로젝트의 리워드 번호를 끼워 넣으면 거절 · 남은 수량 초과 거절 · 배송지 비었으면 2단계로 · 1,000원 미만 거절 · 마감·숨김·내 프로젝트 불가
🆘 막혔을 때
다른 프로젝트의 리워드 번호가 통과돼요

리워드를 번호로만 찾으면 그렇습니다. where(eq(reward.projectId, p.id)) 처럼 이 프로젝트의 리워드만 읽은 목록에서 찾아야 "없는 리워드"가 됩니다.

🔁 방금 무슨 일이 일어났나브라우저는 "무엇을 골랐는지"만 보내고, 서버가 DB 의 최신 값으로 같은 규칙을 다시 돌려 총액을 정합니다. 11주차에는 이 총액을 결제 대기 후원에 적어 두고, 결제가 끝나면 이 금액과 비교합니다.
🤔 스스로 확인
화면에서 이미 검사했는데 서버가 또 검사하는 이유 두 가지는?
  • 화면 검사는 누구나 우회할 수 있다 (개발자 도구, 직접 요청)
  • 화면을 연 뒤 상황이 바뀔 수 있다 (품절, 마감, 가격 변경)
zod 와 quoteFunding 은 무엇이 다른가?

zod 는 "모양"(숫자인가, 범위 안인가)만 봅니다. DB 를 봐야 아는 것(재고, 마감, 가격, 이 프로젝트의 리워드인가)은 quoteFunding 이 봅니다.

4여러 단계 후원 흐름 테스트 (Playwright)
💡 왜 흐름 테스트까지?규칙 함수가 맞아도, 화면에서 버튼이 이어지지 않으면 후원은 못 합니다. 사람이 하는 순서 그대로(로그인 → 리워드 → 배송지 → 새로고침 → 확인) 브라우저를 움직여 확인합니다.
✅ 확인하는 법휴대폰·데스크톱 두 화면에서 5개 테스트 통과: 로그인 필요 · 리워드→배송지→확인 + 새로고침 유지 · 건너뛰기 막기 · 리워드 없이 후원(1,000원 이상, 배송지 건너뜀) · 마감·내 프로젝트 불가
🆘 막혔을 때
strict mode violation: getByText("후원 내용") resolved to 2 elements

작성자가 실제로 겪은 문제입니다. 같은 글자가 화면에 두 번 있으면 Playwright 가 어느 것인지 몰라 멈춥니다. 확인 화면의 상자에 role="group" 과 이름(aria-label="후원 내용")을 주고 getByRole("group", { name: "후원 내용", exact: true }) 로 찾으면 정확히 하나만 잡힙니다 — 화면 낭독기에도 좋은 구조예요.

🔁 방금 무슨 일이 일어났나세 단계 후원이 사람이 쓰는 순서대로 동작하는지 자동으로 확인하게 했습니다. 앞으로 후원 화면을 고치다 무언가를 망가뜨리면 CI 가 먼저 알려 줍니다.
