찜하기: 누르자마자 바뀌고, 실패하면 되돌아가기

하트를 누르면 서버 대답을 기다리지 않고 화면부터 바꿉니다(낙관적 업데이트). 서버가 실패하면 조용히 되돌리고 알려 줍니다. 카드·상세·헤더·내 찜이 같은 값을 함께 보게 하는 도구가 TanStack Query 입니다. 덤으로, 창작자 스튜디오가 새 후원을 스스로 확인하게 만듭니다.

🗺️ 이번 주 그림 — 찜 캐시 하나를 네 곳이 함께 본다
서버 (레이아웃)내 찜 목록을 미리 읽어 캐시에 채워 보낸다
찜 캐시 ["likes"]브라우저의 TanStack Query 캐시
카드의 하트목록·홈
상세의 하트+ 찜 개수
헤더의 ♡ 3내 찜 개수
내 찜 화면/me/likes

어디서 누르든 캐시가 바뀌고 → 네 곳이 동시에 바뀐다. 서버가 실패하면 캐시를 이전 값으로 되돌린다.

용어한 줄 뜻
TanStack Query서버에서 가져온 값을 브라우저에 캐시하고, 여러 컴포넌트가 함께 보게 하고, 다시 가져오는 때를 관리해 주는 도구
낙관적 업데이트"성공하겠지" 하고 화면부터 바꾸는 것. 실패하면 되돌린다
hydration서버가 만든 값을 브라우저가 이어받아 쓰는 것. 여기서는 서버가 채운 찜 캐시를 브라우저 캐시로 되살린다
React Context앱 전체에서 쓰는 도구(여기서는 토스트)를 어느 컴포넌트에서든 꺼내 쓰게 하는 React 기능
1찜 API: GET · POST · DELETE
💡 왜 서버 액션이 아니라 API(Route Handler)로?찜은 목록·상세·헤더 여러 곳에서 브라우저가 직접 부르고, TanStack Query 가 "가져오기(GET)"와 "바꾸기(POST·DELETE)"를 나눠 관리합니다. 9주차 API 설계 규칙(응답 코드, 에러 모양)을 그대로 씁니다.
✅ 확인하는 법
  • npx vitest run tests/db/likes.test.ts — 찜하기 두 번째는 "이미 있음", 취소는 여러 번 해도 같은 결과
  • 로그인 없이 /api/likes → 401, 잘못된 번호 → 400
🔁 방금 무슨 일이 일어났나찜을 "몇 번을 보내도 결과가 같은" API 로 만들었습니다 (새로 찜하면 201, 이미 찜해 있으면 200). 빠르게 두 번 눌러도 찜이 두 줄 생기지 않습니다.
2찜 버튼: 낙관적 업데이트와 되돌리기 + 토스트
🗺️ 그림 먼저 — 하트를 누른 뒤 0.5초 동안 일어나는 일
onMutate① 진행 중인 요청 멈추기 ② 지금 값 기억 ③ 캐시를 "성공한 셈"으로 바꾸기 → 하트가 바로 채워짐
onError실패면 ②의 값으로 되돌리고 토스트
onSettled성공이든 실패든 서버의 진짜 목록으로 다시 맞추기

TanStack Query 는 9주차(무한 스크롤)에 이미 설치했습니다 (@tanstack/react-query@5.104.0). 이번에는 "가져오기"(useQuery)에 더해 "바꾸기"(useMutation)를 씁니다.

첫 화면부터 하트가 채워져 있게, 레이아웃(서버)이 내 찜 목록을 캐시에 미리 채워 보냅니다.

💡 왜 토스트는 Zustand 가 아니라 Context?토스트는 "값"이라기보다 앱 전체가 쓰는 도구(show("…"))입니다. 저장·복원도 필요 없고 자주 바뀌지도 않습니다. 이럴 때는 React 에 들어 있는 Context 로 충분합니다 — 도구는 필요한 만큼만.
✅ 확인하는 법
  • 예시 계정으로 로그인 → 목록 카드의 하트를 누르면 즉시 채워지고, 헤더의 ♡ 숫자도 함께 +1
  • 상세로 가면 하트가 채워져 있고 찜 개수도 맞다 (새로 가져오지 않았는데도)
  • 로그아웃 상태에서 하트 → 로그인 화면으로, 로그인하면 원래 화면으로
🆘 막혔을 때
하트가 바뀌었다가 잠깐 뒤 원래대로 깜빡여요

진행 중이던 "찜 목록 가져오기"가 늦게 도착해 낙관적 값을 덮어쓴 경우입니다. onMutate 첫 줄의 cancelQueries 가 그걸 막습니다.

첫 화면에 하트가 비었다가 채워져요

서버에서 첫 값을 채우지 않은 경우입니다. 레이아웃의 setQueryData + HydrationBoundary, 그리고 서버와 브라우저가 같은 이름표(LIKES_KEY)를 쓰는지 확인하세요.

🔁 방금 무슨 일이 일어났나찜 상태를 브라우저 캐시 한 곳에 두고, 누르면 캐시부터 바꾸고(낙관적), 실패하면 되돌리게 했습니다. 서버가 첫 값을 채워 보내서 처음부터 깜빡임이 없습니다.
🤔 스스로 확인
낙관적 업데이트를 결제에도 쓰면 안 되는 이유는?

찜은 실패해도 되돌리면 그만이지만, 결제는 "성공한 척" 보여 줬다가 되돌리면 사용자가 크게 혼란스럽고 돈 문제가 됩니다. 되돌려도 괜찮은, 실패가 드문 동작에만 씁니다.

카드·헤더·상세가 따로 API 를 부르지 않는데도 같이 바뀌는 이유는?

모두 useLikes() 로 같은 캐시(["likes"])를 보기 때문입니다. 캐시가 바뀌면 그 캐시를 보는 모든 컴포넌트가 다시 그려집니다.

3내 찜 (/me/likes)
✅ 확인하는 법/me/likes 에서 하트를 눌러 취소하면 카드가 바로 사라지고, 헤더 숫자도 −1
🔁 방금 무슨 일이 일어났나서버가 그린 "내 찜" 목록을 찜 캐시로 한 번 더 걸러 보여 줍니다. 그래서 여기서 취소해도 새로고침 없이 사라지고, 실패하면 다시 나타납니다.
4창작자 스튜디오: 새 후원 자동 확인 + 토스트 중복 버그
🗺️ 그림 먼저 — 15초마다 조용히 다시 묻기
서버가 첫 목록initialData — 화면이 바로 보인다
/api/projects/[id]/fundings탭을 보고 있을 때만
새 후원?토스트 "새 후원 1건" + 새 줄 강조
🆘 작성자가 겪은 버그: 토스트가 세 번 떠요

새 후원이 1건인데 "새 후원 1건" 토스트가 여러 번 떴습니다. 원인: 토스트를 띄우면 ToastProvider 가 다시 그려지고, 그때 value={{ show }} 가 매번 새 객체가 되어 useToast() 값이 "바뀐 것"으로 보입니다. 그 값을 의존성에 넣은 useEffect 가 다시 돌아 토스트를 또 띄우는 거죠.

해결: const api = useMemo(() => ({ show }), [show]) — 값 객체를 한 번만 만들어서 계속 같은 객체를 넘깁니다 (2단계 ToastProvider 코드의 주석).

✅ 확인하는 법창작자 계정(ohneul_workshop@seed.moa.test)으로 스튜디오를 열어 두고, 다른 브라우저에서 그 프로젝트에 테스트 결제 → 15초 안에 목록에 나타나고 토스트가 한 번
🔁 방금 무슨 일이 일어났나같은 TanStack Query 로 "주기적으로 다시 가져오기"를 붙였습니다. 서버가 알려 주는(푸시) 기술 없이도, 작은 서비스에서는 이 정도로 충분합니다.
🤔 스스로 확인
새 후원을 "후원 번호"가 아니라 "결제 완료 시각"으로 판단하는 이유는?

먼저 만든 후원(결제 대기)이 결제창에 오래 머물다 나중에 결제될 수 있습니다. 번호가 작아도 "새로 결제된" 후원이에요.

5흐름 테스트 + 운영 빌드에서만 나는 문제 (prefetch)
💡 서버 실패를 어떻게 테스트하나요?page.route 로 찜 요청만 가로채 0.5초 뒤 500 을 돌려줍니다. "먼저 채워졌다가(낙관적) → 되돌아가고 → 토스트"를 차례로 확인합니다. 토스트 영역은 role="status" + 이름 "알림" 이라 다른 status 와 헷갈리지 않습니다.
🆘 작성자가 겪은 문제: 개발 서버에서는 되는데 운영 빌드에서만 내 찜이 비어요

운영 빌드의 Link 는 화면에 보이는 순간 다음 페이지를 미리 받아 둡니다(prefetch). 헤더의 "내 찜" 링크가 찜하기 전에 /me/likes 를 받아 두었다가, 찜한 뒤에 그 옛 화면을 보여 준 겁니다.

교훈: CI 는 운영 빌드(npm run start)로 흐름 테스트를 돌리기 때문에 이 문제를 잡았습니다. 개발 서버만 믿지 마세요.

🔁 방금 무슨 일이 일어났나"실패하면 되돌린다"는 약속을 일부러 실패를 만들어 확인했고, 운영 빌드에서만 나는 미리 받기(prefetch) 문제를 찾아 고쳤습니다.
