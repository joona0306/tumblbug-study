# 케이스 스터디 양식 (20주차)

> 포트폴리오를 보는 사람은 "무엇을 만들었나"보다 **"어떤 문제를, 어떻게 판단해서, 어떤 결과를 냈나"**를 봅니다.
> 모두가 같은 텀블벅 클론을 만들었더라도, 이 문서의 내용(내 인터뷰, 내 결정, 내 운영 숫자)은 사람마다 다릅니다.
> 1~2쪽 분량의 GitHub README 또는 개인 블로그 글로 만드세요.

```markdown
# [서비스 이름] — 크라우드펀딩 MVP

> 한 줄 소개. [운영 주소] · [GitHub] · [데모 영상 1분]

## 1. 문제와 사용자
- 인터뷰 [N]명에서 발견한 핵심 문제 (인용 1~2개)
- 가장 중요한 인사이트 1개

## 2. 무엇을 만들었나
- 핵심 흐름: 등록 → 후원 → 결과 (스크린샷 3장)
- 범위에서 뺀 것과 그 이유

## 3. 디자인
- 사용자 흐름도, 디자인 시스템(토큰·컴포넌트) 캡처, Figma 링크
- 사용성 테스트에서 발견해 고친 것 1~2개 (전/후)

## 4. 기술과 설계 결정
- 구조도 (브라우저 · Next.js · Neon · Vercel Blob · 토스페이먼츠 · Sentry)
- 중요한 결정 2~3개 (ADR 요약: 무엇을 골랐고 무엇을 포기했나)
- 상태 관리: 상태 지도(서버·URL·폼·화면·전역)와 도구 선택 이유 (Zustand와 TanStack Query를 어떻게 나눴나)
- DB: ERD, 인덱스 전후 실행 계획, 트랜잭션 경계를 어디에 뒀나
- 배포: CI/CD 파이프라인 그림 (PR → CI → 미리보기 → 승인 → 운영), Vercel(서버리스)과 Docker+EC2(직접 운영)의 차이, 롤백 연습 기록
- 품질을 지키는 방법: PR·CI, 테스트(무엇을 왜 테스트했나), 에러 모니터링

## 5. 운영과 개선
- 실제 운영: 창작자 [N]명, 프로젝트 [N]개, 후원 [N]건 (테스트 결제)
- 개선 사이클: 지표 [전] → 관찰 → 가설 → 변경 → 지표 [후]
- 운영 중 만난 문제와 대응 (Sentry 에러, 예약 작업 등)

## 6. 알려진 한계와 다음 단계
- 예: 후원 즉시 결제(실제 서비스는 마감 후 결제), 환불·정산 없음
- 다음에 한다면 무엇을 먼저 할지

## 7. 배운 것
- 1~3단계와 비교해 가장 크게 달라진 점 3가지
```

## 작성 요령
- **숫자로**: "빨라졌다" 대신 "후원 완료율 3.1% → 4.8%"
- **포기한 것도 쓰기**: 선택지를 비교하고 버린 흔적이 판단력을 보여줍니다
- **짧게**: 긴 설명은 ADR·PR 링크로 대신합니다
- **정직하게**: 테스트 결제로 운영했다면 그렇게 씁니다
