# 데이터 모델: 개념 ERD → 화면-데이터 매핑 → 물리 ERD

> **ERD(개체-관계 그림)**: 저장할 데이터 덩어리(개체)를 네모로, 그 사이의 관계를 선으로 그린 그림.
> 실무에서는 **기획 단계에 개념 ERD**(무엇이 있고 어떻게 연결되나)를 먼저 그리고,
> **개발 단계에서 물리 ERD**(실제 표·칸·타입·제약 조건)로 구체화합니다.
>
> | 언제 | 무엇 | 누가 봐도 이해되나 |
> |---|---|---|
> | 2주차 (기획) | ① 개념 ERD | 기획자·디자이너·개발자 모두 |
> | 3~4주차 (디자인) | ② 화면-데이터 매핑표 | 디자이너·개발자 |
> | 6주차 (DB 심화) | ③ 물리 ERD | 개발자 |
>
> 아래는 이 교재의 예시 답안입니다. 여러분의 PRD 범위에 맞게 고쳐 그리세요. Figma 예시 파일의 Flow 페이지에 그림이 있습니다.

## ① 개념 ERD (2주차)

### 그리는 순서
1. PRD의 사용자 스토리에서 **명사**를 뽑는다: 사용자, 창작자, 후원자, 프로젝트, 리워드, 후원, 결제, 찜, 배송지, 사진, 카테고리…
2. **저장해야 하고, 여러 개가 생기는 것**만 개체(네모)로 남긴다
   - 창작자·후원자·관리자 → 모두 "사용자" 하나 (역할만 다름)
   - 배송지 → 후원마다 하나씩 적으므로 후원의 속성 (따로 주소록 기능이 없으니까)
   - 카테고리 → 고정된 몇 개 중 하나라면 프로젝트의 속성, 관리자가 늘리고 줄이면 개체
   - 사진 → 대표 사진 1장이라 프로젝트의 속성 (여러 장이면 개체)
3. 개체 둘씩 짝지어 **두 방향으로** 묻는다: "프로젝트 1개에 리워드는 몇 개? → 여러 개", "리워드 1개는 프로젝트 몇 개에 속하나? → 1개" ⇒ 프로젝트 1 : N 리워드
4. 양쪽 다 "여러 개"면 **N : M** — 사이에 연결 개체가 필요하다 (예: 찜)

### 예시 답안
```
사용자 ─1────N─ 프로젝트        (한 사용자가 여러 프로젝트를 만든다 — 창작자로서)
프로젝트 ─1────N─ 리워드
사용자 ─1────N─ 후원           (한 사용자가 여러 번 후원한다 — 후원자로서)
프로젝트 ─1────N─ 후원
리워드 ─1────N─ 후원           (후원은 리워드 0개 또는 1개 — "리워드 없이 후원" 가능)
사용자 ─N────M─ 프로젝트        (찜: 한 사람이 여러 프로젝트를, 한 프로젝트를 여러 사람이)
```

| 개체 | 핵심 속성 (이름만, 타입 없이) |
|---|---|
| 사용자 | 이메일, 이름, 역할(일반/관리자) |
| 프로젝트 | 제목, 한 줄 요약, 소개, 카테고리, 목표 금액, 마감일, 대표 사진, 상태, 숨김 여부 |
| 리워드 | 이름, 설명, 금액, 수량 한정, 판매 수량, 전달 시기, 배송 필요 여부 |
| 후원 | 수량, 추가 후원금, 총액, 응원 메시지, 배송지(받는 사람·연락처·주소), 결제 상태, 실패 이유 |
| 찜 | (사용자와 프로젝트를 잇는 것 자체가 정보) + 찜한 날짜 |

### 범위 판단에 쓰기 (PRD와 연결)
- "리워드에 색상·사이즈 옵션" → 리워드 옵션 개체 + 후원-옵션 연결이 추가되고 수량 계산이 옵션별로 바뀜 → **이번 범위 제외** 근거
- "사진 여러 장" → 사진 개체 + 순서 → 제외
- "배송지를 주소록으로 저장" → 사용자 1 : N 주소 개체 → 제외 (후원마다 입력)

## ② 화면-데이터 매핑표 (3~4주차)

> 시안의 글자·숫자 하나하나가 **어느 개체의 어느 속성에서, 어떻게 계산되어** 오는지 적는다.
> 칸이 비면 → 데이터가 없는 것 → ERD를 고치거나 시안에서 뺀다.

| 화면 | 보이는 것 | 출처 | 계산 | 누가 볼 수 있나 |
|---|---|---|---|---|
| 목록 카드 | 진행률 78% | 후원(결제 완료)의 총액 합계 ÷ 프로젝트 목표 금액 | 합계 | 모두 |
| 목록 카드 | 12일 남음 | 프로젝트 마감일 − 오늘 | 계산 | 모두 |
| 상세 | 후원자 48명 | 후원(결제 완료) 중 서로 다른 사용자 수 | 개수 | 모두 |
| 상세 | 12개 남음 | 리워드 수량 한정 − 판매 수량 | 계산 | 모두 |
| 상세·카드·헤더 | 찜 ♥ / 찜 3 | 찜(사용자, 프로젝트) 존재 여부 / 내 찜 개수 | 개수 | 본인 |
| 대시보드 | 찜 → 후원 전환 4.0% | 찜한 사용자 중 후원한 사용자 비율 | 찜 + 후원 연결 | 창작자 본인 |
| 대시보드 | 최근 후원자·배송지 | 후원의 배송지 속성 | 목록 | **해당 프로젝트 창작자만, 결제 완료 건만** |
| 내 후원 | 결과 "성공 142%" | 프로젝트 상태 + 진행률 | 계산 | 본인 |

발견한 것 (예시):
- "찜 → 후원 전환율"은 찜 날짜와 후원 날짜가 모두 있어야 "찜한 뒤 후원했는지"를 알 수 있다 → 찜에 날짜 속성 추가
- 배송지는 개인정보 → 누가 볼 수 있는지 칸을 매핑표에 둔다 (권한 설계로 이어짐)

## ③ 물리 ERD (6주차)

> 개념 ERD를 실제 표로 바꾼다. **무엇이 바뀌었는지** 적어 두면 케이스 스터디 재료가 된다.

| 개념 ERD | 물리 ERD에서 | 이유 |
|---|---|---|
| 사용자 | `user` (Better Auth 표) + `role` 칸, 비밀번호는 `account`, 로그인 기록은 `session` | 인증 라이브러리 구조 + 보안 |
| 1 : N 선 | N 쪽 표의 외래 키 칸 (`project.creator_id`, `reward.project_id`, `funding.project_id` …) | 관계를 칸으로 표현 |
| 찜 (N : M) | 연결 표 `project_like(user_id, project_id, created_at)`, 두 칸을 합쳐 기본 키 | 같은 프로젝트를 두 번 찜하지 못하게 DB가 막음 |
| 후원의 "리워드 0~1개" | `funding.reward_id` 는 비울 수 있음(NULL 허용) | 리워드 없이 후원 |
| 진행률·후원자 수 | **저장하지 않음** — SQL 집계로 계산 | 저장하면 두 곳의 값이 어긋날 수 있음 (정규화) |
| 판매 수량 | `reward.sold_qty` 는 저장 (예외) | 결제 순간 조건부 차감으로 초과 판매를 막기 위해 (ADR-003) |
| 금액 | 정수(원 단위) + `CHECK (amount > 0)` | 소수점 오차 방지, 잘못된 값은 DB가 거절 |
| 웹훅 | `payment_event` 표 추가, `event_id` UNIQUE | 개념 단계엔 없던 "시스템이 필요로 하는 데이터" |
| 자주 거르는 조건 | 인덱스: `project(status, deadline)`, `funding(project_id, status)` | 목록·집계 속도 (EXPLAIN ANALYZE 전후 비교) |

> 💡 정규화: "같은 사실을 한 곳에만 저장한다". 진행률을 프로젝트 표에 저장하면 후원이 들어올 때마다 두 곳을 고쳐야 하고,
> 하나라도 빠지면 값이 어긋납니다. 대신 판매 수량처럼 **동시성 제어가 필요한 값은 의도적으로 저장**할 수 있고, 그 이유를 ADR로 남깁니다.
