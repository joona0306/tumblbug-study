# 결정 기록 (ADR, Architecture Decision Record)

> **ADR**: 중요한 결정을 내릴 때마다 "무엇을, 왜, 무엇을 포기하고" 정했는지 짧게 남기는 기록.
> 나중에 "왜 이렇게 만들었지?"에 답할 수 있고, 포트폴리오에서 **내 판단력**을 보여주는 가장 좋은 자료입니다.
>
> 규칙: 결정 1개 = 파일 1개(`adr/001-제목.md`). 번호는 바꾸지 않고, 결정을 뒤집으면 새 ADR을 쓰고 옛 것에 "대체됨"을 적습니다.

## 양식
```
# ADR-000: [결정 제목]
- 상태: 제안 / 결정 / 대체됨(ADR-0xx)
- 날짜: YYYY-MM-DD

## 상황
무엇을 정해야 하나? 왜 지금 정해야 하나?

## 선택지
1. [선택지 A] — 장점 / 단점
2. [선택지 B] — 장점 / 단점

## 결정
[무엇을 골랐나]

## 이유
[왜. 인터뷰·지표·제약 조건 등 근거]

## 결과 (포기한 것, 해야 할 일)
- 
```

## 예시 ADR-001: 모금 상태를 어떻게 정할까
- 상태: 결정
- 날짜: (4단계 2주차)

### 상황
프로젝트는 마감일이 지나면 목표 달성 여부에 따라 성공/실패가 된다. 누가, 언제 이 상태를 정할지 결정해야 한다.

### 선택지
1. **화면을 열 때마다 계산** — 항상 정확, 추가 도구 불필요 / 목록에서 "성공한 것만" 같은 필터를 SQL로 하기 어렵고, 기록이 남지 않음
2. **예약 작업이 하루 1번 DB에 저장** — 필터·기록이 쉬움 / 작업이 돌기 전까지는 화면이 틀릴 수 있음(최대 하루)
3. **둘 다** — 계산은 순수 함수 하나로, 화면은 항상 계산값, 예약 작업은 확정값을 저장

### 결정
3번. `getProjectStatus(목표, 모인 금액, 마감일, 지금)` 순수 함수 + Vercel Cron 하루 1번 확정.

### 이유
- 사용자에게 보이는 값은 언제나 정확해야 한다 (인터뷰: 후원자는 결과를 다시 확인한다)
- 순수 함수는 **입력이 같으면 결과가 같아서** 단위 테스트로 경계값(마감 당일 23:59:59, 목표 딱 도달)을 확실히 검증할 수 있다
- 확정값이 DB에 있으면 목록 필터·성공률 지표를 SQL 한 줄로 계산할 수 있다

### 결과
- 예약 작업이 실패하면 필터가 하루 늦을 수 있음 → 운영 루프에서 작업 로그 확인
- 계산 로직은 반드시 이 함수 한 곳에만 둔다 (화면·예약 작업이 같은 함수를 씀)

## 예시 ADR-002: 후원금은 언제 결제할까
- 상태: 결정
- 날짜: (4단계 2주차)

### 상황
실제 텀블벅은 후원 시 결제 수단만 등록해 두고, **마감 후 성공한 프로젝트만** 결제한다. 우리도 그렇게 할지 정해야 한다.

### 선택지
1. **후원 즉시 결제** (2단계 방식 재사용) — 이미 배운 흐름, 구현 단순 / 실패 프로젝트는 원래 환불이 필요
2. **마감 후 결제 (빌링키 예약 결제)** — 실제 서비스와 같음 / 카드 등록·자동결제 계약·실패 재시도 등 범위가 크게 늘어남

### 결정
1번. 후원 즉시 (테스트) 결제.

### 이유
- 14주 안에 핵심 흐름을 운영 수준(테스트·모니터링 포함)으로 끝내는 것이 목표
- 결제는 테스트 모드라 실제 돈이 움직이지 않는다

### 결과
- 케이스 스터디의 "알려진 한계"에 명시한다
- 다음 버전 후보: 빌링키 예약 결제 (실패 프로젝트 자동 미결제)
