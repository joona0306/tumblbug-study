# 결정 기록 (ADR, Architecture Decision Record)

> **ADR**: 중요한 결정을 내릴 때마다 "무엇을, 왜, 무엇을 포기하고" 정했는지 짧게 남기는 기록.
> 나중에 "왜 이렇게 만들었지?"에 답할 수 있고, 포트폴리오에서 **내 판단력**을 보여주는 가장 좋은 자료입니다.
>
> 규칙: 결정 1개 = 파일 1개(`adr/001-제목.md`). 번호는 바꾸지 않고, 결정을 뒤집으면 새 ADR을 쓰고 옛 것에 "대체됨"을 적습니다.

## 양식
```
# ADR-000: [결정 제목]
- 상태: 제안 / 결정 / 대체됨(ADR-0xx)
- 날짜: YYYY-MM-DD

## 상황
무엇을 정해야 하나? 왜 지금 정해야 하나?

## 선택지
1. [선택지 A] — 장점 / 단점
2. [선택지 B] — 장점 / 단점

## 결정
[무엇을 골랐나]

## 이유
[왜. 인터뷰·지표·제약 조건 등 근거]

## 결과 (포기한 것, 해야 할 일)
- 
```

## 예시 ADR-001: 모금 상태를 어떻게 정할까
- 상태: 결정
- 날짜: (4단계 2주차)

### 상황
프로젝트는 마감일이 지나면 목표 달성 여부에 따라 성공/실패가 된다. 누가, 언제 이 상태를 정할지 결정해야 한다.

### 선택지
1. **화면을 열 때마다 계산** — 항상 정확, 추가 도구 불필요 / 목록에서 "성공한 것만" 같은 필터를 SQL로 하기 어렵고, 기록이 남지 않음
2. **예약 작업이 하루 1번 DB에 저장** — 필터·기록이 쉬움 / 작업이 돌기 전까지는 화면이 틀릴 수 있음(최대 하루)
3. **둘 다** — 계산은 순수 함수 하나로, 화면은 항상 계산값, 예약 작업은 확정값을 저장

### 결정
3번. `getProjectStatus(목표, 모인 금액, 마감일, 지금)` 순수 함수 + Vercel Cron 하루 1번 확정.

### 이유
- 사용자에게 보이는 값은 언제나 정확해야 한다 (인터뷰: 후원자는 결과를 다시 확인한다)
- 순수 함수는 **입력이 같으면 결과가 같아서** 단위 테스트로 경계값(마감 당일 23:59:59, 목표 딱 도달)을 확실히 검증할 수 있다
- 확정값이 DB에 있으면 목록 필터·성공률 지표를 SQL 한 줄로 계산할 수 있다

### 결과
- 예약 작업이 실패하면 필터가 하루 늦을 수 있음 → 운영 루프에서 작업 로그 확인
- 계산 로직은 반드시 이 함수 한 곳에만 둔다 (화면·예약 작업이 같은 함수를 씀)

## 예시 ADR-002: 후원금은 언제 결제할까
- 상태: 결정
- 날짜: (4단계 2주차)

### 상황
실제 텀블벅은 후원 시 결제 수단만 등록해 두고, **마감 후 성공한 프로젝트만** 결제한다. 우리도 그렇게 할지 정해야 한다.

### 선택지
1. **후원 즉시 결제** (2단계 방식 재사용) — 이미 배운 흐름, 구현 단순 / 실패 프로젝트는 원래 환불이 필요
2. **마감 후 결제 (빌링키 예약 결제)** — 실제 서비스와 같음 / 카드 등록·자동결제 계약·실패 재시도 등 범위가 크게 늘어남

### 결정
1번. 후원 즉시 (테스트) 결제.

### 이유
- 16주 안에 핵심 흐름을 운영 수준(테스트·모니터링 포함)으로 끝내는 것이 목표
- 결제는 테스트 모드라 실제 돈이 움직이지 않는다

### 결과
- 케이스 스터디의 "알려진 한계"에 명시한다
- 다음 버전 후보: 빌링키 예약 결제 (실패 프로젝트 자동 미결제)

## 예시 ADR-003: 수량 한정 리워드를 어떻게 초과 판매 없이 팔까
- 상태: 결정
- 날짜: (4단계 2주차)

### 상황
"선착순 100개" 리워드가 1개 남았을 때 두 사람이 거의 동시에 결제하면, 둘 다 "1개 남음"을 보고 결제할 수 있다.
둘 다 승인하면 **없는 물건을 판 것**이 된다.

### 선택지
1. **결제 전에 남은 수량 확인만** — 단순 / 확인과 결제 사이에 다른 사람이 끼어들 수 있음 (동시성 문제)
2. **후원 시작 시 10분간 수량 예약** — 결제 중엔 확실히 내 것 / 예약 만료 처리(예약 작업)가 필요하고, 결제를 안 하고 나간 사람이 수량을 잡아둠
3. **결제 승인 직전에 조건부 차감** — `sold_qty + 수량 <= limit_qty`일 때만 늘리는 UPDATE 한 줄. DB가 한 번에 한 요청씩 처리하므로 둘 중 하나만 성공 / 드물게 "결제창까지 갔는데 품절"을 겪는 사람이 생김

### 결정
3번. 토스페이먼츠는 **서버가 승인 API를 호출하기 전까지 돈을 가져가지 않으므로**, 차감에 실패하면 승인하지 않고 "품절" 안내만 하면 된다.

### 이유
- 초과 판매 0건을 코드 한 곳(UPDATE 한 줄)으로 보장 — 테스트하기 쉽다
- 예약·만료 같은 추가 상태가 없다

### 결과
- 승인 API가 실패하면 차감한 수량을 되돌려야 한다 (되돌리기 누락을 점검하는 SQL을 운영 루프에 추가)
- 결제 실패 이유에 `SOLD_OUT`이 생긴다 → 퍼널 지표에서 따로 본다

## 예시 ADR-004: 전역 상태는 어떤 도구로 관리할까
- 상태: 결정
- 날짜: (4단계 5주차)

### 상황
두 곳에서 "여러 화면이 함께 쓰는 값"이 생겼다.
- 여러 단계 후원: ①리워드 → ②배송지 → ③확인 페이지를 오가도 선택이 유지되고, 새로고침해도 사라지지 않아야 한다
- 찜: 카드·상세의 하트와 헤더의 찜 개수가 동시에 바뀌고, 누르자마자 반영돼야 한다

### 선택지
1. **React Context + useState** — 추가 설치 없음 / 값이 바뀌면 그 Context를 쓰는 화면 전체가 다시 그려짐, 새로고침 유지는 직접 구현
2. **Zustand** — 작고 배우기 쉬움, 필요한 값만 골라 구독, `persist`로 브라우저 저장 한 줄 / 라이브러리 하나 추가
3. **TanStack Query** — 서버 데이터 캐시·재시도·자동 새로고침에 강함 / 이 앱은 서버 컴포넌트가 데이터를 가져오므로 역할이 겹침, 후원 단계 선택 같은 "브라우저에만 있는 값"에는 맞지 않음

### 결정
Zustand (후원 단계 스토어 + 찜 스토어). 토스트처럼 "앱 전체에 한 개, 자주 안 바뀌는 값"은 React Context.

### 이유
- 두 문제 모두 "브라우저에만 있는 값을 여러 화면이 공유"하는 문제다 → 클라이언트 상태 도구가 맞다
- `persist` 미들웨어로 새로고침 유지가 한 줄, 선택적 구독으로 불필요한 다시 그리기가 없다

### 결과
- 서버가 진실의 원천: 찜 스토어는 서버에서 받은 초기값으로 시작하고, 서버 응답이 실패하면 되돌린다
- 결제 완료 시 후원 단계 스토어를 비운다 (다음 후원에 이전 선택이 남지 않게)
- 케이스 스터디에 "TanStack Query를 쓰지 않은 이유"를 적는다

## 상태 전이도 (2주차에 그릴 것)
> **상태 전이도**: 어떤 것이 가질 수 있는 상태와, 어느 상태에서 어느 상태로만 바뀔 수 있는지를 그린 그림.
> 화살표가 없는 방향(예: 완료 → 대기)은 **코드에서 막아야 하는 버그**다. 각 화살표가 곧 테스트 케이스가 된다.

```
프로젝트   [모금중] ──마감 시각, 모인 금액 ≥ 목표──▶ [성공]
              └──────마감 시각, 모인 금액 < 목표──▶ [실패]      (성공·실패는 끝. 되돌아가지 않음)

후원(결제) [결제 대기] ──승인 성공──▶ [완료]
               ├─────품절(차감 실패)──▶ [실패: SOLD_OUT]
               ├─────승인 실패────────▶ [실패: 카드 거절 등]  → 차감 되돌리기
               └─────사용자 취소──────▶ [실패: USER_CANCEL]

리워드 수량 [남음] ──sold_qty = limit_qty──▶ [품절] ──승인 실패로 되돌림──▶ [남음]
```
