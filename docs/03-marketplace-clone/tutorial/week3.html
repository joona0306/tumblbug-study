검색·필터·상태, 그리고 누구에게 무엇을 보여줄까

이번 주는 "찾기"와 "권한"입니다. 검색 조건을 주소에 담는 방법을 배우고, 주소·숨은 칸처럼 브라우저가 보내는 모든 값을 서버가 어떻게 걸러내는지 익힙니다.

먼저 그림으로: 검색 조건은 주소를 타고 SQL이 된다

1제목 검색
📖 LIKE 와 이스케이프SQL의 LIKE '%의자%'는 "의자가 들어간 것"입니다. 여기서 %는 "아무 글자 여러 개", _는 "아무 글자 하나"라는 특별한 뜻이에요. 사용자가 100%를 검색하면 %가 특별한 뜻으로 해석되지 않도록 앞에 \를 붙여 "그냥 글자"로 만듭니다(이스케이프). ILIKE의 I는 대소문자 무시.
✅ 확인하는 법 (작성자 검증 결과와 비교)
검색어기대 결과
패드"아이패드…"처럼 중간에 들어간 것도 찾는다
switch / SWITCH"Nintendo Switch…"를 둘 다 찾는다 (대소문자 무시)
%제목에 실제로 %가 든 상품만 (이스케이프를 안 했다면 전체가 나옴)
'; drop table product;--0개, 표는 멀쩡 (Drizzle이 값을 SQL과 분리해서 보내기 때문)

검색 후 주소창에 ?q=…가 붙고, 새로고침해도 결과가 유지된다.

💡 알려진 한계"스위치"로 검색하면 영어 제목 "Switch"는 못 찾습니다. 글자가 다르니까요. 실제 서비스는 별칭 사전이나 검색 전용 엔진을 쓰는데, 이번 범위 밖입니다. 4주차 개선 아이디어로 적어 두세요.

2카테고리·판매중 필터
📖 조건을 배열에 모으기const conditions: SQL[] = []에 켜진 조건만 넣고 and(...conditions)로 묶습니다. 조건이 몇 개든 같은 코드로 처리되고, 하나도 없으면 전체 목록이 됩니다. ProductFilter의 category 타입이 Category라서, 검사 안 한 글자를 넘기면 타입 에러가 납니다.

app/globals.css의 .search { … } 블록을 아래로 바꾸고, 체크박스 스타일을 추가합니다. (검색창이 이제 폼이 아니라 폼 안의 div라서 display: flex가 필요해요)

✅ 확인하는 법
  • 카테고리만, 판매중만, 검색어+카테고리 등 조합해도 맞는 결과가 나온다
  • 결과 주소를 복사해 시크릿 창에 붙여 넣으면 같은 조건의 화면이 열린다
  • 주소를 직접 ?category=해킹으로 바꾸면 무시되고 전체 목록 (서버 검사)
  • "조건 지우기"로 처음 화면

🆘 작성자가 실제로 빠질 뻔한 함정

처음엔 return value in STATUS_LABELS;로 썼습니다. 그런데 in은 모든 객체가 물려받는 이름까지 찾아서, "toString" 같은 값도 통과해 버립니다. 누군가 상태 값으로 toString을 보내면 DB에 이상한 값이 들어갈 뻔했어요. Object.hasOwn은 우리가 직접 적은 키(selling, sold)만 인정합니다. 타입 가드도 결국 코드라서 테스트가 필요합니다.

4연락 방법은 로그인한 사람에게만

상세 페이지에서 판매자의 contact를 함께 조회하되, 로그인한 경우에만 화면에 그립니다.

💡 "숨기기"와 "안 보내기"는 다르다

CSS로 가리거나 브라우저에서 조건을 걸어 숨기면, 값 자체는 브라우저로 이미 전달되어 F12로 볼 수 있습니다. 이 페이지는 서버 컴포넌트라서, 조건에 맞지 않아 그리지 않은 값은 아예 보내지 않아요. 작성자 검증: 로그인하지 않은 요청의 응답 전체에서 연락처 문자열을 찾았더니 없었습니다.

주의: 이 값을 "use client" 부품에 props로 넘기면 그 순간 브라우저로 전달됩니다. 민감한 값은 서버 컴포넌트에서 거른 뒤에만 넘기세요.

✅ 확인하는 법
  • 시크릿 창(로그인 안 함)에서 상세 → "로그인하면 판매자 연락 방법을 볼 수 있어요." Ctrl+U(페이지 소스)에서 연락처를 검색해도 없다
  • 다른 계정으로 로그인 → 판매자의 연락 방법이 보인다
  • 연락 방법을 안 적은 판매자의 상품 → "판매자가 아직 연락 방법을 적지 않았어요."
