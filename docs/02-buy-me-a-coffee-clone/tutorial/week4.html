배포하고, 결제를 10번 해보고, 실패에서 배우기

배포 과정은 1단계에서 한 번 해봤으니 빠르게 지나갑니다. 이번 주의 중심은 결제가 실패하는 이유를 기록하고 모아 보는 운영입니다.

1배포 준비 (1단계에서 가져온 것 확인)

배포 설정은 1단계 코드를 복사할 때 이미 따라왔습니다. 무엇이 준비되어 있는지만 확인하세요.

파일하는 일2단계에서 달라진 점
scripts/migrate.mjs운영 배포 때 DB 구조 자동 반영이번에는 기록 3개(init, add_bio, add_support)가 순서대로 적용됨
vercel.json서버 위치 싱가포르그대로
app/layout.js의 <Analytics />방문 수 측정그대로
/api/healthDB 상태 확인그대로

그다음은 1단계 4주차와 같은 순서입니다.

  1. GitHub에 새 저장소 my-coffee를 만들고 push (1단계 방법)
  2. Neon my-coffee 프로젝트에 dev 브랜치를 만들고 .env.local을 dev 주소로 교체, 기본 브랜치의 테스트 데이터 정리 (1단계 방법). 정리 SQL은 DELETE FROM "user"; — support 줄도 함께 지워집니다(cascade)
2Vercel 배포 (환경 변수 5개)

vercel.com/new에서 my-coffee를 Import하고 환경 변수 5개를 넣습니다.

KeyValue
DATABASE_URLNeon my-coffee 기본 브랜치의 주소
BETTER_AUTH_SECRET새로 만든 운영용 문자열 (개발용과 다르게)

💡 NEXT_PUBLIC_ 값을 바꿨다면 꼭 다시 배포NEXT_PUBLIC_로 시작하는 값은 빌드할 때 브라우저 코드 안에 글자로 박혀 들어갑니다. Vercel에서 값을 바꿔도 이미 만들어진 코드에는 옛 값이 남아 있어요. 바꾼 뒤에는 Deployments → Redeploy를 하세요.
🆘 결제 성공 후 localhost로 이동해요

성공·실패 주소는 코드에서 window.location.origin(지금 접속한 주소)으로 만들기 때문에 운영에서는 자동으로 운영 주소가 됩니다. localhost로 간다면 운영 주소가 아니라 내 컴퓨터에서 결제한 것이니 주소창을 확인하세요.

✅ 확인하는 법
  • 빌드 로그에 [migrate] 운영 DB 마이그레이션 완료
  • 운영 주소에서 가입 → 소개 저장 → 내 후원 페이지에 결제위젯이 보인다
  • 휴대폰으로 내 후원 페이지에 들어가 테스트 결제 1회 → 감사 화면 → 대시보드 합계 반영
3테스트 결제 10회 — 성공도, 실패도 일부러

결제 기능은 "한 번 됐다"로 끝내면 안 됩니다. 운영 주소에서 아래 시나리오를 모두 해보고 결과를 체크하세요. 실패 시나리오도 일부러 만들어야 실패 처리가 제대로 되는지 알 수 있어요.

#시나리오기대 결과 (DB의 status / fail_reason)
1~33,000 / 5,000 / 10,000원 각각 결제 완료paid 3건, 대시보드 합계 18,000원 증가
4이름을 비우고 결제 완료paid, 공개 페이지에 "익명"
5줄바꿈이 있는 메시지로 결제 완료공개 페이지에 줄바꿈 그대로
6~7결제창을 열었다가 닫기 (PC 1회, 휴대폰 1회)failed / USER_CANCEL
8금액 위조 (2주차 3단계 실습을 운영 주소로)failed / AMOUNT_MISMATCH
9감사 화면에서 새로고침 3번후원 건수 그대로
10결제창을 연 채로 브라우저 탭을 닫아버리기pending으로 남음 → 4단계 SQL에서 "중간에 사라진 주문"으로 잡힘 (30분 후)
4측정과 실패 추적 (운영 루프)

① 성공 지표: 결제 완료율

② 실패는 왜 났나

두 파일을 프로젝트의 sql/ 폴더에 저장해 두고, Neon SQL Editor(기본 브랜치)에 붙여넣어 실행합니다. 실패 SQL은 두 덩어리라 하나씩 실행하세요.

✅ 확인하는 법3단계 시나리오를 다 했다면 대략 이런 결과가 나옵니다: 결제 시도 11건 이상, 완료 5건 이상, 실패 이유에 USER_CANCEL 2건과 AMOUNT_MISMATCH 1건. (작성자 검증 데이터: 시도 8건 / 완료 3건 → 37.5%, 실패 이유 4종 집계)

③ 로그와 함께 보기

  • Vercel → Logs에서 [결제]로 검색하면, 승인 실패·금액 불일치 때 남긴 로그(orderId, 이유)가 나옵니다. SQL의 order_id와 맞춰 보면 "언제, 어떤 주문이, 왜" 실패했는지 알 수 있어요.
  • 개발자센터에 가입해 내 테스트 키를 쓴다면, 개발자센터의 결제 로그에서 토스 쪽 기록도 볼 수 있습니다.
💡 실패 이유를 읽는 법USER_CANCEL이 많다 = 결제창까지 갔다가 마음을 바꿨다(결제 과정이 번거로운가?). AMOUNT_MISMATCH가 있다 = 누군가 조작을 시도했거나 코드에 금액 버그가 있다(반드시 확인). "중간에 사라진 주문"이 많다 = 결제창에서 이탈이 많다. 같은 "실패"라도 대응이 다릅니다.

5사용성 테스트 + 접근성 점검

방법은 1단계 4주차 7단계와 같습니다. 이번 과제는 두 역할로 나눕니다.

역할과제
후원자 (지인 A)1. 이 크리에이터에게 5,000원을 후원하고 응원 메시지를 남겨 주세요 (테스트 결제라 돈은 안 나가요)
2. 방금 남긴 메시지가 어디에 보이는지 찾아 주세요
크리에이터 (지인 B)1. 가입하고 한 줄 소개를 써 주세요
2. 내 후원 페이지 주소를 찾아 복사해 주세요
3. 지금까지 받은 후원 합계를 알려 주세요

접근성: Tab만으로 금액 고르기(방향키로 바꾸기) → 이름·메시지 → 결제위젯 → 후원하기까지 갈 수 있는지, Lighthouse 접근성 점수가 90점 이상인지 확인하세요. (작성자 검증: 교재 코드 그대로면 후원 페이지·대시보드·실패 페이지 모두 100점)

6지표 기반 개선 1개

1단계에서 배운 개선 사이클(지표 → 관찰 → 가설 → 수정·배포 → 재측정)을 결제 완료율로 한 바퀴 돕니다.

예시로 한 바퀴

  1. 지표: 결제 완료율 50%, 실패 이유는 대부분 USER_CANCEL
  2. 관찰: 지인 A가 결제위젯에서 결제수단을 한참 고민하다 창을 닫음. "테스트인데 진짜 돈 나가는 거 아니지?"라고 물음
  3. 가설: "후원하기 버튼 바로 위에 '테스트 결제라 실제로 돈이 나가지 않아요' 안내를 두면 USER_CANCEL이 줄 것"
  4. 수정·배포: 그 한 줄만 추가해 push
  5. 재측정: 며칠 뒤 새 후원들로 완료율과 실패 이유를 다시 계산

2단계 완료 기준 점검

부록: 실제로 돈을 받으려면

지금 서비스는 테스트 키라서 돈이 움직이지 않습니다. 실제 결제를 받으려면 코드보다 코드 밖의 준비가 훨씬 많아요. 교재 범위 밖이지만 큰 그림만 알아 두세요. (정확한 요건은 시점과 사업 형태에 따라 달라지니 반드시 공식 안내와 전문가에게 확인하세요.)

준비물왜 필요한가
사업자등록PG사와 계약하려면 보통 사업자가 필요합니다
통신판매업 신고인터넷으로 돈을 받고 무언가를 제공하는 사업이면 대개 필요합니다
PG사 가맹 계약·심사토스페이먼츠 등과 계약하고 심사를 통과해야 라이브 키가 발급됩니다. 이때 테스트 키를 라이브 키로 바꿉니다
이용약관 · 개인정보처리방침 · 환불 정책결제하는 사람에게 규칙과 개인정보 처리 방법을 알려야 합니다
후원(기부)의 성격 검토대가 없는 금전 모집은 법적으로 다르게 취급될 수 있어, 서비스 형태에 맞는 검토가 필요합니다
정산·세금받은 돈을 크리에이터에게 나눠 주려면 정산 구조와 세금 처리가 필요합니다 (이번 범위의 "제외" 항목)
